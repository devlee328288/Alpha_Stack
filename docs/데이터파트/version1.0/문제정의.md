## 2. 문제 진술

### 2.1 누구의 문제인가

**나의 문제가 아니라 뒤 순번 팀원의 문제입니다.**

이 파트가 잘 되면 아무도 눈치채지 못합니다. 잘못되면 **그 사실을 아무도 눈치채지
못한 채** 프로젝트 전체가 틀린 결론을 냅니다. 그게 이 파트의 성격입니다.

| 이 파트가 실패하는 방식 | 뒤에서 무슨 일이 일어나나 |
|---|---|
| 자료가 **없다** | 팀원이 첫 줄을 못 쓴다. 눈에 보이므로 즉시 발견된다 |
| 자료가 **틀렸다** | 모델이 돌아가고 성능도 나온다. **아무도 모른다** ← 🔴 진짜 위험 |
| 자료가 **미래를 본다** | 성능이 좋게 나온다. 발표하고 나서야 틀린 걸 안다 ← 🔴 최악 |
| 자료를 **다시 못 만든다** | 재현이 안 된다. 결론이 주장으로 격하된다 |

### 2.2 그래서 이 파트의 산출물은 '데이터'가 아니다

> **산출물은 데이터가 아니라 "그 데이터를 믿어도 되는 이유"입니다.**

이건 팀 전체의 문제 정의와 같은 자세입니다. 이 프로젝트는 *"예측기가 아니라 검증기를
만든다"* 로 방향을 잡았습니다([ADR-AS-0002](../../decisions/0002-예측대상과-레이블.md)).
데이터 계층에서 그 말을 번역하면 이렇게 됩니다 —

**"자료를 모았다"가 아니라 "이 자료가 무엇을 언제 어디서 어떻게 담았고, 무엇이 빠졌는지
말할 수 있다."**

### 2.3 가장 비싼 실패 — Point-in-Time 위반

🔴 **이 파트에서 가장 조용하고 가장 치명적인 오류입니다.**

2020 사업연도 재무제표를 `2020-12-31` 행에 붙이면 **미래를 본 것입니다.**
그 숫자가 세상에 나온 날은 **2021년 3월**입니다.

```
사업연도 종료   2020-12-31   ← 여기 붙이면 look-ahead
사업보고서 제출  2021-03-20   ← 실제로 알 수 있게 된 날. 여기 붙여야 한다
```

석 달치 미래를 학습에 넣고도 **예외는 나지 않습니다.** 성능만 좋아집니다.
[F-09](../../요구사항/version1.0/요구사항.md)가 `walk_forward` 에서 막은 누수와
**같은 종류의 오류를, 한 계층 아래에서** 저지르는 것입니다.

| 자료 | 잘못 붙이기 쉬운 날짜 | 붙여야 하는 날짜 |
|---|---|---|
| 재무제표 | 사업연도 종료일 | **공시 제출일**(`rcept_dt`) |
| 정기보고서 | 보고서 대상 기간 | **접수일** |
| 뉴스 | 사건 발생일 | **기사 발행 시각** |
| 지수·시세 | — | 장 마감 후 확정. 당일 15:30 이전에는 알 수 없다 |
| 종목토론방 | — | 게시 시각 |

**그래서 이 파트의 모든 저장 스키마는 `발생 시각`과 `알 수 있게 된 시각`을 따로 둡니다.**

### 2.4 두 번째 문제 — 크롤링은 '되는가'가 아니라 '해도 되는가'

기술적으로 긁을 수 있는 것과 긁어도 되는 것은 다릅니다. 그리고 이 판단을
**나중에** 하면 이미 만든 것을 버려야 합니다.

우리 대상의 실제 `robots.txt` 를 직접 받아 확인했습니다
(→ [시장조사 §2](시장조사.md)):

```
finance.naver.com/robots.txt
    Allow:    /item/board.naver?code=*          ← 종목토론방 첫 페이지는 허용
    Disallow: /item/board.naver?code=*&page=*   ← 페이지 넘기기는 금지
```

**과거를 소급해 긁는 것은 막혀 있고, 매일 앞으로 쌓는 것은 열려 있습니다.**
이 한 줄이 커뮤니티 데이터 설계를 통째로 정합니다 — 우리는 백필하지 않고 **누적**합니다.

### 3.1 네 덩어리

| # | 덩어리 | 무엇 |
|---|---|---|
| ① | **수집기** | 공시 · 정기보고서 · 뉴스 · 커뮤니티 · 동영상 · 시세 · 통계 7종 |
| ② | **적재·정제 계층** | 원본 보존 → 정규화 → 품질 게이트. 수집 로그와 워터마크 |
| ③ | **공급 API** | 뒤 순번 팀원이 함수 하나로 꺼내 쓰는 정문 |
| ④ | **화면** | 수집 현황 + 코스피 대시보드. 버튼으로 즉시 수집 |

### 3.2 두 가지 수집 주기

| 주기 | 무엇 | 왜 |
|---|---|---|
| **하루 1회 배치** | 전체 대상 증분 수집 | 장 마감 후 확정된 자료를 받는다 |
| **버튼 즉시 수집** | 사용자가 고른 대상만 | 시연 때 "지금 받아 보겠습니다"가 되어야 한다 |

⚠️ **버튼이 배치를 대체하지 않습니다.** 버튼은 *증분 한 조각*이고, 빠진 구간을 메우는
책임은 배치와 워터마크에 있습니다. 버튼만 있으면 **아무도 안 누른 날이 구멍**으로 남습니다.

## 4. 성공 기준 — 전부 검증 가능해야 합니다

> 팀 전체 문서와 같은 규칙입니다. *"잘 동작한다"* 는 기준이 아닙니다.

### 4.1 임계가 있는 기준 (합격/불합격)

| # | 기준 | 측정 방법 |
|---|---|---|
| **1. 공백을 말할 수 있다** | 모든 수집 대상에 대해 *"어느 날짜가 비었나"* 가 **전부 열거**된다. 하나도 못 세면 실패 | `python scripts/check_data.py` → `reports/data_quality.json`. 미검사 항목이 있으면 `exit 1` |
| **2. Point-in-Time 위반 0건** | 공시·보고서 계열 테이블에 `알 수 있게 된 시각`이 **비어 있는 행이 0** | 스키마 제약 + 테스트. 사업연도만 있고 접수일이 없는 행은 적재 거부 |
| **3. 재현된다** | 같은 구간을 다른 날 두 번 떠도 **스냅샷 해시가 같다** | [F-02](../../요구사항/version1.0/요구사항.md) 이미 구현 · `python scripts/make_snapshot.py --verify` |
| **4. 약관을 지킨다** | 크롤링 대상별 `robots.txt` 허용 여부를 **코드가 실행 시점에 확인**하고, 불허 경로는 요청 자체를 안 한다 | 차단 테스트. 금지 경로 요청 시 예외 |
| **5. 팀원이 30분 안에 쓴다** | 문서를 처음 본 팀원이 **함수 하나**로 원하는 구간을 받아 첫 피처를 만든다 | 킥오프에서 팀원 1명에게 실제로 시켜 보고 시간을 잰다 |

### 4.2 임계 없이 실측치만 보고하는 칸

- 대상별 **수집 소요 시간**과 호출 수 (일 한도 대비 몇 %인가)
- 뉴스·커뮤니티의 **일별 수집량** 분포
- 정제 단계에서 **버려진 행의 비율과 사유**

> **왜 여기에 임계를 안 거나.** 수집량에 합격선을 걸면 *"많이 긁어야 통과하는"*
> 역인센티브가 생깁니다. 우리가 원하는 것은 **많은 자료가 아니라 설명 가능한 자료**입니다.

## 5. 무엇을 하지 않는가 — 범위 밖

| 안 하는 것 | 왜 |
|---|---|
| **실서버 운영 · 클라우드 배포** | 팀 합의(2026-08-26). 1차는 로컬로 마무리. Supabase · AWS · Vercel 미사용 |
| **외부 DB(Postgres 등) 상시 운영** | 파일(SQLite · parquet) 직접 읽기로 충분하다. `krx_pg.py` 는 있지만 1차에서 안 켠다 |
| **실시간 틱·호가 수집** | 일 단위 지평(5거래일)에 틱은 과잉이다 |
| **기사 본문 전문 저장·재배포** | 저작권. 제목·요약·링크·메타데이터까지만 |
| **로그인이 필요한 페이지 수집** | 약관 위반 소지. 공개 페이지와 공식 API 만 |
| **`robots.txt` 가 막은 경로** | 기술적으로 가능해도 하지 않는다 |
| **감성분석 모델 학습** | 마이닝은 **집계·키워드·빈도**까지. 모델은 뒤 순번 팀원 몫 |

> ⚠️ **"안 하는 이유를 적는 것"이 범위를 선명하게 만듭니다.** 위 7줄이 없으면
> 2주 동안 범위가 계속 늘어납니다.

## 6. 이 파트의 약점 — 심사자가 찌를 곳

| 찌를 곳 | 우리 답 |
|---|---|
| **"수집은 그냥 API 호출 아닌가"** | 호출은 쉽습니다. 어려운 건 **언제 알 수 있었는지**를 지키는 것입니다. §2.3의 point-in-time 이 이 파트의 실제 난이도입니다 |
| **"크롤링이 합법인가"** | 대상별 `robots.txt` 를 **직접 받아 확인**했고(→[시장조사 §2](시장조사.md)), 허용 범위 안에서만 설계했습니다. 코드가 실행 시점에도 확인합니다 |
| **"자료가 예측에 도움이 되긴 하나"** | **이 파트는 그것을 주장하지 않습니다.** 도움이 되는지 판정하는 것은 검증 엔진의 몫이고, 실제로 팀원 제안(F-30)을 우리 데이터로 재서 방향 축을 기각한 사례가 있습니다 |
| **"뉴스·커뮤니티는 노이즈 아닌가"** | 그럴 수 있습니다. 그래서 **수집과 판정을 분리**했습니다. 우리는 잴 수 있게 만들고, 쓸모없다고 나오면 그 결과를 그대로 적습니다 |
| **"대시보드는 겉치레 아닌가"** | 팀 합의도 내부 로직 우선입니다. 그래서 화면의 1순위는 **수집 현황과 공백을 드러내는 것**이고, 코스피 화면은 그다음입니다 |
