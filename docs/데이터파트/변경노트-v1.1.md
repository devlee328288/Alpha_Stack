## 0. 왜 v1.1 이 필요한가

v1.0 을 쓴 뒤 외부 사양을 실측했더니 **문서가 사실과 다른 곳이 나왔습니다.** 그중 하나는

이상치를 버리지 않고 열거하는 것과 같은 이유로, **틀린 것을 조용히 고치지 않고 무엇이
어떻게 틀렸는지 남깁니다.** v1.0 은 지우지 않습니다.

## 1. 🔴 D-22(종목토론방) 삭제 — Must → Won't

### 무엇이 틀렸나

v1.0 [시장조사](version1.0/시장조사.md)와 [요구사항](version1.0/요구사항.md)이 이렇게 적었습니다:

> `finance.naver.com`: `/item/board.naver?code=*` 는 Allow, `&page=*` 는 Disallow
> → 커뮤니티는 백필 금지, **매일 1페이지 누적만**

**1페이지도 안 됩니다.** `robots.txt` 를 직접 받아 확인한 전문입니다
(2026-08-26 KST · HTTP 200 · `text/plain; charset=euc-kr` · 295 bytes):

```
User-agent: *
Disallow: /
User-agent: yeti
Disallow: /
Allow: /sise/
Allow: /research/
Allow: /marketindex/
Allow: /fund/
Allow: /template/head_js.naver
Allow: /world/
Allow: /item/board.naver?code=*
Disallow: /item/board.naver?code=*&page=*
Disallow : /fund/news/
Disallow : /marketindex/news/
```

`?code=*` 를 허용하는 규칙군은 **전부 `User-agent: yeti` 그룹 소속**입니다. yeti 는 네이버
자체 크롤러입니다. 우리 같은 제3자 봇이 매칭되는 것은 `User-agent: *` 그룹이고, 그
내용은 **`Disallow: /` 한 줄** — 사이트 전면 불허입니다.

[RFC 9309 §2.2.1](https://www.rfc-editor.org/rfc/rfc9309.txt) 상 크롤러는 **자신에게
매칭되는 그룹 하나만** 따릅니다. yeti 의 Allow 는 우리에게 적용되지 않습니다.

> 📌 **그룹이 갈리는 근거는 빈 줄이 아닙니다.** 위 원문에는 `Disallow: /` 와
> `User-agent: yeti` 사이에 빈 줄이 없습니다. RFC 9309 은 *"rule 라인이 나온 뒤의
> user-agent 라인이 새 그룹을 연다"* 로 정의합니다. 빈 줄에 근거를 두면 다른 사이트의
> `robots.txt` 를 읽을 때 잘못 일반화합니다.

### 조치

| 항목 | v1.0 | v1.1 |
|---|---|---|
| **D-22** 커뮤니티 수집기 ② 종목토론방 | Must | **Won't** |
| 수집 범위 | 4종 (시세·공시·뉴스/커뮤니티·동영상) | **3종** — 커뮤니티는 카페글(D-21)만 |
| D-51 종목토론방 글 수 집계 | Should | **Won't** (원자료가 없다) |

**UA 를 `yeti` 로 위장하는 안은 선택지에 올리지 않습니다.** 사칭입니다.

> 💡 **이것은 손실이 아니라 산출물입니다.** 수집을 안 한 것보다 **안 하기로 정한 근거가
> 문서에 남는 것**이 낫습니다. 심사자가 *"왜 커뮤니티가 없나"* 물으면 답이 있습니다.

## 3. 수치·필드 정정

### 3.1 네이버 검색 API

| v1.0 | 실제 | 근거 |
|---|---|---|
| 쿼터 초과 = `errorCode 010` | ❌ **그런 코드 없음.** 공식 코드는 `SE01`~`SE06`·`SE99` 7종뿐. 쿼터 초과는 **HTTP 429** | 뉴스 검색 공식 오류 코드표 |
| `start+display-1 ≤ 1000` | ⚠️ **공식 근거 없음.** 명세는 `display 1~100`·`start 1~1000` 두 독립 범위뿐 | developers.naver.com · API HUB 양쪽 문서에 해당 부등식 없음 |
| 25,000콜/일 (전 코퍼스 합산) | ✅ 맞음. 단 **앱(클라이언트 아이디)별** | 공식 |

- `start+display-1 ≤ 1000` 은 **삭제하지 말고 "안전측 가정"으로 강등**합니다. 지켜서
  손해가 없고 어기면 `SE03` 위험이 있습니다. **D-04 스모크 테스트 1번**으로
  `start=1000&display=100` 을 한 번 쏴서 200 인지 400/SE03 인지 기록하면 확정됩니다.
- **재시도 분기는 HTTP 상태 429 로 하고 본문 코드는 로깅만** 합니다 — 개발자센터와
  HUB 의 본문 형식이 다르기 때문입니다(HUB 는 `{"error":{"errorCode":"400",...}}` 중첩).
- ⚠️ **쿼터 리셋이 자정 정각이 아니라 "0시~1시" 구간**입니다(공식 FAQ).
  → 배치는 **01:10 KST 이후**로 겁니다.
- ⚠️ **카페글 응답에는 `pubDate` 가 없습니다** (필드: `title`·`link`·`description`·
  `cafename`·`cafeurl`). 뉴스와 같은 시간축 정렬·일자 파티셔닝이 **불가능**합니다.
  `sort=date` 정렬은 되지만 날짜 값 자체가 안 옵니다. → D-21 스키마를 뉴스와 따로 잡습니다.
- 뉴스 `pubDate` 형식은 RFC 1123 (`"Thu, 11 Jun 2026 18:34:00 +0900"`).
  **영문 요일·월 약어라 로케일 의존 파싱에 주의**합니다.

### 3.2 YouTube Data API v3

v1.0 의 두 수치(`search.list` 100콜/일 · 그 외 10,000유닛/일)는 **맞습니다.** 다만
**의미가 달라졌고 버킷이 셋**입니다.

| 버킷 | 한도 | 우리 용도 |
|---|---|---|
| `search.list` 자체 버킷 | **100콜/일** (콜당 1유닛) | **미사용** (D-23 수용 기준에 grep 검사) |
| `videos.batchGetStats` 자체 버킷 | 10,000유닛/일 | 조회수 수집 주경로 |
| 그 외 전 엔드포인트 합산 | 10,000유닛/일 | `channels.list`·`playlistItems.list` |

> 개편 전에는 `search.list` 가 **콜당 100유닛**으로 공용 버킷을 깎았습니다(그래서 100콜이
> 한계였습니다). 지금은 **콜당 1유닛 + 자체 버킷**이라, 100콜을 다 써도 공용 10,000 은
> 그대로입니다. v1.0 이 수치만 적고 이 구조를 안 적었습니다.

**실측으로 잡힌 함정 3개**

1. **`playlistItems.list` 에 조회수가 없습니다.** `part` 는 `snippet`·`contentDetails`·
   `id`·`status` 4종뿐이고 `statistics` 가 없습니다. → `videos.list` 또는
   `videos.batchGetStats` **추가 호출이 필수**입니다.
2. **`playlistItems.snippet.publishedAt` 은 "재생목록에 추가된 시각"** 입니다.
   영상 게시시각은 **`contentDetails.videoPublishedAt`** 입니다. 이걸 틀리면
   `event_at` 이 통째로 어긋납니다.
3. **`videos.batchGetStats` 의 `snippet` 에는 `title` 이 없습니다** (`publishTime` 뿐).
   제목이 필요하면 `playlistItems` 쪽에서 가져와야 합니다.
   `contentDetails` 도 `duration` 하나뿐이고, `summary`(부분 실패 식별용) 필드는
   **실재하지 않습니다** — Google discovery 문서(revision 20260825) 원문 대조.
   → 부분 실패는 **요청한 id 집합과 반환된 items 를 차집합**해서 찾아야 합니다.

**수집 경로 확정** (`search.list` 미사용):
`channels.list(part=contentDetails)` → `contentDetails.relatedPlaylists.uploads`
→ `playlistItems.list(playlistId=UU…, part=contentDetails, maxResults=50)`
→ `videos.batchGetStats(id=…, part=statistics)` (id 최대 50)

채널 50개 × 최근 50영상 ≈ **101유닛/일** — 한도의 1% 수준입니다.
쿼터 리셋은 **태평양시(PT) 자정** = KST 오후 4~5시(서머타임에 따라 이동)입니다.

### 3.3 KRX · DART 한도 — **검증되지 않았습니다**

| 값 | 상태 |
|---|---|
| KRX 10,000콜/일 | ⚠️ **확인도 반증도 안 됨.** 이번 조사에서 KRX 한도를 조사한 주제가 없습니다. 검증된 값처럼 다루면 안 됩니다 |
| DART 20,000콜/일 | ⚠️ **근거 약함.** 공식 문구가 *"일반적으로는 20,000건 이상"* 이라며 스스로 *"요청 제한이 다르게 설정된 경우"* 단서를 답니다. 2차출처 두 곳은 10,000 이라고 적어 상충합니다 |

→ 두 값 모두 **"기본값(키별 상이 가능) · 실제 값은 이용현황 페이지에서 확인"** 으로
표기를 낮춥니다. D-04 예산 상한은 보수적으로 잡습니다.

⚠️ **DART 는 한도 초과를 HTTP 오류가 아니라 `HTTP 200` + 본문 `status="020"` 으로 줍니다.**
(잘못된 키도 `200` + `status="010"` 으로 옴을 실측.) HTTP 예외만 잡는 코드는 **한도 초과를
놓칩니다.**

## 4. D-12(DART PIT) — 수용 기준 적용 시점 변경

### 문제

v1.0 D-12: *"접수일이 없는 응답은 **적재 거부**"*.
그런데 **`fnlttSinglAcntAll`(재무제표) 응답에 `rcept_dt` 가 없습니다.** `rcept_no` 만
있습니다 — 공식 필드 목록으로 확인했고, 삼성전자 FY2023 실호출 176행의 키 합집합에
`dt`·`date` 포함 키가 **0개**임을 실측했습니다.

문자 그대로 적용하면 **재무제표가 전량 거부**되어 재무 피처를 쓰려는 뒤 순번 팀원이 멈춥니다.

### 조치

**거부 게이트를 원시 응답이 아니라 "접수일 보강 이후"로 옮깁니다.**

보강 경로는 **`list.json` 조인**입니다:
`list.json(corp_code, pblntf_ty="A", bgn_de="20150101", end_de=오늘, page_count=100)`
→ `rcept_no → rcept_dt` 맵 → 재무제표 행의 `rcept_no` 로 조인.

- 실측 검증: 삼성전자 `rcept_no=20240312000736` → `list.json` 에서 `total_count=1`,
  `rcept_dt='20240312'` **1:1 매칭 성공**
- 비용: 회사당 1콜(대형주 47~56건이 1페이지), 2,700사 ≈ **2,700콜 = 한도의 13.5%**
- 접수일은 불변이라 **영구 캐시** 가능 → 재수집 비용 0
- ⚠️ 조회 구간을 **넓게** 잡습니다. 에너토크 FY2021 의 실제 문서는 **2024-05-28** 접수라
  좁은 창으로는 안 잡힙니다. `total_page > 1` 이면 페이지를 순회합니다.

### 🚫 `rcept_no[:8]` 슬라이싱은 채택하지 않습니다

앞 8자리가 접수일자라는 것은 **공식 문서에 없는 관행**입니다. 정기공시만 **4,800건을
실측 검증**한 결과 **3건(0.062%)이 깨졌고, 방향이 나쁩니다**:

| `rcept_no` | 앞 8자리 | 실제 `rcept_dt` | 문제 |
|---|---|---|---|
| `20180330004096` (엠피씨플러스) | 2018-03-30 | **2018-04-02** | 접수일을 **3일 앞당겨** 읽음 → **lookahead** |
| `20180330004046` (씨제이이앤엠) | 2018-03-30 | **2018-04-02** | 〃 |
| `20250401000004` (DH오토넥스) | 2025-04-01 | 2025-03-31 | 하루 늦음(보수적 방향) |

앞 두 건은 **아직 공개되지 않은 정보를 3일 먼저 아는 것**입니다 — D-12 가 존재하는 이유
그 자체입니다. 전체 공시로 넓히면 오차율이 **1.2%** 로 올라갑니다.

→ 슬라이싱은 **조인 결과를 교차검증하는 경보용으로만** 씁니다(불일치 시 로그).

### 부수 결정

- `known_at` 은 `rcept_dt`(YYYYMMDD, KST 날짜)로 둡니다. **시각 정보가 없으므로 당일
  장중 사용은 근거가 없습니다** → **`known_at` 다음 거래일부터 유효**로 잡습니다.
- 정정공시 식별 수단 3종(전부 공식): `report_nm` 접두어(`[기재정정]` 등) ·
  `rm` 에 `'정'` 포함(= 이 문서는 뒤에 정정되어 대체됨) · `last_reprt_at=Y`(최종본만).
- ⚠️ **한계로 명시**: `fnlttSinglAcntAll` 은 vintage 를 고를 수 없습니다(사업연도+보고서코드만
  받음). **원본 시점 숫자가 필요하면 이 API 로는 불가능**하고 XBRL 원문 파싱이 필요합니다.
  → 1차 범위 밖으로 두고 문서에 적습니다.
- ⚠️ **커버리지 손실을 지표로 남깁니다** — 정정본만 반환되는 종목(에너토크 FY2021 →
  `known_at` 2024-05-28)은 과거 구간 백테스트에서 통째로 빠집니다. 버리지 말고 **셉니다.**

## 5. 채택 결정 (D-03 · D-02 · D-43)

### 5.1 `robots.txt` 파서 = `protego`

**표준 라이브러리 `urllib.robotparser` 는 탈락입니다 — 판단이 아니라 실측입니다.**

`RuleLine.applies_to` 가 `filename.startswith(self.path)` 접두사 매칭이 전부이고,
규칙 경로에 `quote()` 를 적용해 `*` 가 `%2A` 리터럴이 됩니다. 결과적으로
**명시적 `Disallow` 인 URL 에 `can_fetch()` 가 `True` 를 반환**합니다(fail-open).

> 차단 가드가 반대 방향으로 틀리면 **가드가 없는 것보다 나쁩니다.** 안전하다는 착각을 줍니다.

| 후보 | 판정 |
|---|---|
| `urllib.robotparser` | ❌ fail-open. 와일드카드·`$` 미지원 |
| `protego` | ✅ 전 케이스 정답. `$`·최장일치·쿼리스트링·비표준 라인(`Disallow : `)까지 |
| `reppy` | ❌ PyPI 최신 2019년(0.4.14), 지원 파이썬 ~3.7 |
| `robotexclusionrulesparser` | ❌ 같은 케이스 fail-open. 우선순위가 순서 의존적. 최종 릴리스 2016년 |

**`protego==0.6.2` 로 고정합니다.** `<=0.6.1` 에 ReDoS 취약점
[GHSA-wjmf-p669-5m5p / CVE-2026-55520](https://github.com/scrapy/protego/security/advisories/GHSA-wjmf-p669-5m5p)
(severity **High**)이 있습니다. 외부가 주는 파일을 파싱하는 D-03 은 정면 노출입니다.

> 📌 GHSA API 가 `cvss` 를 `null` 로 반환해 **구체 점수는 확인되지 않았습니다.**
> `severity=high` 까지만 확정입니다.

**직접 구현해야 하는 것** — `protego` 는 파서 전용이라 fetch 를 안 합니다:
- **HTTP 상태 분기를 RFC 9309 대로**: `4xx`(404 포함) → **전면 허용**(MAY access) /
  `5xx`·네트워크 오류 → **전면 차단**(MUST assume complete disallow).
  ⚠️ 흔한 실수가 5xx 를 허용으로 처리하는 것인데 RFC 는 **MUST 로 금지**합니다.
- 24시간 캐시 (RFC 문구와 일치). 단 *"unless unreachable"* 단서를 살려
  5xx 로 갱신 실패 시 **직전 캐시를 계속 씁니다.**
- ⚠️ 응답이 `charset=euc-kr` 입니다. **UTF-8 로 가정하지 않습니다.**

### 5.2 SQLite 마이그레이션 = `PRAGMA user_version` + 자작 30줄

`alembic`·`yoyo`·`sqlite-utils` **전부 기각.** alembic 이 SQLite 에 주는 것은
batch(move-and-copy) 모드인데, 실측상 그 급의 전면 재작성은 19초짜리이고 정작 D-02 가
필요한 `ADD COLUMN` 은 **0.16ms 로 공짜**입니다. 필요 없는 비싼 경로를 위한 의존성입니다.

**900만 행 실측** (SQLite 3.53.2 · 727MB · WAL):

| 연산 | 시간 |
|---|---|
| `ADD COLUMN` (DEFAULT 없음) | **0.72ms** |
| `ADD COLUMN NOT NULL DEFAULT 0` | **0.16ms** |
| `RENAME COLUMN` | 1.00ms |
| `ADD COLUMN` + **CHECK 제약** | **5,088ms** (약 3만 배) |
| `DROP COLUMN` | **19,163ms** (900만 행 전체 UPDATE 와 동급) |

**규약 4개 — 타협 불가**
1. **`BEGIN IMMEDIATE` 를 명시한다.** 파이썬 `sqlite3` 기본 모드는 DDL 을 암묵
   트랜잭션에 넣지 않는다. 빼면 마이그레이션이 원자적이지 않다.
2. **`executescript()` 를 쓰지 않는다.** 열린 트랜잭션을 먼저 커밋해 롤백이 불가능해진다
   (실측: ROLLBACK 이 *"no transaction is active"* 로 실패, 반쪽 스키마가 남음).
3. **`PRAGMA user_version=N` 을 스키마 변경과 같은 트랜잭션에 넣는다.**
   *"헤더라서 트랜잭션 밖"* 이라는 통설은 실측으로 반증됐다(ROLLBACK 시 복귀).
4. **`PRAGMA user_version` 만 쓴다.** `schema_version` 은 SQLite 내부용이고 공식 문서가
   DB 손상을 경고한다.

**스키마 규칙**: 새 컬럼에 **CHECK 제약 금지**(3만 배) · **`DROP COLUMN` 금지**(19초) ·
`DEFAULT CURRENT_TIMESTAMP`·`UNIQUE`·`PRIMARY KEY` 는 `ADD COLUMN` 에서 거부됨(상수만) ·
반대로 **`NOT NULL DEFAULT <상수>` 는 마음껏** 써도 된다(오히려 더 빨랐다).
