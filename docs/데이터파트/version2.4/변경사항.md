## 1. 액면분할이 조정되지 않아 −98% 가 학습에 들어가고 있었다

장환님이 피처를 검증하다 발견해 전달해 주신 건이다. 전수로 확인했다.

```
삼성전자 2018-05-04 (액면분할 50:1)
  20180503  종가 2,650,000
  20180504  종가    51,900     close 로 계산 → -98.04%   KRX 등락률 → -2.08%
```

이 값이 `full/daily_price_dev.parquet` 에 그대로 있었고, `close` 파생 피처 19개와
라벨까지 전파됐다.

### 무엇을 했나

`common/corporate_actions.py` 에 **가격을 이어 붙이는 함수 4개**를 넣었다.
탐지(`is_basis_adjusted`)는 원래 있었고 **조정이 없었다.**

| 함수 | 하는 일 |
|---|---|
| `adjustment_factor(prev_row, row)` | 그 날의 조정 배율 (`Fraction`) |
| `factor_series(rows)` | 행마다 배율 |
| `span_factor(factors, entry, exit)` | 구간 안 조정의 누적 |
| `back_adjusted_closes(rows)` | 후방조정 종가 계열 |

자세한 것은 [`수정주가_기능명세.md`](수정주가_기능명세.md).

### 🔴 가격이 끊기는 이유가 둘이라 방식도 둘이다

| 유형 | 재는 법 | 근거 |
|---|---|---|
| 평상일 | `기준가 = close − change` | `close`·`change` 가 정수라 계수가 **정확한 유리수** |
| **재개일** | **상장주식수 배율** | 재개 단일가 기준가를 믿으면 과거가 **120배** 부푼다 |

기준가 조정 5,246건 중 **2,057건(39.2%)이 거래정지 재개**였고 자본변동이 아니었다.
그렇다고 재개일을 버릴 수도 없다 — **정지일을 빼면 액면분할·병합이 0건 남는다.**
KRX 가 주권 교체 때문에 반드시 정지시키기 때문이다.

### 효과 (실측)

```
ret_1 ≤ −50% 인 행 : 1,355 → 745   (610행 제거, 45.0%)
삼성전자·삼성전자우 20180504 가 최악 목록에서 사라졌다
조정 수익률 vs KRX 등락률 : 8,933,630행 중 0.01%p 초과 0행 (최대 0.005%p)
```

남은 745행은 **장기 거래정지 뒤 재개**로, 수정주가가 아니라 표본 선택으로 다룰 것들이다.

### ⚠️ 아직 적용하지 않았다

수익률을 계산하는 4곳(`evaluation/horizon.py` 3곳 · `export_team_dataset.py` 1곳)은
**그대로 두었다.** 파트 경계를 넘으므로 팀에 묻는다. 이번에는 **함수를 만들고 검증까지만** 했다.

→ [이슈 #51](https://github.com/devlee328288/Alpha_Stack/issues/51)

## 2. DART 규격이 우리 자신의 출력을 100% 거부하고 있었다

다음 세션에 350종 × 5개년을 받기 **직전**에 막았다.

### 진단이 절반만 맞았다

처음 진단은 "이름이 어긋났다" 였다 — `_normalize_account` 가 `thstrm_amount` 를
`this_amount` 로 바꿔 내보내니 금액 칸이 `extras` 로 밀린다는 것.

이름을 원본으로 되돌리고 삼성전자 2023 연결 176행으로 반입을 태웠다.
**176행 전부가 그대로 격리됐다.**

나머지 절반은 이것이었다.

```
DART 원본 17칸 중 우리가 버리던 것 : bsns_year · corp_code · reprt_code · rcept_no
                                     (실측: 176/176 행 전부에 실려 온다)
```

`bsns_year`·`reprt_code`·`fs_div` 가 `required` 라 전량 걸린 것이다.

### 무엇을 했나

| 파일 | 변경 |
|---|---|
| `ingest/clients/dart_data.py` | `_normalize_account` 가 **원본 이름**을 쓰고 식별 칸 4개를 되살린다 |
| 〃 | `fs_div`·`rcept_dt` 를 키워드로 받아 채운다 |
| 〃 | `_receipt_date()` 신설 — `list.json` 으로 접수일을 되찾는다 (영구 캐시) |
| 〃 | `_pick_accounts` 의 키 참조 5줄 |
| `ingest/inbox/schemas/financial.json` | `fileMeta.note` 를 **사실로** 고쳤다 |

### 결과

```
전 : 합격   0 / 격리 176
후 : 합격 176 / 격리   0        rcept_dt = 20240312 (실호출로 되찾음)
```

### 규격 주석이 사실과 달랐다

원래 이렇게 쓰여 있었다.

> "DART 응답은 ... 이 값들이 응답 최상위에 한 번만 붙고 **계정 줄에는 안 실린다**"

**틀린 말이었다.** 우리 코드가 버려서 없어진 것을 DART 탓으로 적어 둔 것이다.
그 위에 `fileMeta` 라는 보정 장치가 통째로 서 있었다. 주석을 실측대로 고쳤고,
아직 구현되지 않은 사이드카(`<파일명>.meta.json`) 읽기도 **"아직 없다"고 명시**했다.

→ [이슈 #43](https://github.com/devlee328288/Alpha_Stack/issues/43)

## 3. 🔴 덤 — 가장 소리 높여 지키려던 규칙이 한 번도 안 돌았다

#43 을 파다 나온 것이다. 반입 엔진은 규칙이 **언급하는 칸이 하나라도 없으면**
규칙 전체를 건너뛴다. `X and Y` 에는 맞지만 `X or Y` 에는 **정반대로** 작동한다.

> "둘 중 하나만 있으면 된다" → **"둘 다 있어야 잰다"**

걸린 것 중에 `has_time_anchor` 가 있었다. 규격이 *"이 프로젝트에서 가장 조용한 오류"* 를
막으려고 둔 **error** 규칙인데, **한 번도 돈 적이 없었다.**

`rcept_dt` 를 채우자 그때부터 돌기 시작했다(위반 0).
다만 `corp_or_stock_code` 는 아직 스킵된다 — `stock_code` 칸이 없어서다.

**이번 PR 에서는 고치지 않았다.** 지금 통과하던 파일을 격리시킬 수 있어,
어느 규격의 어느 규칙이 새로 걸리는지 먼저 세어 봐야 한다.

→ [이슈 #52](https://github.com/devlee328288/Alpha_Stack/issues/52)

## 5. 테스트가 수집할 때마다 깨지지 않게 했다

`test_warn_규칙이_아는_사실을_그대로_센다` 가 깨졌다. `zero_ohlc` 기대값
283,468 → 283,983. `git stash` 로 되돌려도 똑같이 깨져 **내 변경과 무관함을 확인**했다.

원인은 그날 아침 수집이었다. 증가분 515건이 새로 받은 4일의 몫(134·131·128·122)과
**정확히 일치**했다. 규칙은 멀쩡하고 기대값만 낡은 것이다.

그래서 값을 갱신하는 대신 **측정 시점을 고정**했다.

```python
MEASURED_THROUGH = "20260825"
```

값만 바꿨으면 다음 수집 때 또 깨진다. 규칙이 멀쩡한데 빨간불이 반복되면
팀은 규칙을 고치지 않고 **테스트를 끈다.**
