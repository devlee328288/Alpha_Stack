## 0. 이 파트가 끝나면 팀원이 할 수 있는 것

| 누가 | 무엇을 | 어떻게 |
|---|---|---|
| 오준영 (모델) | 학습에 쓸 지수 시세를 꺼낸다 | `supply.index_series(as_of=...)` 한 줄 |
| 강민석 (백테스팅) | 봉인 구간을 실수로 열지 못한다 | 요청하면 `SealedRangeError` 가 난다 |
| 신장환 (피처) | 지표 함수에 넣을 표의 모양을 안다 | 계약 테스트가 컬럼·정렬·dtype 을 고정한다 |
| 팀 전체 | 오늘 자료가 성한지 한눈에 본다 | 수집 현황 화면 |
| 팀 전체 | 발표 때 "이 숫자 어디서 났나"에 답한다 | 수집 대장 + 스냅샷 해시 |

전체 모듈 지도와 줄 수는 [부록 B](#부록-b-모듈-지도)에 있습니다. 본문에서는 뺐습니다 —
읽는 사람이 알고 싶은 것은 파일 크기가 아니라 할 수 있는 일이기 때문입니다.

## 1. 하루를 따라가 보기

기능 목록을 읽기 전에, 이것이 실제로 어떻게 쓰이는지 먼저 봅니다.

### 아침 9시 — 어제 자료가 잘 들어왔나

화면을 엽니다. 맨 위에 카드 세 장이 있습니다.

```
  ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
  │ 어제 수집        │  │ 설명 안 되는 것  │  │ 오늘 호출        │
  │  2 / 2 출처     │  │      0 건       │  │  0 / 10,000     │
  └─────────────────┘  └─────────────────┘  └─────────────────┘
```

셋 다 초록이면 더 볼 것이 없습니다. 닫고 나갑니다.

가운데 카드가 빨간색이면 — **설명되지 않는 이상치**가 생겼다는 뜻입니다.
"이상한 값이 있다"가 아니라 "우리가 아는 이유로 설명이 안 되는 값이 있다"입니다.
정리매매나 신규상장 첫날은 값이 크게 튀지만 이유를 알기 때문에 여기 안 셉니다.

### 아침 9시 5분 — 어제 배치가 실패해 있다

출처 행이 빨간 줄로 떠 있고 오른쪽에 **다시 받기** 버튼이 있습니다.
누르면 그 출처만 다시 받습니다. 셋 중 하나가 나옵니다.

- 받아졌다 → `신규 348행`
- 한도가 없다 → `내일 재개 · 남은 한도 0/10,000`
- 또 실패했다 → 사유와 **다음에 할 일**

세 번째가 중요합니다. "실패했습니다"만 적힌 화면은 아무 도움이 안 됩니다.

### 오전 10시 — 오준영이 모델을 돌린다

```python
from supply import index_series

df = index_series(as_of="2026-08-31")
```

`as_of` 를 빼면 **에러가 납니다.** 기본값이 없기 때문입니다.
빼먹고 돌아가면 미래를 본 채로 학습이 되고, 그건 에러가 안 나서 더 위험합니다.

### 오후 3시 40분 — 장이 끝났다

배치가 자동으로 돕니다. 대장을 읽어 **이미 받은 날짜는 건너뜁니다.**
그래서 두 번 연속 돌려도 두 번째는 신규 0건입니다.

## 3. 기능 명세

칸을 못 채우면 설계가 안 끝난 것입니다. 빈 칸은 `[확인필요]` 로 남겨 둡니다.

### 3.1 D-02 이미 받은 날짜를 다시 받지 않는다

```
상태        구현됨                        담당  이동원
부르는 법    collect_log.should_collect(conn, source, target)
들어가는 것  (출처 이름, 대상)
나오는 것    bool — False 면 이미 답을 들었다
확인 방법    tests/test_collect_log.py
성공 기준    4,097 거래일을 다시 돌려도 KRX 호출 0회
코드        ingest/store/collect_log.py  (2026-08-31 기준 524줄)
```

**안 받은 이유를 다섯으로 가릅니다.** 이것이 이 기능의 핵심입니다.

| 상태 | 뜻 | 다시 시도하나 |
|---|---|---|
| `ok` | 받았다 | 아니오 |
| `empty` | 받아 봤는데 0건이었다 (휴장일) | 아니오 |
| `error` | 시도했는데 실패했다 | 예, 3회까지 |
| `quota_exhausted` | 오늘 한도를 다 썼다 | 예, 내일 |
| `out_of_range` | 출처가 그 기간을 안 준다 | 아니오 |

`empty` 와 `error` 를 안 가르면 휴장일마다 매일 다시 물어보게 됩니다.
`quota_exhausted` 는 재시도 횟수를 먹지 않습니다 — 우리 잘못이 아니기 때문입니다.

포기한 것: `RUNNING` 상태. 프로세스가 죽으면 영원히 남고, 그건 사람 손이 필요해집니다.
"지금 도는 중"은 파일로 냅니다. 파일은 지우면 그만입니다.

### 3.2 D-11 하루 한 번 새것만 받는다

```
상태        구현됨                        담당  이동원
부르는 법    python scripts/fetch_krx.py   (지수는 fetch_index.py — 아직 따로 돈다)
성공 기준    두 번 연속 실행 시 두 번째가 신규 0건
확인 방법    tests/test_krx_store_collect_log.py  (12개)
코드        ingest/store/krx_store.py  (2026-08-31 기준 969줄)
```

시세 수집기가 대장에 기록을 남기지 않던 것을 2026-08-31 에 이었습니다.

고치기 전에는 `krx_store` 가 대장을 쓰지도 읽지도 않아, 다시 돌려도 마지막 성공 시각이
안 바뀌었습니다. 화면이 매일 받고 있는데도 8월 26일이라고 말하게 되어 있었습니다.

쓰기는 옛 `fetch_log` 와 `collect_log` 둘 다, 읽기는 `collect_log` 하나입니다.
900만 행 백필이 `fetch_log` 위에서 돌았기 때문에 그것을 지울 수는 없습니다.

시세는 날짜당 2콜입니다(KOSPI · KOSDAQ). 한 줄이 한 콜에 대응해야 예산과 대장이
어긋나지 않으므로 대상을 `KOSPI/20260826` 형태로 적습니다 — 지수 쪽과 같은 규칙입니다.

⚠️ **옛 대장을 옮긴 4,343줄은 날짜만 들고 있었습니다**(`20260826`). `fetch_log` 에 시장
칸이 없어서입니다. 한 표 안에 두 규칙이 살면 같은 날짜가 두 벌로 갈라지므로,
`krx_store.rebuild_collect_log()` 가 `daily_price` 를 **실제로 세어** 시장별로 다시
깔았습니다. 없는 값을 지어내지 않았고, 시각만 옛 대장에서 그대로 물려받았습니다.

```
다시 깐 결과 (2026-08-31)
  before 4,343 → removed 4,343 → built 8,686 → after 8,686

  KOSPI   대장 3,774,002 · 시세표 3,774,002   일치
  KOSDAQ  대장 5,435,810 · 시세표 5,435,810   일치
  합계    대장 9,209,812 · 시세표 9,209,812   일치
```

같은 이유로 `collect_log.import_legacy()` 에서 `fetch_log` 항목을 뺐습니다. 두면
누군가 다시 부를 때 날짜 전용 줄이 되살아납니다.

### 3.3 D-10 자료가 성한지 검사한다

```
상태        구현됨                        담당  이동원
부르는 법    python scripts/check_data.py
나오는 것    reports/data_quality.json
성공 기준    설명되지 않는 이상치가 있으면 exit 1
소요        1분 48초 (2026-08-31 실측 · 고치기 전 2분 58초)
코드        scripts/check_data.py  (592줄)
```

**게이트는 "이상한 값"이 아니라 "설명되지 않는 값"에 겁니다.** 이 구분이 전부입니다.

2026-08-29 전수 검사에서 극단값 2,080행이 나왔고, 전부 아래 넷으로 설명됐습니다.

| 설명 | 행 수 |
|---|---|
| 정리매매 | 1,923 |
| 거래정지 후 재개 | 468 |
| 자본변동 | 22 |
| 신규상장 첫날 | 155 |
| **설명 안 됨** | **0** |

가격제한폭은 시기마다 다릅니다. 2015-06-15 에 ±15% 에서 ±30% 로 바뀌었고,
2023-06-26 부터 신규상장 첫날은 공모가의 60~400% 입니다.
그래서 **±30% 라는 하나의 문턱을 쓰지 않습니다.**

실제로 재 봤습니다 (9,209,812행 전수, 2026-08-31).

| 단순 `|등락률| > 30` 규칙을 쓰면 | 결과 |
|---|---|
| 잡히는 행 | 1,592건 — **전부 위 네 이유로 설명되는 정상 데이터** |
| 놓치는 행 | 495건 — 2015-06-15 이전, 그때 상한은 ±15% 였다 |

검증을 건너뛰는 구멍이 하나 있었습니다. 2026-08-31 에 경고 한 칸으로 드러냈습니다.

거래정지 표시행은 시·고·저가 0 으로 옵니다. 283,468행이 그렇습니다(2026-08-31 실측).
검사 코드는 이렇게 생겨 있었습니다.

```python
if halted:                    # 시·고·저가 0 → 정지 표시행으로 세고 끝
    tally["zero_ohlc"] += 1
elif ... low <= min(open, close) and max(open, close) <= high ...:
    tally["inversion"] += 1   # 진짜 대소 역전
```

`elif` 라서 **정지 표시행은 대소 검사를 통째로 건너뜁니다.** 대부분은 맞습니다 —
283,343행은 거래량도 0 이라 검사할 값 자체가 없습니다.

문제는 나머지 **125행**입니다. 시·고·저가 0 인데 거래량이 0 보다 큽니다.
125행 전부 거래대금도 0 보다 큽니다(220원 ~ 456,000,000원 · 97종목 ·
2010-02-12~2025-03-21). 가장 큰 것은 `349720` 의 2020-10-07 로 147,946주 ·
288,494,700원이 실제로 거래됐습니다.

즉 **거래가 있었는데 시·고·저가 0 으로 들어온 행**입니다. 정지 표시가 아닙니다.
그런데 정지로 분류돼서 한 번도 검증을 안 받고 있었습니다.

전체의 0.0014% 입니다. 버리지 않고 `halted_but_traded` 경고 한 칸으로 셉니다.
자료 오류로 보지 않는 것은 체결이 실재하기 때문입니다 — 종가 × 거래량이 거래대금과
대체로 맞습니다. 다만 *"정지 중이라 체결이 없다"* 는 전제가 깨지므로 정지행과 갈라
둡니다. 표본에는 종가와 거래량을 함께 남깁니다. 숫자만 있으면 쫓아갈 수 없습니다.

성능도 문제입니다. 전체 2분 58초 중 98.6초가 질의 하나입니다.
그리고 그 질의 모양은 **우리 저장소가 스스로 경고해 둔 것**입니다 —
`krx_store.py` 가 "18초 vs 0.8초"라고 적어 둔 형태를 `check_data.py` 가 쓰고 있습니다.
게이트가 느리면 사람이 안 돌립니다.

### 3.4 D-00 `as_of` 없이는 과거를 못 본다

```
상태        구현됨                        담당  이동원
부르는 법    supply.index_series(as_of="20260831")
              supply.price_series(codes, start, end, as_of=...)
              supply.training_frame(..., holdout_start=...)
나오는 것    pandas DataFrame — 빈 결과에도 컬럼이 남는다
확인 방법    tests/test_supply_boundary.py · tests/test_supply_price.py
코드        supply/  (591줄, 2026-08-31)
```

**문이 둘입니다.** 손잡이가 아니라 이름으로 갈랐습니다.

| 문 | 언제 쓰나 | 왜 갈랐나 |
|---|---|---|
| `price_series` | 예측할 때 | 그 시점에 알 수 있던 것만 준다 |
| `training_frame` | 학습할 때 | 정리매매 판정은 미래를 보므로 예측 경로에 두면 안 된다 |

시세는 **거래일 T 의 자료를 T+1 0시(KST)부터** 알 수 있었다고 봅니다.
2026-08-26 에 마감 40분 뒤인 16:10 에 요청해 보니 0행이었습니다.
정확한 공표 시각을 재지 않았으므로 하루를 통째로 미룹니다.

⚠️ **문서가 거짓말하는 자리가 있습니다.** `AsOfRequired` 예외가 정의는 돼 있는데
어디서도 던지지 않습니다. 실제로 나는 것은 파이썬 내장 `TypeError` 입니다.
결과는 같지만(빠뜨리면 터진다) 문서 여러 곳이 `AsOfRequired` 가 난다고 적고 있습니다.

## 8. 용어집

| 말 | 뜻 |
|---|---|
| `as_of` | "언제 시점에서 본 자료인가". 이 값보다 뒤의 자료는 안 준다 |
| `known_at` | 그 자료를 **알 수 있었던 시각**. 거래일 T 의 시세는 T+1 0시 |
| 워터마크 | 어디까지 받았는지 표시. 다음에 그 뒤부터 받는다 |
| 정리매매 | 상장폐지 직전 거래 기간. 가격이 크게 튄다 |
| 기준가 조정 | 액면분할·증자로 기준가가 바뀌는 일. 과거 주가는 안 고쳐진다 |
| zero-OHLC | 시·고·저가 **0** 인 행. 거래정지 표시다. 종가는 전일 종가로 남는다 |
| 봉인 구간 | 최종 검증 전까지 열지 않기로 한 기간 |
| 룩어헤드 | 그 시점에 몰랐을 정보가 새어 든 것. 에러가 안 나서 위험하다 |

## 부록 A. 왜 이렇게 만들었나

### 원문을 남기는 이유

정규화 규칙이 틀린 것을 나중에 발견했을 때, 원문이 없으면 **다시 받아야** 합니다.
받는 데 한도가 걸리고, 출처가 과거를 안 줄 수도 있습니다.
그래서 응답 원문을 그대로 남기고, 재정규화는 원문에서 다시 만듭니다.

한 번 틀렸던 적이 있습니다. 재정규화가 **수집 시각을 현재로 덮어썼습니다.**
그러면 대장이 "방금 받았다"고 말하게 되고, 실제로는 며칠 전 자료입니다.
지금은 재정규화가 수집 시각을 건드리지 않습니다.

### 게이트를 "설명되지 않는 것"에만 거는 이유

처음에는 이상치를 전부 error 로 걸었습니다. 그랬더니 게이트가 매번 빨간불이었고,
사람이 보다가 지쳐서 결국 안 보게 됐습니다.

이상치의 대부분은 **정상적인 시장 사건**입니다. 정리매매 20,763행,
신규상장 1,716행, 자본변동일 40,967행이 그렇습니다.
이것들을 error 로 걸면 진짜 문제가 그 안에 묻힙니다.

그래서 규칙을 뒤집었습니다 — 아는 이유로 설명되면 **세고 열거만** 하고,
설명이 안 되는 것에만 걸립니다. 지금 그 값은 0 입니다.

| 룩어헤드 — *"1분기 실적을 4월 1일부터 반영하면 안 된다. 실제 공시일 기준"* | 우리가 공시를 3차로 미룬 이유가 이것이다. 접수일 조인 없이 붙이면 이 함정에 그대로 빠진다 |
| 생존편향 — *"상장폐지된 부실기업이 전부 빠져서 결과가 부풀려짐"* | 중도 소멸 종목 **910개** |
| 낮은 신호 대 잡음 비율 | 기준선 52.64% 위 유의 임계가 54.99%(iid) / 57.22%(중첩보정). **신호가 얼마나 얇은지의 숫자** |

수업은 개념을 주고 우리는 크기를 잽니다. 둘을 짝지으면 발표에서 강합니다.

### 수업 지침을 그대로 쓰면 안 되는 곳

| 수업이 가르친 것 | 우리 자료에서는 |
|---|---|
| 결측치를 평균·앞값·뒤값으로 채운다 (02-preprocessing) | 거래정지 구멍을 채우면 **존재하지 않는 체결가**가 생긴다. zero-OHLC 283,468행이 그 자리다 |
| 결측치를 시계열 보간으로 메운다 (09-finance-ml) | 위와 같다. 원인이 다른 결측을 같은 보간으로 메우면 없던 가격을 만든다 |
| 로그 변환을 거래량에 적용한다 | 거래량 0 인 행이 있어 `log(0)` 이 터진다 |
| 열 전체를 한 번에 min-max 정규화한다 | 검증 구간 값이 학습에 흘러든다 |
| 요청 사이에 `time.sleep(1)` · 「헤더 위장」으로 User-Agent 를 바꾼다 (06-data-crawling) | 우리는 **`robots.txt` 를 먼저 본다.** 수업은 `robots.txt`·이용약관·저작권을 다루지 않는다 |

마지막 줄이 중요합니다. 수업 자료에는 크롤링 예절에 대한 내용이 없고,
UA 를 바꾸는 방법이 나옵니다. 우리는 그 반대 방향을 택했습니다 —
종목토론방을 접은 것도 `robots.txt` 때문입니다.

### 수업에 없어서 우리가 채운 것

- **수정주가 · 거래정지 · 정리매매 · 가격제한폭 · zero-OHLC** — 09-finance-ml 에 한 글자도 없습니다.
  한국 시장 고유의 함정이라 우리가 직접 재야 했습니다.
- **`merge_asof`** — 02-preprocessing 다섯 노트북 어디에도 없습니다.
  수업이 가르치는 조인은 정확일치 키뿐이라, 시점정합 조인은 수업 밖 확장입니다.
- **무작위 분할의 위험** — 05-time-series 는 위치 슬라이싱만 쓰고 `train_test_split` 은
  등장하지 않지만, **왜 위험한지 설명하는 문장이 없습니다.**
- **3분류** — 수업은 분류를 "상승/하락" 2분류로 소개합니다. 우리는 중립 밴드를 두어
  3분류입니다. 밴드를 두는 이유가 수업이 말한 "낮은 신호 대 잡음 비율"입니다.
