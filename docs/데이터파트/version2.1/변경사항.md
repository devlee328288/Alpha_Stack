# 데이터 파트 v2.0 → v2.1 변경사항

> 2026-08-31 · [v2.0](../version2.0/요구사항.md) → [v2.1](명세서.md)
> **Minor(+0.1)** 인 이유: 기능 ID 대역(D-00~D-43)과 수용 기준이 그대로입니다.
> 바뀐 것은 **문서의 짜임과 상태 표기**이고, 새로 밝혀진 사실 셋이 붙었습니다.

## 1. 문서를 다시 짰습니다 — 무엇을 만드는지 먼저 보이게

팀장이 문서를 읽고 *"명확하게 무슨 기능을 구현하는지 확인하기 어렵다"* 고 했습니다.
원인을 찾아보니 문장력이 아니라 **짜임** 이었습니다.

### 무엇이 문제였나

v2.0 을 재 봤습니다.

| 문제 | v2.0 실측 | v2.1 |
|---|---|---|
| 절 제목이 파일 이름이다 | 기능명세 9절 중 7절이 `수집 대장 (D-02) — collect_log.py · 515줄` 꼴 | 제목을 **할 수 있는 일**로 바꿨다 |
| 조작 경로가 없다 | 411줄 중 실행 명령이 **1줄** | 화면 명세를 버튼·연결선으로 그렸다 |
| 상태가 두 곳에 있어 갈라졌다 | `check_data.py` 가 한 문서엔 "없다", 다른 문서엔 "✅ 닫힘" | 상태는 **2절 표에만** 적는다 |
| 굵은 글씨가 너무 많다 | 411줄에 볼드 150개 = **2.7줄마다 하나** | 화면 문구와 기능 ID 두 곳만 |
| 이모지 위계가 없다 | 10종 39개, 뜻이 정의되지 않음 | 🔴 막힘 · 🟡 진행 중 · ✅ 닫힘 **셋만** |

목차 규칙은 [부록 D](명세서.md#부록-d-이-문서를-쓰는-규칙)에 적어 두었습니다.
다음 판을 쓰는 사람이 같은 자리로 돌아오지 않게 하려는 것입니다.

### 무엇을 빌려 왔나

기존 문서를 버리지 않았습니다. **자리만 옮겼습니다** — 버그 서사와 결정 근거는
[부록 A](명세서.md#부록-a-왜-이렇게-만들었나)로 내렸고, 줄 수·모듈 지도는
[부록 B](명세서.md#부록-b-모듈-지도)로 내렸습니다. 본문에는 기능만 남겼습니다.

## 2. 새로 밝혀진 사실 셋

### 2.1 🔴 시세 수집기가 대장에 기록을 안 남긴다

```
collect_log   krx_index  4,343행   마지막 성공  2026-08-26T10:34:59
              krx_stock  4,343행   마지막 성공  2026-08-26T11:37:48
```

`krx_store` 가 `collect_log` 를 쓰지도 읽지도 않습니다. 다시 돌려도 이 시각이
안 바뀝니다. **수집 현황 화면의 가장 중요한 칸이 닷새째 거짓말을 하고 있습니다.**

화면을 만들기 전에 고쳐야 합니다. 안 고치면 화면이 틀린 값을 예쁘게 보여 줍니다.

### 2.2 🔴 OHLC 대소 검증을 건너뛰는 125행

거래정지 표시행(시·고·저가 0)은 대소 검사를 건너뜁니다. `if halted: … elif …` 구조라
그렇습니다. 283,343행은 거래량도 0 이라 맞는 처리입니다.

그런데 **125행은 거래량이 0 보다 큽니다.** 전부 거래대금도 0 보다 큽니다.
가장 큰 것은 `349720` 의 2020-10-07 로 147,946주 · 288,494,700원이 실제 거래됐습니다.

거래가 있었는데 시·고·저가 0 으로 들어온 행입니다. 정지 표시가 아닌데 정지로 분류돼
한 번도 검증을 안 받았습니다. 전체의 0.0014% 입니다.

### 2.3 🟡 품질 게이트 98.6초의 원인이 우리 코드 안에 적혀 있었다

전체 2분 58초 중 98.6초가 질의 하나입니다. 그리고 그 질의 모양은
`ingest/store/krx_store.py` 가 **"18초 vs 0.8초"라고 스스로 경고해 둔 형태**입니다.
같은 저장소의 `scripts/check_data.py` 가 그 경고를 안 따랐습니다.

게이트가 느리면 사람이 안 돌립니다. 그러면 게이트가 있으나 마나입니다.

## 3. 외부 가이드를 대조한 결과

팀장이 외부에서 받아 온 데이터 파이프라인 가이드(FastAPI + PostgreSQL + 4에이전트)를
우리 코드와 항목별로 대조했습니다. 30여 항목이 셋으로 갈렸습니다.

| 갈래 | 개수 | 대표 |
|---|---|---|
| 이미 만들어 둔 것 | 12 | 수집 대장 · 재시도 백오프 · 룩어헤드 방지 · 무결성 검사 |
| 정면으로 부딪히는 것 | 10 | PostgreSQL · ±30% 필터 · 격리 테이블 · 종목토론방 |
| 가이드가 옳고 우리에게 없는 것 | 16 | 화면 전부 · 배선 공백 |

### 실측으로 가이드를 기각한 것 셋

9,209,812행 전수 검사입니다 (2026-08-31).

| 가이드 규칙 | 재 본 결과 |
|---|---|
| 등락률 ±30% 초과면 오류 | **오탐 1,592건** — 전부 정리매매·거래정지재개·자본변동·신규상장으로 설명되는 정상 데이터. 동시에 **미탐 495건** — 2015-06-15 이전은 상한이 ±15% 였다 |
| 거래량 0 인데 주가 변동이면 오류 | **11,370건이 걸리는데 100% 가 거래정지 표시행.** `volume=0 이면서 open>0` 인 행은 **0건** — 규칙의 진짜 양성 공간이 비어 있다 |
| 문제 데이터를 격리 테이블로 빼고 적재 중단 | **12,962행 · 1,002 종목(전체의 27.2%)** 이 걸린다. 게다가 거래정지일 종가가 다음 재개일 등락률의 **기준**이라, 정지행을 격리하면 재개일 468행의 설명 근거가 사라져 "설명 안 됨 0건"이 스스로 깨진다 |

이 숫자들은 발표에서 *"왜 단순 규칙을 안 썼나"* 에 대한 답이 됩니다.

**가이드 덕분에 얻은 것도 있습니다** — 위 [2.2](#22--ohlc-대소-검증을-건너뛰는-125행) 의
125행은 가이드의 "거래량 0인데 주가 변동" 규칙을 거울처럼 뒤집다가 찾았습니다.

## 5. 범위에서 뺀 것

원래 이 파트의 다음 작업은 DART 공시 적재였습니다. 팀 문서 두 곳이 이미
"지금이 아니다"라고 답해 둔 것을 뒤늦게 확인했습니다.

| 무엇 | 어디에 적혀 있었나 |
|---|---|
| 공시(F-28) → **3차** | 요구사항 v2.0 §2 — *"공시 시점 정합을 룩어헤드 없이 2주에 붙이면 우리 프레이밍이 그 지점에서 무너진다"* |
| 거시 통계 → **범위 밖** | Must 18건에도 계획서 일정표에도 없다 |

원래 계획한 PR 셋(DART 준비 · 공시 적재 · 통계 정규화)이 **Must 18건 중 0건**을
담당하고 있었습니다. 순서를 바꿉니다.

### 다만 막다른 길 하나는 없앱니다

`ingest/clients/dart_data.py` 의 404 안내 메시지가
`python scripts/build_corp_code.py` 를 실행하라고 합니다. **그 파일이 없습니다.**
팀원이 DART 를 건드리는 순간 존재하지 않는 명령을 안내받고 막힙니다.

실질 로직(`fetch_corp_code_rows`)은 이미 있습니다. JSON 으로 쓰는 래퍼만 없습니다.

## 6. 거시 통계 룩어헤드 — 아직 안 새지만 코드가 안전하다고 단언한다

`ecos_data.align_to_dates` 와 `fred_data.align_to_dates` 가 통계의 **기간 시작일**을
그 값을 알게 된 날로 취급합니다. 2026년 7월 소비자물가가 2026-07-01 부터 붙습니다.
실제 공표는 8월 초입니다.

| 주기 | 선취 기간 |
|---|---|
| 월 | 약 32일 |
| 분기 | 약 115일 |
| 연 | 최대 424일 |

**지금 새고 있지는 않습니다.** `align_to_dates` 호출처가 저장소 전체에서 0건이고
`macro_series` 표도 없습니다(`user_version=4`).

가장 나쁜 부분은 **코드가 안전하다고 단언한다**는 것입니다. `fred_data.py` 의 주석이
*"앞의 값을 끌어오는 방향이 맞다 … 뒤의 값을 끌어오면 미래 정보가 새어 든다"* 고
적혀 있습니다. 보간 방향은 맞습니다. **틀린 것은 날짜 도장입니다.**
그래서 룩어헤드 점검을 해도 이 자리를 지나칩니다.

쓰지 않기로 한 것과 별개로, 안전하다고 적힌 채로 두면 안 됩니다.

## 7. 수업 자료를 대조했습니다

`learning/` 을 읽고 우리 코드와 맞춰 [부록 C](명세서.md#부록-c-수업에서-배운-것과-우리-자료)에
정리했습니다. 팀원 넷이 같은 수업을 들으므로 수업 용어를 쓰면 설명이 짧아집니다.

가장 쓸모 있었던 것 셋입니다.

1. **수업이 개념을 말한 자리에 우리는 숫자가 있습니다.** 생존편향 → 중도 소멸 910종목,
   룩어헤드 → 상관 10배 부풀림. 짝을 지으면 발표에서 강합니다.
2. **수업 지침을 그대로 쓰면 안 되는 곳이 다섯 있습니다.** 결측치를 채우라는 지침이
   대표적입니다 — 거래정지 구멍을 채우면 존재하지 않는 체결가가 생깁니다.
3. **06-data-crawling 7번에 KRX 업종분류·WICS 수집 코드가 둘 다 있습니다.**
   킥오프 안건 ⑤(산업 분류)의 근거로 쓸 수 있습니다.

그리고 수업 실습 산출물에서 버그 둘을 실측했습니다 — WICS 루프의 섹터 코드 고정으로
420행 전량이 한 섹터로 수집됐고, 기준일이 어긋난 두 표를 outer merge 해 2,765 종목이
5,358행으로 불어났습니다. **둘 다 에러 없이 조용히 틀립니다.** 우리 조인에도 행 수
검증이 필요하다는 뜻입니다.

⚠️ `09-finance-ml` 은 지금 작성 중입니다. 조사하는 동안에도 파일이 커졌습니다
(6,554 → 6,668바이트). 작업할 때마다 다시 봐야 합니다.
