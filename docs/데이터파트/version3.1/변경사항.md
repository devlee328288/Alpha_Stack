## 1. 🔴 종목 피처·라벨이 원가격이었다 (이슈 [#80](https://github.com/devlee328288/Alpha_Stack/issues/80))

### 무엇이 잘못됐나

v3.0 에서 `daily_price` 에 수정주가 `adj_*` 4칸을 채우고 팀에 *"`close` 말고
`adj_close` 를 쓰세요"* 라고 안내했습니다. **그런데 정작 반출 스크립트가 원가격을
보고 있었습니다.** 신장환 팀원이 발견했습니다.

원문에는 액면분할이 반영돼 있지 않아 분할일 하루가 폭락으로 읽힙니다.

```
삼성전자 2018-04-25 · 5거래일 시가 수익률
  원가격으로 →  -97.90%  → 라벨 "하락"     ← 틀렸다
  수정주가로 →   +5.12%  → 라벨 "상승"     ← 맞다
```

### 실측 피해

| 무엇 | 값 |
|---|---|
| 분할·병합이 있던 표본 종목 | **18 / 30 (60%)** |
| 라벨이 뒤집힌 행 | **370행 (0.448%)** |
| `rsi_14` 오염 (삼성전자 · 분할 1건) | **198행 (5.49%)** · 최대 50.17포인트 |
| `atr_14` | 186행 (5.16%) |
| `sma_60` / `sma_20` / `sma_5` | 59행 / 19행 / 4행 |

`sma_5` 가 4행인데 `rsi_14` 가 198행인 것은 **지수이동평균 계열이 충격을 오래 끌기**
때문입니다. 단순이동평균은 창을 벗어나면 회복되지만 EMA 는 감쇠할 뿐입니다.

재반출 후 라벨 분포도 움직였습니다 — `하락 29,271 → 29,194` · `상승 26,352 → 26,408`.
**분할일 가짜 폭락이 "하락" 으로 세어지고 있었다**는 뜻입니다.

### 어떻게 고쳤나

가격 칸을 고르는 자리를 `price_basis` **하나로** 모았습니다.

| 대상 | 기준 | 왜 |
|---|---|---|
| 종목 | **`adj_*`** | 액면분할이 있다 |
| 지수 | `close` (원문) | 분할이라는 사건 자체가 없고 `index_price` 에 수정 칸도 없다 |

**칸 이름은 바꾸지 않았습니다** — `sma_5` 는 그대로 `sma_5` 이고 안의 값만 바뀝니다.
받아 쓰던 팀원 코드는 고칠 것이 없습니다.

**평가 계층(`evaluation/horizon.py`)은 한 줄도 안 건드렸습니다.** 그쪽은
`rows[i]["open"]` 이라는 **이름만** 읽으므로, 그 이름 자리에 수정 시가를 앉혀 넘기면
같은 함수가 그대로 수정주가로 셉니다. `verify_labels` 의 기존 대조도 통과합니다.

> ⚠️ 함정이 하나 있어 방어를 넣었습니다. 거래정지일의 `adj_open` 은 `NaN` 인데
> `horizon` 쪽 걸러내기는 `if not entry.get("open")` 이라 **`NaN` 을 못 거릅니다**
> (`not float("nan")` 은 `False`). 원문에서 정지일 시가가 `0` 이라 걸러지던 것과 같은
> 규약이 되도록 `0` 으로 바꿔 담습니다.

### 영향 범위

- **바뀐 파일은 8개 중 1개** — `features_labels_stocks30_dev.csv`. 나머지 7개는
  직전 반출과 **SHA-256 까지 동일**합니다(반출이 재현 가능함도 함께 확인).
- 지수(`features_labels_kospi200_dev.csv`)는 라벨 분포가 **완전히 같습니다.**
- 강민석 팀원의 `evaluation_backtest.py`·`evaluation_risk.py` 는 `daily_price` 를
  직접 읽지 않아 영향이 없습니다.

> 🔴 **행 수 검증으로는 이걸 못 잡습니다.** 재반출 전후 행 수가 80,439 로 똑같고
> SHA-256 만 달랐습니다. `verify_hf_dataset.py` 는 지금 원시 자료·표본·선정만 대조하고
> **피처·라벨은 보지 않습니다.** 거기까지 넓히는 것은 남은 일입니다.

## 2. 반출본을 칸마다 재서 카드가 그 값을 쓰게 했다

### 왜

데이터셋 카드에 `adj_source` 분포 같은 숫자가 **글자로 박혀** 있었습니다. 자료가
바뀌어도 글자는 안 바뀝니다.

### 무엇을 만들었나

| 새 파일 | 무엇 |
|---|---|
| `common/export_profile.py` | 반출 폴더의 파일을 **직접 읽어** 칸마다 잰다 |
| `scripts/profile_export.py` | 이미 만들어 둔 반출 폴더에 나중에 붙이는 CLI |
| `tests/test_export_profile.py` | 16개 — 기대값은 **손으로 센 수**다 (항등식이 아니다) |
| `PROFILE.json` (반출 산출물) | 파일 8개 · 칸 181개의 결측률·값 범위·분포·앞 3행 |

**DB 를 다시 조회하지 않고 나간 파일 자체를 읽습니다.** 카드가 설명해야 하는 것은
"DB 에 무엇이 있나" 가 아니라 **"지금 팀원 손에 가는 이 파일에 무엇이 들었나"**
이기 때문입니다.

parquet 은 **칸 하나씩** 읽습니다 — 302MB·789만 행을 통째로 열면 문자열 칸이 수 GB 를
먹습니다. 칸 단위로는 **파일 8개 181칸을 7.8초**에 잽니다.

### 카드가 어떻게 달라졌나

8.9KB → 40KB. 칸별 표(핵심은 펼치고 나머지는 `<details>`), 결측 요약, 앞 3행 실물,
`PROFILE.json` 사용법이 들어갔습니다.

**값이 실제로 그럴 때만 붙는 조건부 경고**를 뒀습니다. 설명을 칸 이름에만 매달면
"최댓값 669만%" 가 범위 `-15.38 ~ 23.42` 인 지수 파일에도 붙어 **카드가 그 파일에
대해 거짓말을 합니다.**

### 재면서 드러난 것

**① 지수 51종 중 하나는 `close` 가 통째로 없다.** `코스피 (외국주포함)` 이고 결측이
정확히 3,618행 — 개발구간 거래일 수와 같습니다. 지수 파일은 12칸 중 9칸에 결측이
있습니다(`open`·`high`·`low` 14.15% · 거래량·거래대금·시가총액 12.04%).
**특정 지수를 쓰기 전에 그 지수에 그 칸이 있는지부터 봐야 합니다.**

**② `change_rate` 최댓값 6,699,900% 는 오류가 아니다.** 거래정지 중 종가가 `1`원으로
적혀 있던 종목이 67,000원에 재개된 날입니다(`008080` · 2013-09-11). `close` 최솟값
`1` 도 실제 가격이 아니라 거래정지 표시값입니다(17행). **그대로 피처에 넣으면 스케일이
이 한 행에 끌려갑니다.**

### 테스트가 잡은 진짜 버그

빈 문자열과 `None` 이 둘 다 `"(빈값)"` 으로 접히는데 **대입으로 담아 한쪽이 조용히
사라지고** 있었습니다. 합계 행 수는 그대로라 눈으로도 안 잡힙니다.

## 3. 노트북 04 에 9~11장을 이었다

`notebooks/02-품질·전처리/04.수정주가를채우다.ipynb` — 37셀 → **56셀**.

- **9장** 반출이 원가격을 보던 이야기. 라벨 뒤집힘·피처 오염을 노트북 안에서 직접 잰다
- **10장** `PROFILE.json` 을 읽어 칸별 통계를 펴고, 위 두 발견을 원문까지 따라간다
- **11장** 배운 것 여섯 줄

### 노트북이 이미 깨져 있던 것도 고쳤다

15번 셀이 앵커를 `"20140613"` 으로 못 박아 두었는데, **FDR 의 3,000거래일 창이 날마다
하루씩 밀리면서 오늘 그 날이 창 밖으로 나가 `KeyError` 로 죽었습니다.** 창은 오늘이
아니라 **종목의 마지막 거래일**에 걸리므로, 날짜를 적어 두면 언젠가 반드시 깨집니다.
`min(adjusted)` 로 그때그때 잡게 했습니다.

앵커가 `20140613 → 20140616` 으로 밀리면서 이어붙이기 오차 실측이 **0.39% → 0.397%**
가 됐습니다. 노트북과 카드의 숫자를 실측에 맞추고, **소수 셋째 자리는 그날의 앵커가
정한다**는 것도 함께 적었습니다 — "0.4% 안쪽" 이 요지입니다.

## 4. 🆕 API 키 발급 가이드 (팀원 전원 대상)

[`API키_발급_가이드.md`](API키_발급_가이드.md)

`.env` 는 `.gitignore` 가 막고 저장소는 PUBLIC 이라, 키는 **각자 받아 각자 넣어야**
합니다. 그런데 어디서 어떻게 받는지가 어디에도 정리돼 있지 않았습니다.

키 9종의 발급처·절차·한도·함정을 한 장에 모았습니다. 특히

- **KRX 는 발급이 2단계** — 인증키 발급과 **서비스별 이용신청**이 별개입니다.
  2단계를 건너뛰면 `Unauthorized API Call` 이 뜨는데, 키가 틀린 줄 알게 됩니다.
- **공공데이터포털은 Encoding/Decoding 두 벌** — 섞어 쓰면 "등록되지 않은 키" 가
  뜨고, 키를 재발급받게 되는 함정입니다.
- **네이버 검색 API 는 2026-07-30 부로 신규 발급이 중단**됐습니다.

### `scripts/check_keys.py` — 자가 점검

```bash
python scripts/check_keys.py            # 있는지 · 모양이 맞는지
python scripts/check_keys.py --live     # 실제로 통하는지
```

**키 값을 한 글자도 출력하지 않습니다**(길이와 앞 두 글자만). 화면을 공유해도 안전합니다.
"키가 없다"·"모양이 틀렸다"·"이용신청이 안 됐다" 를 **갈라서** 알려 줍니다 — 셋 다
겉으로는 "안 된다" 로만 보이지만 할 일이 다릅니다.

**2026-09-03 실측** — 8개 키가 실호출까지 통과했습니다(KRX · 공공데이터포털 · DART ·
ECOS · FRED · KOSIS · 금감원 · HuggingFace).

### `.env` 와 `.env.example` 을 같은 차림새로 맞췄다

둘이 어긋나 있었습니다. **키 이름이 다른 게 아니라 항목이 서로 없었습니다.**

| 어디에만 있었나 | 항목 | 처리 |
|---|---|---|
| `.env` | `DATA_GO_KR_API_KEY1`~`5` | **하나로 합침** — 다섯이 전부 같은 값이었다 |
| 견본 | `STORE_BACKEND` | `.env` 에 `sqlite` 명시 (코드 기본값에 기대지 않는다) |
| 견본 | `DATABASE_URL` · `YOUTUBE_API_KEY` | 빈 값으로 자리만 |

이제 **항목과 순서까지 완전히 같습니다**(15개). 공공데이터포털은 계정당 인증키
**하나**를 주고 활용신청한 모든 API 에 그 키를 씁니다 — 다섯 개가 필요하지 않았습니다.
코드는 `1`~`5` 도 별칭으로 계속 받습니다.

## 5. 🆕 공공데이터포털 수집 설계

[`공공데이터포털_수집_설계.md`](공공데이터포털_수집_설계.md) · **설계만** (구현은 다음)

가져올 가치가 있는 것은 **시세도 재무도 아니라 "다리"** 입니다 —
`종목코드 ↔ 법인등록번호 ↔ ISIN` 매핑입니다. 공공데이터포털의 기업기본·재무정보는
전부 `crno`(법인등록번호)로 조회하는데 우리 `daily_price` 에 그 칸이 없어서,
매핑 없이는 **붙일 방법 자체가 없습니다.**

덤으로 **상장일·상장폐지일·감사의견·종업원수**가 들어옵니다. 지금 "개발구간 끝보다
90일 앞에서 자료가 끊기면 중도 소멸" 이라는 어림으로 하던 것을 **공식 기록**으로
바꿀 수 있습니다.

엔드포인트 6개를 **직접 호출해서** 확인했고(문서를 옮겨 적지 않았습니다), 못 찾은
6개는 활용자 가이드를 받아 확정합니다. 마이그레이션은 **v10** 예정입니다.

## 이번 판의 교훈

| 무엇 | 배운 것 |
|---|---|
| 고친 것과 나가는 것은 다르다 | 원본을 고쳤다고 **경로가 고쳐지지는 않는다** |
| 행 수는 값을 못 지킨다 | 행 수가 같고 SHA 만 다를 수 있다 |
| 칸 이름만 읽는 함수는 갈아끼울 수 있다 | 남의 파트를 안 건드리고 기준을 바꿨다 |
| falsy 검사는 `NaN` 을 못 거른다 | `not 0` 은 `True`, `not float("nan")` 은 `False` |
| 설명은 재서 쓴다 | 손으로 적은 숫자는 자료가 바뀌어도 안 바뀐다 |
| 날짜를 못 박으면 언젠가 깨진다 | 외부 API 의 창은 날마다 밀린다 |
