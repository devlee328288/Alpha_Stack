## 2. 문제 진술

### 2.1 누구의 문제인가

**나의 문제가 아니라 뒤 순번 팀원의 문제입니다.**

이 파트가 잘 되면 아무도 눈치채지 못합니다. 잘못되면 **그 사실을 아무도 눈치채지
못한 채** 프로젝트 전체가 틀린 결론을 냅니다. 그게 이 파트의 성격입니다.

| 이 파트가 실패하는 방식 | 뒤에서 무슨 일이 일어나나 |
|---|---|
| 자료가 **없다** | 팀원이 첫 줄을 못 쓴다. 눈에 보이므로 즉시 발견된다 |
| 자료가 **틀렸다** | 모델이 돌아가고 성능도 나온다. **아무도 모른다** ← 🔴 진짜 위험 |
| 자료가 **미래를 본다** | 성능이 좋게 나온다. 발표하고 나서야 틀린 걸 안다 ← 🔴 최악 |
| 자료를 **다시 못 만든다** | 재현이 안 된다. 결론이 주장으로 격하된다 |

### 2.2 그래서 이 파트의 산출물은 '데이터'가 아니다

> **산출물은 데이터가 아니라 "그 데이터를 믿어도 되는 이유"입니다.**

팀 전체가 *"예측기가 아니라 검증기를 만든다"* 로 방향을 잡았습니다. 데이터 계층에서
그 말을 번역하면 이렇게 됩니다 — **"자료를 모았다"가 아니라 "이 자료가 무엇을 언제
어디서 어떻게 담았고, 무엇이 빠졌는지 말할 수 있다."**

### 2.3 가장 비싼 실패 — Point-in-Time 위반

🔴 **이 파트에서 가장 조용하고 가장 치명적인 오류입니다.**

2020 사업연도 재무제표를 `2020-12-31` 행에 붙이면 **미래를 본 것입니다.**
그 숫자가 세상에 나온 날은 **2021년 3월**입니다.

```
사업연도 종료   2020-12-31   ← 여기 붙이면 look-ahead
사업보고서 제출  2021-03-20   ← 실제로 알 수 있게 된 날. 여기 붙여야 한다
```

석 달치 미래를 학습에 넣고도 **예외는 나지 않습니다.** 성능만 좋아집니다.

| 자료 | 잘못 붙이기 쉬운 날짜 | 붙여야 하는 날짜 |
|---|---|---|
| 재무제표 | 사업연도 종료일 | **공시 접수일** |
| 정기보고서 | 보고서 대상 기간 | **접수일** |
| 뉴스 | 사건 발생일 | **기사 발행 시각** |
| 지수·시세 | — | 장 마감 후 확정. 당일 15:30 이전에는 알 수 없다 |

**그래서 이 파트의 모든 저장 스키마는 `발생 시각`과 `알 수 있게 된 시각`을 따로 둡니다.**

> 🔬 **편법 하나를 실측으로 기각했습니다.** DART 재무제표 응답에는 접수일이 없고
> 접수번호만 옵니다. 앞 8자리를 날짜로 쓰는 관행이 있어 정기공시 **4,800건을 검증**했더니
> **3건이 어긋났고 그중 둘은 실제 접수일보다 3일 이른 방향**이었습니다. 아직 공개되지
> 않은 정보를 사흘 먼저 아는 셈입니다. → **공시목록 API 조인으로 갑니다.**

### 2.4 두 번째 문제 — 크롤링은 '되는가'가 아니라 '해도 되는가'

기술적으로 긁을 수 있는 것과 긁어도 되는 것은 다릅니다. 그리고 이 판단을
**나중에** 하면 이미 만든 것을 버려야 합니다.

> 🔴 **v1.0 이 이 절에서 틀렸습니다.** *"종목토론방 첫 페이지는 허용"* 이라고 읽었는데,
> `robots.txt` 원문을 다시 보니 그 `Allow` 규칙들이 **전부 `User-agent: yeti`(네이버
> 자체 크롤러) 그룹 소속**이었습니다.

```
finance.naver.com/robots.txt
    User-agent: *
    Disallow: /                              ← 우리에게 적용되는 그룹. 전면 불허
    User-agent: yeti
    Disallow: /
    Allow: /item/board.naver?code=*          ← yeti 전용. 우리 것이 아니다
```

[RFC 9309 §2.2.1](https://www.rfc-editor.org/rfc/rfc9309.txt) 상 크롤러는 **자신에게
매칭되는 그룹 하나만** 따릅니다. → **종목토론방 수집을 접었습니다.**

> 📌 **그룹이 갈리는 근거는 빈 줄이 아닙니다.** 원문에는 `Disallow: /` 와
> `User-agent: yeti` 사이에 빈 줄이 없습니다. RFC 9309 는 *"rule 라인이 나온 뒤의
> user-agent 라인이 새 그룹을 연다"* 로 정의합니다. 빈 줄에 근거를 두면 다른 사이트를
> 읽을 때 잘못 일반화합니다.

> 💡 **UA 를 `yeti` 로 위장하는 안은 선택지에 올리지 않습니다.** 사칭입니다.
> 그리고 **이건 손실이 아니라 산출물입니다** — 수집을 안 한 것보다 **안 하기로 정한
> 근거가 문서에 남는 것**이 낫습니다.

## 3. 그래서 무엇을 만드나

### 3.1 네 덩어리

| # | 덩어리 | 무엇 |
|---|---|---|
| ① | **수집기** | 시세 · 지수 · 공시 · 통계 · 뉴스 · 카페글 · 동영상 |
| ② | **적재·정제 계층** | 원본 보존 → 정규화 → 품질 게이트. 수집 대장과 워터마크 |
| ③ | **공급 API** | 뒤 순번 팀원이 함수 하나로 꺼내 쓰는 정문 |
| ④ | **화면** | 수집 현황 + 코스피 대시보드. 버튼으로 즉시 수집 |

**수집 범위는 3종입니다** — ① 시세·통계 ② 공시 ③ 뉴스·동영상.
(v1.0 의 4종에서 커뮤니티가 카페글만 남아 뉴스 쪽으로 합쳐졌습니다.)

### 3.2 두 가지 수집 주기

| 주기 | 무엇 | 왜 |
|---|---|---|
| **하루 1회 배치** | 전체 대상 증분 수집 | 장 마감 후 확정된 자료를 받는다 |
| **버튼 즉시 수집** | 사용자가 고른 대상만 | 시연 때 *"지금 받아 보겠습니다"* 가 되어야 한다 |

⚠️ **버튼이 배치를 대체하지 않습니다.** 버튼은 *증분 한 조각*이고, 빠진 구간을 메우는
책임은 배치와 대장에 있습니다. 버튼만 있으면 **아무도 안 누른 날이 구멍**으로 남습니다.

## 4. 성공 기준

### 4.1 임계가 있는 기준 (합격/불합격)

| # | 기준 | 측정 방법 |
|---|---|---|
| **1. 공백을 말할 수 있다** | 모든 수집 대상에 대해 *"어느 날짜가 비었나"* 가 **전부 열거**된다 | 품질검사 → `reports/data_quality.json`. 미검사 항목이 있으면 `exit 1` |
| **2. Point-in-Time 위반 0건** | 공시·보고서 계열에 `알 수 있게 된 시각` 이 **비어 있는 행이 0** | 스키마 제약 + 테스트. 접수일 없는 행은 적재 거부 |
| **3. 재현된다** | 같은 구간을 다른 날 두 번 떠도 **스냅샷 해시가 같다** | ✅ 지수는 구현 완료 (`885ea3d3…`) |
| **4. 약관을 지킨다** | `robots.txt` 허용 여부를 **코드가 실행 시점에 확인**하고, 불허 경로는 요청 자체를 안 한다 | ✅ `common/robots.py` 구현 완료. ⚠️ **부르는 수집기가 아직 0건** |
| **5. 팀원이 30분 안에 쓴다** | 문서를 처음 본 팀원이 **함수 하나**로 원하는 구간을 받아 첫 피처를 만든다 | **킥오프에서 실제로 시켜 보고 시간을 잽니다** |

### 4.2 임계 없이 실측치만 보고하는 칸

- 대상별 **수집 소요 시간**과 호출 수 (일 한도 대비 몇 %인가)
- 뉴스·카페글의 **일별 수집량** 분포
- 정제 단계에서 **버려진 행의 비율과 사유**

> **왜 여기에 임계를 안 거나.** 수집량에 합격선을 걸면 *"많이 긁어야 통과하는"*
> 역인센티브가 생깁니다. 우리가 원하는 것은 **많은 자료가 아니라 설명 가능한 자료**입니다.

## 5. 무엇을 하지 않는가 — 범위 밖

| 안 하는 것 | 왜 |
|---|---|
| **종목토론방 수집** | `robots.txt` 가 제3자 크롤러에게 **사이트 전체를 막는다** (§2.4) |
| **실서버 운영 · 클라우드 배포** | 팀 합의. 1차는 로컬로 마무리. Supabase 미사용 |
| **외부 DB(Postgres 등) 상시 운영** | **SQLite 하나**로 충분하다. `krx_pg.py` 1,428줄(⚠️ 귀속이 틀렸다 — 1,428 은 Postgres 경로 **세 파일 합계**이고 `krx_pg.py` 만이면 **412줄**. 2026-08-31 재측정)은 있지만 1차에서 안 켠다 |
| **실시간 틱·호가 수집** | 5거래일 지평에 틱은 과잉이다 |
| **기사 본문 전문 저장·재배포** | 저작권. 그리고 네이버 약관 7.3 ③ 이 저장·가공을 금지한다. 제목·요약·링크까지만 |
| **로그인이 필요한 페이지 수집** | 약관 위반 소지. 공개 페이지와 공식 API 만 |
| **`robots.txt` 가 막은 경로** | 기술적으로 가능해도 하지 않는다 |
| **감성분석 모델 학습** | 마이닝은 **집계·키워드·빈도**까지. 모델은 다른 담당 |

> ⚠️ **"안 하는 이유를 적는 것"이 범위를 선명하게 만듭니다.** 위 8줄이 없으면
> 2주 동안 범위가 계속 늘어납니다.

## 6. 이 파트의 약점 — 심사자가 찌를 곳

| 찌를 곳 | 우리 답 |
|---|---|
| **"수집은 그냥 API 호출 아닌가"** | 호출은 쉽습니다. 어려운 건 **언제 알 수 있었는지**를 지키는 것입니다. §2.3 의 point-in-time 이 이 파트의 실제 난이도이고, **편법 하나를 4,800건 실측으로 기각**했습니다 |
| **"크롤링이 합법인가"** | `robots.txt` 를 **직접 받아 확인**했고, 그 결과 **수집 대상 하나를 접었습니다**(§2.4). 코드가 실행 시점에도 확인합니다 |
| **"자료가 예측에 도움이 되긴 하나"** | **이 파트는 그것을 주장하지 않습니다.** 판정은 검증 엔진의 몫이고, 실제로 팀원 제안을 우리 데이터로 재서 **방향 축을 기각한 사례**가 있습니다 |
| **"뉴스는 노이즈 아닌가"** | 그럴 수 있습니다. 그래서 **수집과 판정을 분리**했습니다. 우리는 잴 수 있게 만들고, 쓸모없다고 나오면 **그 결과를 그대로 적습니다** |
| **"대시보드는 겉치레 아닌가"** | 화면의 1순위는 **수집 현황과 공백을 드러내는 것**이고, 코스피 화면은 그다음입니다 |
