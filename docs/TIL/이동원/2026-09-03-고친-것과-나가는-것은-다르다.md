## 오늘 한 것

어제 수정주가 `adj_*` 4칸을 채우고 팀에 *"`close` 말고 `adj_close` 를 쓰세요"* 라고
안내했습니다. 오늘 신장환 팀원이 알려 왔습니다 — **정작 우리 반출 스크립트가 원가격을
보고 있다**고.

맞았습니다. 게다가 피처만이 아니라 **라벨까지** 그랬습니다.

---

## 1. 원본을 고쳤다고 경로가 고쳐지지는 않는다

이게 오늘의 핵심입니다.

`daily_price` 테이블에는 `adj_close` 가 제대로 들어 있었습니다. 노트북도 썼고, 카드에도
적었고, 팀에도 안내했습니다. **그런데 팀에 실제로 나가는 파일을 만드는 코드가 그 칸을
보지 않았습니다.**

```python
# scripts/export_team_dataset.py — 어제까지
close = frame["close"].astype(float).to_numpy()      # 🔴 원문
out["fwd_return_5d"] = forward_returns_aligned(rows, day_index)   # 🔴 rows 도 원문
```

"고쳤다" 고 생각한 것과 "나간다" 는 것 사이에 층이 하나 더 있었습니다. 저는 그 층을
세지 않았습니다.

### 얼마나 어긋났나

행마다 두 번 계산해서 맞대어 봤습니다.

```
삼성전자 2018-04-25 · 5거래일 시가 수익률
  원가격으로 →  -97.90%  → 라벨 "하락"
  수정주가로 →   +5.12%  → 라벨 "상승"
```

라벨이 **정반대**입니다. 표본 30종목에서 분할이 있던 종목이 18개(60%), 라벨이 뒤집힌
행이 370행(0.448%)이었습니다.

---

## 2. 라벨보다 피처가 훨씬 오래 아프다

이건 예상 못 했습니다. 라벨은 5거래일 창이라 분할일 근처 몇 행만 틀립니다. 그런데
피처는 창이 깁니다. 삼성전자 액면분할 **한 건**만 놓고 재 봤습니다.

| 지표 | 오염된 행 | 비율 |
|---|---:|---:|
| `sma_5` | 4 | 0.11% |
| `sma_20` | 19 | 0.53% |
| `sma_60` | 59 | 1.66% |
| `atr_14` | 186 | 5.16% |
| **`rsi_14`** | **198** | **5.49%** |

`sma_5` 는 4행인데 `rsi_14` 는 198행입니다. **`sma_60` 보다도 `rsi_14` 가 훨씬
깁니다.** 창 길이만 보면 60 > 14 인데 왜 반대일까요.

**단순이동평균은 창을 벗어나면 회복되지만, 지수이동평균은 감쇠할 뿐 끊기지 않기
때문입니다.** `sma_60` 은 분할일이 60칸 뒤로 밀려나면 그 순간 깨끗해집니다. `rsi_14`
는 EMA 기반이라 분할일의 충격이 계속 남아 있는 값에 섞여 들어갑니다. RSI·ATR·MACD 가
전부 이 계열입니다.

`rsi_14` 의 최대 어긋남은 **50.17포인트**였습니다. 0~100 척도에서 50포인트면
과매수(70)와 과매도(30)를 가르는 지표가 반대편으로 넘어갑니다.

## 3. 남의 파트를 안 건드리고 고치는 법

라벨 규칙은 `evaluation/horizon.py` 의 공개 함수를 따릅니다. 그런데 평가 계층은
강민석 팀원 담당이라 제가 고칠 수 없습니다. 처음엔 막혔다고 생각했는데, 그 함수를
읽어 보니 이렇게 돼 있었습니다.

```python
out.append(exit_["open"] / entry["open"] - 1.0)
```

**칸 이름만 읽습니다.** 값이 어디서 왔는지는 모릅니다.

그래서 부르는 쪽에서 `adj_open` 을 `"open"` 이라는 **이름 자리에 앉혀** 넘겼습니다.
같은 함수가 그대로 수정주가로 셉니다. 평가 계층은 한 줄도 안 바뀌었고,
`verify_labels` 의 기존 대조도 그대로 통과합니다.

> 인터페이스가 **이름으로만** 돼 있으면 구현을 갈아끼울 수 있다는 걸 오늘 처음
> 실감했습니다. 타입으로 묶여 있었다면 이렇게 못 했을 겁니다.

### 다만 함정이 있었다

```python
if not entry.get("open"):     # horizon.py 의 걸러내기
    continue
```

원문에서 거래정지일 시가는 `0` 이라 이 검사에 걸립니다. 그런데 **수정 시가는 그 날이
`NaN`** 입니다.

```python
>>> not 0
True                # 걸러진다
>>> not float("nan")
False               # 🔴 안 걸러진다
```

falsy 검사가 `NaN` 을 못 거릅니다. 지금은 `training_frame` 이 정지일을 이미 덜어내
결측이 0행이지만(실측), 그쪽이 바뀌면 라벨이 조용히 틀립니다. 넘길 때 `0` 으로 바꿔
담아 원문과 같은 규약을 만들었습니다.

## 4. 행 수 검증은 이걸 못 잡는다

재반출하고 직전 것과 대조했습니다.

```
features_labels_stocks30_dev.csv   80,439행 → 80,439행   SHA-256 🔴 다름
나머지 7개                                                SHA-256 ✅ 같음
```

**행 수가 똑같습니다.** 값이 통째로 바뀌었는데도요. 행 수만 세는 검사로는 절대 못
잡습니다. 이건 전에도 한 번 겪은 일인데(칸 이름이 겹쳐 덮어쓰기가 났던 때), 그때
배운 걸 검증 스크립트에 반영해 두지 않아서 또 놓쳤습니다.

`verify_hf_dataset.py` 는 지금 원시 자료·표본·선정만 대조하고 **피처·라벨은 보지
않습니다.** 남은 일로 적어 뒀습니다.

덤으로 얻은 것도 있습니다 — 7개가 SHA-256 까지 같다는 건 **반출이 재현 가능하다**는
증거입니다. "같은 커밋에서 다시 돌리면 같은 파일이 나온다" 를 처음 실측했습니다.

## 5. 설명은 적지 말고 재라

카드에 `adj_source` 분포가 **글자로** 박혀 있었습니다. 자료가 바뀌어도 글자는 안
바뀝니다. 그래서 반출된 파일을 그 자리에서 다시 읽어 칸마다 재고, 카드가 그 값을
쓰게 했습니다.

DB 를 다시 조회하지 않고 **나간 파일 자체를** 읽는 게 중요했습니다. 카드가 설명해야
하는 건 "DB 에 무엇이 있나" 가 아니라 **"지금 팀원 손에 가는 이 파일에 무엇이
들었나"** 니까요. 둘은 같아야 하지만, **같은지 확인하는 것과 같다고 믿는 것은
다릅니다.**

parquet 은 칸 하나씩 읽습니다. 302MB·789만 행을 통째로 열면 문자열 칸이 부풀어 수 GB
를 먹는데, 칸 단위로는 **파일 8개 181칸을 7.8초**에 잽니다.

### 재고 나니 몰랐던 게 나왔다

**지수 51종 중 하나는 `close` 가 통째로 없었습니다.** `코스피 (외국주포함)` 이고
결측이 정확히 3,618행 — 개발구간 거래일 수와 같습니다. 아무도 몰랐습니다.

**`change_rate` 최댓값이 6,699,900% 였습니다.** 하루 상한가가 +30%인데 말이 안 되는
값이라 오류인 줄 알았는데, 원문을 따라가 보니 아니었습니다. 거래정지 중 종가가 `1`원
으로 적혀 있던 종목이 67,000원에 재개된 날이었습니다(`008080` · 2013-09-11).
KRX 가 준 그대로입니다. 다만 그대로 피처에 넣으면 스케일이 이 한 행에 끌려갑니다.

## 6. 조건부로 붙이지 않으면 카드가 거짓말을 한다

칸 설명을 칸 **이름**에만 매달았더니, 지수 파일의 `change_rate`(범위 `-15.38 ~ 23.42`)
에도 "최댓값 669만%" 가 붙었습니다. 그 파일에 대해서는 **거짓말**입니다.

그래서 **값이 실제로 그럴 때만** 붙는 조건부 경고로 바꿨습니다. 판정은 실측값으로
합니다.

```python
("change_rate", lambda c: (c.get("max") or 0) > 1000, "🔴 최댓값이 오류가 아니다 — …"),
```

## 7. 테스트가 진짜 버그를 잡았다

칸별 통계 테스트를 쓰다가 하나가 실패했습니다.

```
assert 칸["분포"]["(빈값)"] == 3      # 빈 문자열 2 + None 1
E       assert 1 == 3
```

빈 문자열과 `None` 이 둘 다 `"(빈값)"` 이라는 이름으로 접히는데, **대입으로 담아
한쪽이 다른 한쪽을 덮어쓰고** 있었습니다. 합계 행 수는 그대로라 눈으로는 안 잡힙니다.

기대값을 **손으로 센 수**로 적어 둔 게 도움이 됐습니다. 계산으로 유도했다면
"프로파일러가 센 값 == 프로파일러가 센 값" 이 되어 아무것도 못 잡았을 겁니다.

## 8. 날짜를 못 박으면 언젠가 깨진다

노트북을 재실행하니 **이미 깨져 있었습니다.**

```python
ANCHOR = "20140613"
...
KeyError: '20140613'
```

FDR 은 최근 3,000거래일만 주는데, 그 창이 **날마다 하루씩 밀립니다.** 어제까지는 창
안에 있던 날이 오늘 밖으로 나갔습니다. 게다가 창은 오늘이 아니라 **종목의 마지막
거래일**에 걸립니다.

`min(adjusted)` 로 그때그때 잡게 고쳤습니다. 앵커가 밀리면서 이어붙이기 오차 실측이
`0.39% → 0.397%` 가 됐고, 노트북과 카드의 숫자를 실측에 맞췄습니다. **소수 셋째
자리는 그날의 앵커가 정한다**는 것도 함께 적었습니다 — "0.4% 안쪽" 이 요지입니다.

> 외부 API 를 쓰는 코드에 날짜를 적어 두면, 그건 **시한폭탄**입니다.

## 9. 키가 다섯 개인 줄 알았는데 하나였다

`.env` 에 `DATA_GO_KR_API_KEY1` ~ `5` 가 있었습니다. API 마다 키가 따로 나오는 줄
알았는데, 지문을 대조해 보니 **다섯이 전부 같은 값**이었습니다.

공공데이터포털은 **계정당 인증키 하나**를 주고, 활용신청한 모든 API 에 그 키를 씁니다.
다섯 개가 필요하지 않았습니다.

그리고 그 키는 `%3D` 로 끝나는 **Encoding 키**였습니다. 포털은 Encoding·Decoding 두
벌을 주는데, 섞어 쓰면 "등록되지 않은 키" 가 뜹니다. **오류 메시지가 키가 틀렸다고만
하니, 멀쩡한 키를 재발급받게 되는 함정**입니다. 게다가 Encoding 키를 `urlencode()` 에
넣으면 `%3D` 가 `%253D` 가 되어 또 실패합니다.

이런 것들을 팀원이 각자 겪지 않도록 [발급 가이드](../../데이터파트/version3.1/API키_발급_가이드.md)
와 `scripts/check_keys.py` 를 만들었습니다. 점검 스크립트는 **"키가 없다"·"모양이
틀렸다"·"이용신청이 안 됐다" 를 갈라서** 알려 줍니다 — 셋 다 겉으로는 "안 된다" 로만
보이지만 할 일이 완전히 다릅니다.

## 오늘의 정리

| 무엇 | 배운 것 |
|---|---|
| 고친 것 ≠ 나가는 것 | 원본을 고쳐도 **경로는 안 고쳐진다.** 층을 다 세어야 한다 |
| EMA 는 오래 아프다 | `sma_60`(59행)보다 `rsi_14`(198행)가 길다. 창 길이 문제가 아니다 |
| 이름으로 된 인터페이스는 갈아끼울 수 있다 | 남의 파트를 안 건드리고 기준을 바꿨다 |
| falsy 검사는 `NaN` 을 못 거른다 | `not 0` 은 `True`, `not float("nan")` 은 `False` |
| 행 수는 값을 못 지킨다 | 80,439행 → 80,439행, SHA 만 다름 |
| 설명은 재서 쓴다 | 손으로 적은 숫자는 자료가 바뀌어도 안 바뀐다 |
| 설명도 조건부여야 한다 | 칸 이름에만 매달면 다른 파일에서 거짓말이 된다 |
| 날짜를 못 박으면 깨진다 | 외부 API 의 창은 날마다 밀린다 |

**팀원의 지적이 아니었으면 몰랐을 것**이라는 게 가장 큽니다. 제 파트 안이라 제가 봐야
했는데, 어제 "다 고쳤다" 고 적어 놓은 문서가 오히려 눈을 가렸습니다.
