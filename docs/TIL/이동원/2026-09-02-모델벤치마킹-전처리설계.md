> 모델 벤치마킹과 전처리 설계를 진행했다. DB 는 읽기 전용으로만 열었다.

## 오늘 배운 것

### 1. 인기와 라이선스는 따로 논다 — 전부 실측해야 한다

다운로드 92만의 `jhgan/ko-sroberta-multitask`, 금융 감성으로 유명한
`snunlp/KR-FinBert-SC`, 우리가 MCP 로 쓰던 **pykrx** 까지 — 전부 **라이선스
미표기**였다. GitHub GraphQL 단발 조회와 HF API 로 후보 24개를 재니 절반 가까이가
원칙(라이선스 명시된 것만)에 걸렸다. 팀장 딥리서치의 주장(backtesting.py=AGPL,
vectorbt=독자)도 재검증해서 정확함을 확인했다 — **남의 조사든 내 조사든 실측으로
재확인**하는 원칙이 또 한 번 값을 했다.

### 2. 같은 문제를 두 세션이 따로 발견하면 — 먼저 온 쪽으로 합친다

접수일 기준으로 붙이면 신규 재무가 개발구간에서 0행이라는 것을 실측하고 이슈를
올렸는데(#58), 수집 세션이 같은 발견을 이미 #60 으로 올리고 FY2010~2020 추가
수집까지 시작한 상태였다. #58 은 중복으로 닫고 #60 으로 합쳤다. **이슈를 올리기
전에 열린 이슈부터 훑는 것**이 병행 작업의 기본기라는 걸 몸으로 배웠다.

### 3. 계정은 이름으로도, 코드로도 못 믿는다 — 정규화가 필요하다

삼성전자 손익계산서의 당기순이익이 FY2023 까지는 `당기순이익(손실)`,
FY2024 부터 `당기순이익` 이고, `account_id` 도 FY2018 까지 `ifrs_ProfitLoss`,
FY2019 부터 `ifrs-full_ProfitLoss` 로 갈린다 (IFRS taxonomy 개정).
완전 일치 매칭은 연도가 걸치는 순간 조용히 빈다 — **taxonomy 접두사를 벗긴
계정코드 suffix 매칭**을 전처리 규격에 넣었다.

### 4. 검증식에 음성 대조군을 넣는다

as-of join 누출 검사(붙은 값의 접수일 > 거래일 = 0행)만 있으면 검사가 잘못
만들어져도 항상 통과한다. 같은 검사를 **일부러 틀린 방식(결산기 join)에 적용해
0 이 아님을 함께 확인**하는 음성 대조군을 설계에 상시 규칙으로 넣었다
(삼성전자 실측: 접수일 join 0행 vs 결산기 join 86행+).

### 5. 분수 차분 — 정상성과 기억 보존은 절충할 수 있다

수익률(d=1)은 원계열과의 상관이 0.071 까지 떨어지지만, ADF 를 통과하는 최소
차수 d*=0.3 은 상관 0.930 을 지키면서 정상성을 얻었다 (삼성전자 분할 이후 구간
실측). 라이브러리 라이선스가 불명확해서 가중치 재귀식을 직접 구현했다 — 십수 줄.

### 6. 살아 있는 DB 를 재는 노트북은 문구도 데이터에서 나와야 한다

노트북 첫 실행 때 "개발구간 0행"이었는데, 셀이 도는 사이 수집 세션의 백필이
채워져 두 번째 실행에선 220,750행이 됐다. 하드코딩한 결론 문장이 곧바로
거짓말이 됐다 — **결론 문구를 if 로 데이터에서 뽑고, 스냅샷 경고를 붙이는 것**으로
고쳤다.
