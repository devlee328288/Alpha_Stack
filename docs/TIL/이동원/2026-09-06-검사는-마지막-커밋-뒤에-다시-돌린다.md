## 세션을 열고 ruff 를 돌리니 4건이었다

기준은 3건이다 — 전부 강민석 님 파일이고 내가 고치지 않기로 한 것들. 넷째는 내 노트북이었다.
`notebooks/06-검토·발견/09.…ipynb` 의 한 줄이 110자(E501, 상한 100).

왜 어제 못 잡았나. PR #135 는 검증기와 시험을 먼저 올리고, **노트북과 TIL 을 마지막 커밋에
얹었다.** `ruff check .` 은 그 앞에서 돌렸다. 마지막 커밋 뒤에는 다시 돌리지 않았다.
"브랜치 혼자서 ruff 0" 이라는 규칙은 지켰다고 믿었지만, 그 0 은 마지막 커밋 이전의 0 이었다.

**검사는 마지막 커밋 뒤에 한 번 더 돌린다.** 커밋을 얹을 때마다 검사 결과는 무효가 된다.

## ruff 의 "cell 7" 은 코드셀 7번째가 아니었다

ruff 는 `cell 7:2:101` 이라 했다. 코드셀만 세어 7번째를 열었더니 다른 셀이 나왔다.
문자열로 찾으니 **전체 셀 인덱스 6(마크다운 포함) · 코드셀로는 3번째**였다.
ruff 는 마크다운 셀까지 포함해 1부터 센다. 번호를 믿지 말고 내용으로 찾는 편이 빠르다.

## 노트북은 JSON 원문을 문자열로 바꿨다

nbformat 으로 읽어 다시 쓰면 파일 전체가 다시 직렬화된다. 한 줄 고치자고 diff 가 커지는 것을
피하려고 JSON 원문에서 그 줄 하나만 치환했다. 치환 대상이 정확히 1개인지 `assert` 로 확인하고,
결과는 `git diff --stat` 로 쟀다 — **2 insertions · 1 deletion.** JSON 유효성도 다시 읽어 확인했다.
백슬래시가 든 치환이라 heredoc 대신 스크립트 파일로 썼다(heredoc 이 백슬래시를 삼킨다).

## 배운 것

- 검사의 0 은 **마지막 커밋 시점의 0** 이어야 한다. 커밋을 얹었으면 다시 돌린다.
- ruff 의 노트북 셀 번호는 마크다운을 포함한다. 번호보다 문자열 검색이 확실하다.
- PR 을 낸 뒤 발견한 정정은 새 브랜치 → 새 PR. 이번에도 그렇게 냈다.
