# 매일 받은 것을 어떻게 믿는가 — 이미 고쳐져 있던 것과, 정말 빠져 있던 것

> 2026-09-02 · 이동원 · 자동 수집 1차 (시세 최신화)

## 오늘 한 것

9월 1일 시세를 받아 자료를 최신으로 맞추고(시세 2,765행 · 지수 51행), 품질 리포트가
**규모를 남기도록** 고쳤다.

작업 자체는 명령 두 줄이면 끝나는 일이었다. 배운 것은 그 앞뒤에 있었다 —
**내가 문제라고 생각한 것은 이미 고쳐져 있었고, 진짜로 빠진 것은 다른 데 있었다.**

---

## 1. 0건을 어떻게 다루는가 — 내가 늦게 발견한 이미 있는 답

수집 대장을 열었더니 9월 1일이 이렇게 남아 있었다.

```
20260901  rows=0  2026-09-01T16:04:14
```

장 마감이 15:30 인데 16:04 에 요청하니 0행이었다는 뜻이다. 그리고 `fetch_krx.py`
docstring 에는 이렇게 쓰여 있다.

> 이미 받은 날짜는 건너뛴다. 휴장일(0건)도 기록해 두므로 다시 요청하지 않는다.

읽자마자 "그러면 9월 1일은 영원히 못 받겠구나" 하고 결론을 냈다. 0건으로 굳었으니
다시 요청하지 않을 것이고, 그 하루가 통째로 빈다고 본 것이다.

그런데 `krx_store.py` 를 열어 보니 이미 답이 있었다.

```python
# 0건으로 받은 날짜를 "확정 휴장일"로 볼 때까지 기다리는 기간(일).
# 당일 데이터는 장 마감 후에야 올라오므로, 최근 며칠간의 0건은 다시 확인해야 한다.
ZERO_ROW_RETRY_DAYS = 7
```

**휴장일은 영원히 0건이지만, 오늘·어제의 0건은 아직 안 올라온 것일 수 있다.**
그 둘을 시간으로 가른다. 실제로 `--days 5` 를 돌리니 9월 1일을 다시 받아 2,765행이
들어왔다. 손댈 것이 없었다.

**docstring 은 그 함수가 하는 일을 말하지, 시스템 전체가 하는 일을 말하지 않는다.**
"다시 요청하지 않는다"는 사실이었지만 조건이 붙어 있었고, 그 조건은 다른 파일에
있었다. 요약문을 읽고 결론을 내면 두 번에 한 번은 틀린다.

---

## 2. 정말 빠져 있던 것 — 리포트가 규모를 안 남긴다

수집이 제대로 됐는지 확인하려고 `reports/data_quality.json` 의 diff 를 봤다.
바뀐 것은 `generated_at` 과 카운트 다섯 개뿐이었다.

```
-  "count": 4097,     ← 거래일
+  "count": 4102,
```

그런데 **총 행 수가 diff 에 없었다.** 찾아보니 리포트에 아예 없는 값이었다.
`check_data.py` 는 화면에는 `종목 3,677 · 행 9,223,644 · 거래일 4,102` 를 찍지만,
JSON 에는 **검사 항목만** 남기고 있었다.

이게 왜 문제인가는 `.gitignore` 를 보면 드러난다.

```
data/*.db*          ← DB 는 안 올린다 (KRX 이용약관 제11조 ②, 제3자 제공 금지)
reports/quota_usage.json    ← 이것만 예외로 제외
```

즉 **`data_quality.json` 은 커밋하고 DB 는 커밋하지 않는다.** 그러면 DB 를 안 가진
팀원에게 이 리포트는 *"자료가 얼마나 있나"* 를 알 수 있는 **유일한 경로**다.
그런데 그 유일한 경로가 규모를 안 담고 있었다.

내가 이번에 9,220,879 → 9,223,644 를 확인한 것도 결국 **DB 를 직접 열어서**였다.
나는 DB 를 갖고 있으니 됐지만, 팀원 셋은 그럴 수 없다.

그래서 `scale` 칸을 더했다.

```json
"scale": {
  "stock": {"rows": 9223644, "codes": 3677, "trading_days": 4102,
            "first_date": "20100104", "last_date": "20260901"},
  "index": {"rows": 196119, "indices": 51, ...}
}
```

매일 자동으로 받기 시작하면 이 값의 쓸모가 더 커진다. 어제 리포트와 나란히 놓으면
**"몇 행 늘었나"** 를 DB 없이 볼 수 있고, 그게 곧 조용한 실패를 잡는 감시다.

### 좁혀 재고 전체인 척하지 않는다

`check_data.py --index "코스피 200"` 처럼 하나만 볼 수도 있다. 그때 전체 규모를
적어 두면 나중에 읽는 사람이 속는다. 그래서 좁혀 잰 경우에는 `scope` 를 함께 남긴다.
없으면 전체라는 뜻이다.

## 3. 행 수가 맞아도 안심할 수 없다 — 세 각도로 본다

"어제보다 2,765행 늘었으니 됐다"는 **불완전한 검증**이다.

`daily_price` 의 기본키는 `(bas_dd, code)` 이고 저장은 `INSERT OR REPLACE` 다.
같은 날짜·같은 종목을 다시 넣으면 **행 수는 그대로인 채 내용만 바뀐다.**
행 수를 세는 검증은 이걸 원리상 못 잡는다.

그래서 세 각도를 함께 본다. 각각이 **다른 경로로** 빠진 것을 잡는다.

| 각도 | 무엇을 보나 | 이번에 무엇을 확인했나 |
|---|---|---|
| ① 규모 | 행·종목·거래일이 늘었나 | 9,220,879 + 2,765 = 9,223,644 |
| ② 대장 | 무엇을 언제 받았나 | `fetch_log` 에 20260901 · 2,765 |
| ③ 품질 | 값이 말이 되나 | `error` 다섯 항목 전부 0 |

특히 ③ 의 `missing_trading_days` 는 *달력에는 있는데 받은 기록조차 없는 날*을 센다.
①②와 완전히 다른 방향에서 같은 사실을 확인해 주므로, 셋이 함께 통과하는 것에 의미가 있다.

## 4. 시각이 곧 제약이다

이 작업을 시작한 것이 **09:15, 장이 막 열린 시각**이었다. 그래서 9월 2일 시세는
받을 수 없었다 — 아직 존재하지 않기 때문이다. 받아 보니 예상대로 0건이었고,
그 0건은 7일 안에 자동으로 다시 시도된다.

계획을 세울 때 *"9월 1일부터 오늘까지 받는다"* 고 적었는데, 실제로 받을 수 있는 것은
**하루뿐**이었다. 자동 수집을 언제 돌릴지도 여기서 갈린다 — 아침에 돌리면 전날치를,
저녁에 돌리면 당일치를 받는다. 이건 다음 작업(`pipelines.ingest`)에서 정할 일이다.
