## 1. 무엇을 했나

데이터 파트 명세서를 v2.1 로 다시 짰다. 팀장(나)이 읽고도 *"무슨 기능을 구현하는지
확인하기 어렵다"* 고 느낀 원인을 찾아 구조를 바꿨다.

같이 세 가지를 했다. 팀장이 외부에서 받아 온 데이터 파이프라인 가이드(FastAPI +
PostgreSQL + 4에이전트) 30여 항목을 우리 코드와 대조했고, 수업 자료(`learning/`)를
읽어 우리 코드와 맞춰 봤고, 그 과정에서 **새 결함 셋**을 찾았다.

## 2. 왜 했나

문서가 안 읽히면 팀원이 안 읽는다. 안 읽으면 물어보고, 물어보면 내 시간이 나간다.
2주짜리 프로젝트에서 그 손실이 크다.

그리고 가이드를 그대로 따랐으면 **이미 있는 것을 12개 다시 만들 뻔했다.**
수집 대장·재시도 백오프·룩어헤드 방지·무결성 검사가 전부 이미 서 있다.

## 3. 어떻게 했나 — 고른 것과 버린 것

### 문서 구조

읽기 어려운 원인이 문장력이라고 생각했는데 아니었다. **짜임**이었다.

| 무엇이 문제였나 | v2.0 실측 |
|---|---|
| 절 제목이 파일 이름이다 | 기능명세 9절 중 7절이 `수집 대장 (D-02) — collect_log.py · 515줄` 꼴 |
| 조작 경로가 없다 | 411줄 중 실행 명령이 **1줄** |
| 상태가 두 곳에 있어 갈라졌다 | `check_data.py` 가 한 문서엔 "없다", 다른 문서엔 "✅ 닫힘" |
| 굵은 글씨가 너무 많다 | 볼드 150개 / 411줄 = **2.7줄마다 하나** |

절 제목을 **"할 수 있는 일"** 로 바꿨고, 앞에 하루 시나리오 한 장을 넣었고,
상태는 표 하나에만 적기로 했다.

**파일을 쪼개는 안은 버렸다.** `docs/README.md` 가 "폴더 하나 = 그 시점의 완결된 명세"로
규약을 세워 뒀고, 쪼개면 다음 버전에서 `cp -r` 대상이 늘어난다.

### 가이드 대조

가이드 항목을 셋으로 갈랐다 — 이미 있는 것 12, 충돌 10, 없는 것 16.

충돌 넷은 **실측으로 가이드가 틀렸음을 보일 수 있었다.** 이게 이번 작업에서 제일 값졌다.

### FastAPI

처음에 나는 FastAPI 를 넣자고 추천했다. **틀렸다.**
요구사항 v2.0 F-27 이 이미 *"`api/` 가 빈 `__init__.py` 하나다"* 를 근거로
인터랙티브 대시보드를 2차로 내려 뒀는데 그걸 안 읽고 추천했다.

문서를 먼저 읽었어야 했다.

## 4. 어떻게 확인했나

전부 9,209,812행 전수 검사다 (2026-08-31, 읽기 전용 조회).

## 6. 배운 것

**① 문서를 안 읽고 추천했다.** FastAPI 건이 그랬다. 요구사항 F-27 에 답이 이미 있었다.
"내 기억"보다 "저장소에 적힌 것"이 먼저다.

**② 틀린 가이드가 쓸모 있었다.** 가이드의 "거래량 0인데 주가 변동" 규칙은 우리 자료에서
진짜 양성이 0건이라 기각했는데, **거울처럼 뒤집으니** 검증을 건너뛰는 125행이 나왔다.
기각한 규칙에서 얻은 것이다.

**③ 수업이 개념을 주고 우리가 숫자를 갖는 구조다.** 09-finance-ml 이 생존편향을
말하고, 우리에겐 중도 소멸 910종목이 있다. 짝을 지으면 둘 다 강해진다.
반대로 수정주가·거래정지·정리매매·zero-OHLC 는 수업에 한 글자도 없다 —
한국 시장 고유의 함정이라 우리가 직접 재야 했다.

**④ 수업 실습 코드의 버그가 우리 설계 경고가 된다.** 06-data-crawling 의 WICS 수집에서
섹터 코드가 고정돼 420행 전량이 한 섹터로 수집됐고, 기준일이 어긋난 두 표를
outer merge 해 2,765 종목이 5,358행으로 불어났다. **둘 다 에러 없이 조용히 틀린다.**
우리 조인에도 행 수 검증이 필요하다.

**⑤ 숫자에는 잰 날짜를 붙여야 한다.** 다른 문서의 `krx_pg.py 1,428줄` 이 어디서 왔는지
git 이력을 봐도 그런 적이 없었다. 날짜가 없으니 언제 틀렸는지도 모른다.
