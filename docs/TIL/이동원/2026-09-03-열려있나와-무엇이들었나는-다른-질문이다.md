## 오늘 한 일 한 줄

우리 시세 922만 행이 종목코드로만 자기를 알아서 DART 에도 해외 자료에도 못 붙는
문제를, 공공데이터포털에서 **다리**(`코드 ↔ 법인등록번호 ↔ ISIN`)를 받아 이었습니다.

그런데 이 TIL 은 그 구현 이야기가 아닙니다. **어제 제가 쓴 설계가 오늘 세 군데
틀렸다는 것을 알게 된 이야기**입니다.

---

## 1. 실측했다고 믿었는데, 응답을 한 번도 열어 보지 않았다

어제 설계 문서를 쓸 때 저는 분명 실측을 했습니다.

- 키가 통하는지 확인했고
- 엔드포인트가 열려 있는지 여섯 개를 하나씩 확인했고
- 응답이 200 으로 오는지 확인했습니다

문서에 "실측 근거는 전부 확인" 이라고 적었고, 그때는 그게 사실이라고 믿었습니다.

**그런데 응답 본문을 한 번도 열어 보지 않았습니다.**

오늘 구현하려고 실제로 불러 보니 세 군데가 틀려 있었습니다.

| 설계에 적은 것 | 실제 |
|---|---|
| 전 구간 4,102 거래일 (2010~) | **1,636일** (2020-01-02~). 2019 이전은 전부 0건 |
| `corp_profile` 기본키 `(crno, bas_dd)` | 응답에 `basDt` 칸이 **아예 없다** |
| 칸 이름 `estb_dt`·`xchg_lstg_dt`·`empe_cnt`… | `enpEstbDt`·`enpXchgLstgDt`·`enpEmpeCnt`… |

문서가 정교할수록 더 그럴듯하게 틀려 있었습니다. ERD 를 mermaid 로 그리고, 기본키를
왜 그렇게 잡는지 이유까지 썼는데, **그 기본키가 될 칸이 응답에 없었습니다.**

> **"쓸 수 있나" 와 "무엇이 들어 있나" 는 다른 질문이고, 설계는 뒤엣것 위에 서야
> 합니다.** 앞엣것만 재고 설계하면, 재 봤다는 사실이 오히려 확신을 줍니다.

## 2. 가장 무서운 건 물어볼 생각조차 못 한 것이었다

위 셋은 그래도 **틀린 답**입니다. 물어봤는데 잘못 안 것이죠.

더 나빴던 건 이겁니다.

> 🔴 포털의 `basDt` 목록은 그 시점의 상장 목록이 **아니다.**

`basDt=20200102` 로 받은 2,334종 안에 **그날 이후에야 상장된 종목이 33종**
있었습니다. 듀켐바이오(176750)는 첫 시세가 **2024-12-20**, 4년 뒤입니다.

저는 이걸 **의심조차 안 했습니다.** `basDt` 라는 파라미터가 있으니 기준일 목록이겠거니
하고 넘어갔습니다. 이름이 그렇게 붙어 있으니까요.

이걸 잡은 것도 검사를 촘촘히 해서가 아니었습니다. **두 출처를 맞대어 보다가** 우연히
걸렸습니다 — 포털 목록에는 있는데 우리 시세에는 없는 151종이 뭔가 궁금해서 하나씩
첫 거래일을 조회해 봤을 뿐입니다.

이걸 모르고 유니버스를 만들었으면 **아직 상장도 안 된 종목이 섞였을 겁니다.**
그리고 그건 에러가 안 납니다. **성능만 좋아집니다.**

모듈 주석 · 설계 문서 · 테스트 · 검증기 네 곳에 못 박았습니다. 한 곳에만 적으면
그 파일을 안 읽은 사람이 그대로 씁니다.

## 3. 무엇을 통해 보고 있는지가 답을 바꾼다

같은 날 다른 일에서도 똑같은 걸 겪었습니다.

신장환 님이 `rsi()` 를 고쳤는데(PR #81), 제가 그 전 코드로 팀에 자료를 내보낸
뒤였습니다. 값이 달라졌는지 확인해야 했습니다.

**1단계** — 반출한 CSV 와 새 코드 재계산을 대조했습니다.

```
지수 376칸 · 종목 9,404칸 어긋남  (최대차 7.1e-15 / 1.4e-14)
```

재반출해야 하나 싶었습니다. 그런데 최대차가 1~2 ULP 라 이상했습니다.

**2단계** — 옛 코드를 그대로 되살려 **같은 입력으로 메모리 안에서** 새 코드와
비교했습니다.

```
[지수 kospi200] 3,618행 · 가격 결측 0칸
  ✅ 옛 코드 vs 새 코드 : 0칸 어긋남 (최대차 0)
[종목 30종] 82,852행 · adj_close 결측 0칸
  ✅ 옛 코드 vs 새 코드 : 0칸 어긋남
```

**한 칸도 안 달라졌습니다.** 1단계의 차이는 전부 `to_csv` 가 float64 마지막 자리를
못 적는 **표기 문제**였습니다. 새 코드 결과를 CSV 로 적었다 되읽기만 해도 10,042칸이
같은 규모로 재현됐습니다.

> **무엇을 통해 보고 있는지가 답을 바꿉니다.** CSV 라는 창을 거치면 없는 차이가
> 보입니다. 앞으로 값 대조는 parquet 이나 메모리에서 합니다.

## 4. 검증기가 거짓 경보를 내면 사람이 곧 무시한다

검증 스크립트를 처음 돌렸을 때 빨간불이 떴습니다.

```
🔴 영문이 낀 코드 — 시세에 84종 · 신원에 0종
   시세엔 있는데 신원엔 하나도 없다 — 숫자로 거르는 코드가 어딘가 있다
```

제 코드를 의심하고 한참 뒤졌습니다. 그런데 아니었습니다 — **포털의 목록이 우선주와
외국기업을 아예 안 줍니다.** 못 이은 141종이 우선주 120 + 외국기업 21 이었고,
신형우선주 84종은 그 우선주 안에 있었습니다.

**우리가 거른 것**과 **출처가 안 준 것**을 섞으면 없는 버그를 쫓게 됩니다.
검사를 갈랐습니다.

```
우선주    120  ← 포털이 안 준다 (알려진 사실)
외국기업   21  ← 포털이 안 준다 (알려진 사실)
그 밖       0  ← 여기가 커지면 우리 잘못을 의심한다
```

이제 "그 밖" 만 판정에 씁니다. 알려진 사실은 **사실로 보고**하고, 판정은 **우리가
책임질 수 있는 것에만** 겁니다. 그래야 다음에 빨간불이 떴을 때 사람이 봅니다.

## 5. 빠른 것보다 답이 같은 게 먼저다

`known_at` 계산이 행마다 거래일 달력을 묻는데, 그 함수가 4,102개를 매번 선형
스캔하고 있었습니다. 이분탐색으로 바꿨습니다.

```
1,000번 호출
  옛(선형 스캔) : 354.7 ms
  새(이분탐색)  :   0.5 ms   → 689배
```

여기서 멈추지 않고, **옛 구현을 지우지 않고 되살려** 4,206개 날짜(거래일 + 휴장일)를
전부 맞대어 봤습니다. 어긋남 0.

기대값을 새 코드에서 뽑았으면 그건 항등식이라 아무것도 못 잡습니다.

그리고 함정이 하나 더 있었습니다 — 정렬본은 집합에서 파생된 **사본**이라, 집합만
갈아 끼우면 **에러 없이 옛 달력으로 답합니다.** 그리고 테스트가 실제로 그렇게 합니다
(`test_inbox_derive.py` 가 `_SESSION_CACHE` 를 monkeypatch 합니다).

갱신 책임을 갈아 끼우는 쪽에 맡기면 새로 끼우는 자리마다 잊을 수 있어서, **읽는 쪽
한 곳**에서 지키게 했습니다. 그리고 **일부러 망가뜨려** 회귀 테스트가 잡는지
확인했습니다 — 두 개가 정확히 잡았습니다.

## 6. 쓰이지 않는 상수는 어긋나도 아무 일이 안 일어난다

마이그레이션 번호를 배정하는 `NEXT_MIGRATION_VERSION` 이 **코드 어디서도 쓰이지
않았습니다.** `__all__` 에만 들어 있었습니다.

이 상수는 *"다음 갈래가 어느 번호를 선점할지"* 를 알리는 유일한 자리인데, 손으로
적는 값이고 검사가 없으니 **어긋나도 아무 일이 안 일어납니다.** 그러다 두 갈래가
같은 번호를 잡으면, 그 번호를 이미 적용한 DB 는 나중에 들어온 항목을 **영원히
건너뜁니다.** 예외도 경고도 없이요.

검사를 붙였습니다. 문서로만 있는 규칙은 지켜지지 않습니다.
