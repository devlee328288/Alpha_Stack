# 규격이 자기 자료를 격리했다 — 널 비교와 우선순위

> 2026-09-01 · 이동원 · [PR #32](https://github.com/devlee328288/Alpha_Stack/pull/32)

## 오늘 한 것

팀원이 건네주는 파일을 들이기 위한 **반입 규격 5장**을 세우고, 그 규격을 읽는
**해석기**와 규격 자체를 검사하는 **테스트 50개**를 만들었다. `scripts/build_corp_code.py`
로 DART 고유번호 매핑의 막다른 길도 뚫었다.

그런데 오늘 배운 것은 규격의 내용이 아니라 **규격을 어떻게 틀리는가**였다.

---

## 1. 널 비교는 거짓이 아니라 '모름'인데, pandas 는 거짓으로 만든다

지수 규격을 종목 규격 틀에서 그대로 베껴 왔다. 종목 쪽에서 잘 돌던 규칙이다.

```jsonc
{ "id": "high_ge_low", "expr": "high >= low", "severity": "error" }
```

우리 `index_price` 195,864행에 돌려 봤더니 **24,933행(12.73%)이 격리**됐다.

원인은 자료가 아니라 규칙이었다. 지수는 시가·고가·저가가 **아예 안 오는** 것이 있다
— 종가만 공표하는 지수가 실재한다. 그 행에서 `high` 가 NaN 인데, pandas 의 NaN 비교는
`False` 를 돌려준다. **"모른다"가 "어겼다"가 된 것이다.**

```python
>>> pd.Series([None]) >= pd.Series([1.0])
0    False        # ← 이 False 가 곧 '위반'으로 세어진다
```

종목 자료는 OHLC 가 널이 0건이라 이 문제가 안 보였다. 틀에서 베낀 것이 화근이었다.

고침은 간단했다.

```jsonc
{ "expr": "high is null or low is null or high >= low" }
```

**규격에 널 가드를 의무로 못박고, 그것을 검사하는 테스트를 만들었다.** 규칙마다
"필수가 아닌 칸을 비교하면 `is null` 가드가 있어야 한다"를 기계가 본다.

---

## 2. 이미 내보낸 규격에도 같은 급의 결함이 있었다

그 테스트를 만들자마자 **PR #28 로 이미 머지된 `ohlcv_stock.json`** 이 걸렸다.

```jsonc
{ "id": "high_ge_open_close", "expr": "high >= open and high >= close", "severity": "error" }
```

거래정지 종목은 시고저가 0 인데 종가는 잔존가로 양수다. 그러면 `0 >= 종가` 가 거짓이다.
실측하니 **283,468행(3.08%)** 이 격리 대상이었다. 그리고 그 위반이 zero-OHLC 행과
**정확히 일치**하고 그 밖의 위반은 0건이었다 — 원인이 하나뿐이라는 뜻이다.

지수 조사를 하면서 `high == 0` 탈출구를 넣었는데, 정작 먼저 나간 종목 쪽에는 없었다.
**나중에 배운 것을 앞에 소급하지 않으면 앞은 계속 틀린 채로 남는다.**

---

## 3. 검사를 옮기는 방식이 틀려도 숫자는 그럴듯하게 나온다

규칙을 pandas 로 옮길 때 처음에는 문자열 치환을 했다. `and` → `&`, `or` → `|`.

920만 행에 돌렸더니 **892만 행이 위반**으로 나왔다.

```python
"a is null or b == 0"   →   "a.isna() | b == 0"   →   (a.isna() | b) == 0
```

파이썬에서 **비트 연산자가 비교보다 먼저 묶인다.** `|` 가 `==` 를 삼켰다.

무서운 것은 이게 **예외를 안 낸다**는 것이다. 그냥 숫자가 나온다. 892만이라는 숫자가
너무 커서 이상하다고 느꼈을 뿐, 만약 어중간한 숫자였다면 "자료가 나쁘구나" 하고
넘어갔을 것이다.

고침은 문법을 새로 만드는 게 아니라 **파이썬 파서를 빌리는 것**이었다.

```python
ast.parse(expr, mode="eval")     # 우선순위는 파이썬이 이미 옳게 안다
```

규격의 `expr` 은 통째로 유효한 파이썬 식이다. `high is null` 도 `Name('null')` 과의
`is` 비교로 멀쩡히 파싱된다. 그래서 트리를 걸어가며 우리가 허용한 연산만 수행한다.

`eval` 은 쓰지 않았다. 규격 파일은 사람이 손으로 고치는 것이고, 거기 적힌 문자열을
그대로 실행하면 **규격이 코드가 된다.**

---

## 4. 통과만 보고는 검사가 도는지 알 수 없다

규격 검사 34개가 전부 통과했다. 그런데 규칙이 늘 참을 돌려줘도 똑같이 통과한다.
그래서 반대로 **틀린 행을 일부러 만들어 넣는 시험**을 16개 더 만들었다.

거기서 진짜 버그가 나왔다.

```jsonc
{ "expr": "rcept_dt is null or rcept_no is null or starts_with(rcept_no, rcept_dt)" }
```

재무 규격의 이 규칙 — 접수번호 앞 여덟 자리가 접수일인지 보는 검사 — 이 **아예 돌지
않고 있었다.** 내 해석기가 `starts_with` 의 두 번째 인자에 칸을 못 받게 막아 뒀기 때문이다.

규격에는 멀쩡히 적혀 있었다. **검사가 도는 줄 알았지만 안 돌고 있는** 상태였다.
주입 시험이 없었다면 팀원 파일을 받은 뒤에야, 혹은 영영 몰랐을 것이다.

## 5. 미래참조는 도메인마다 다른 얼굴을 한다

| 도메인 | 어디서 새나 |
|---|---|
| 시세 | 마감 시각. 재지 않은 값을 가정으로 쓰면 샌다 |
| 뉴스 | 장중 기사를 그날 시가에 붙이면 샌다. **`time < 08:30` 가드는 00:00 을 통과시킨다** |
| 재무 | 결산기에 값을 붙이면 석 달이 샌다. **열만 가리고 행을 남기면 "제출했다"는 사실이 샌다** |
| 거시 | 참조기간에 값을 붙이면 샌다. **미 CPI 에 한국 지연(32일)을 쓰면 9~11일 샌다** |

특히 뉴스의 00:00 은 오래 못 봤다. "날짜만 있는 자료를 0시로 채운" 행이 `00:00 < 08:30`
이라 **장 시작 전 기사** 자격을 얻는다. 시각을 모르는 기사에 그 자격을 줄 근거가 없다.

재무의 열 가리기도 그렇다. 금액만 가리고 `bsns_year`·`reprt_code` 를 남기면
"이 회사가 보고서를 낼 것이다"라는 **제출 사실 자체**가 읽힌다. 미제출·지연 제출은
관리종목 지정과 직결되는 강한 신호다. 그래서 열을 가리는 대신 **행을 지운다.**
행이 없으면 셀 것도 없다.

---

## 6. 오늘의 원칙

> **자기 규칙에 자기 자료가 걸리면, 자료가 아니라 규칙을 고친다.**

그리고 그것을 사람의 눈이 아니라 **테스트가 보게 한다.** `error` 규칙이 우리 자료를
한 행이라도 격리하면 실패하는 검사를 두었다. 규격을 고칠 때마다 자동으로 돈다.
