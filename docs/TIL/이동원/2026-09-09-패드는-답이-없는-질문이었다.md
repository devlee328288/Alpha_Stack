# 패드는 답이 없는 질문이었다 — 반출과 같은 입력을 주면 된다

> 2026-09-09 (두 번째 세션) · 이동원 · PR #192 후속 · [#186](https://github.com/devlee328288/Alpha_Stack/issues/186)

## 무슨 일이 있었나

오전에 [PR #192](https://github.com/devlee328288/Alpha_Stack/pull/192) 로 *"판정기가 반출의
파생 칸을 따라가게"* 고쳤는데, 칸별 붉은 항목이 0개인데도 **종합 판정만 붉었습니다.** `tail` 로
잘라 보다 두 번 놓쳐서, 이번엔 `python -u` 로 전체 로그(8분 17초)를 파일에 남기고 처음부터
읽었습니다. 2010~2023년은 전부 초록이고 **2024년에 한 행**이 있었습니다.

| | |
|---|---|
| 행 | 2024-03-13 · `036220` 오상헬스케어 |
| 직전 행 | **2016-05-04 · 인포피아** — 상장폐지 종목의 코드를 8년 뒤 신규상장이 다시 썼다 |
| 반출 | 전 구간에서 계산 → `adj_return_1d` +738.57% → `is_adj_suspect = True` |
| 판정기 | "전년도 12월부터" 패드 → 그 전일이 안 보여 NaN |

## 패드를 얼마로 두든 답이 없다

판정기는 연도별로 잘라 비교하는데 `flag_adjustment_quality` 는 종목의 **직전 행**을 봅니다.
그래서 09-09 오전에 "전년도 12월부터 읽는다" 는 한 달 패드를 넣었고, 그것으로 2,658행의 결측
엇갈림이 사라졌습니다. 그런데 한 달이 답인 이유는 없었습니다. 8년짜리 공백이 하나 있었고,
개발구간 전체를 전수로 세니 **1년 넘는 공백은 그 한 건뿐**이었습니다 — 그러니 1년으로 늘려도
다음 재상장에서 또 붉습니다.

질문을 바꿨습니다. *"패드를 얼마나 둘 것인가"* 가 아니라 *"반출은 무엇을 입력으로 받았나."*
반출은 `bas_dd <= dev_end` 전체를 읽어 한 번 판정합니다. 판정기도 **같은 입력을 한 번** 주고,
연도별 루프에서는 그 표를 붙이기만 하게 했습니다. 기업행위 판정(정리매매·신규상장)이 이미 그
모양이었는데, 품질 판정만 루프 안에서 다시 계산하고 있었습니다.

```
기업행위 판정   9,231,938행 · 172초     (전 구간 1회 — 전부터 그랬다)
품질 판정       7,888,945행 ·  26초     (전 구간 1회 — 오늘부터)
연도별 대조     15개 해     · 9~12초/해
종합            8분 17초 → 6분 9초 · 원시 ✅ 표본 ✅ 선정 ✅
```

`cache_size` 도 SQLite 기본값(2MB)에서 반출과 같은 1GB 로 맞췄습니다. 옛 방식이 왜 틀렸는지는
시험으로 남겼습니다 — `test_전년도_12월_패드로는_코드_재사용의_전일이_안_보인다`.

## 그런데 반출 쪽도 틀렸다 — 결정은 이슈로

+738.57% 는 수정주가 오류가 아니라 **다른 회사**입니다. `flag_adjustment_quality` 는 코드가
같으면 같은 종목으로 보고, `is_first_listing` 은 코드의 첫 행만 켜므로 재상장을 못 잡습니다.
학습에서 빠지긴 하니 결과는 무해하지만 뜻이 틀립니다. "공백이 N 거래일 넘으면 첫 행으로
본다" 는 규칙 하나면 되는데, 반출본이 바뀌므로 팀 결정으로 넘겼습니다.

## 반출을 따라가야 하는 곳이 넷이었다

같은 세션에서 하나를 더 찾았습니다. 오전 [PR #189](https://github.com/devlee328288/Alpha_Stack/pull/189)
가 보통주 판정을 이름 규칙에서 HF 칸 `kind_stkcert_tp_nm` 으로 바꾸면서 공급 층
`DAILY_REQUIRED` 에 그 칸을 넣었는데, **오준영 님 실험 로더가 parquet 에서 읽는
`DAILY_COLUMNS` 는 그대로**였습니다. 시험은 전부 초록이었습니다 — 공급 층 시험은 칸이 있는
표를 손으로 만들어 넘기고, 로더에는 시험이 없었으니까요. 오후에 노트북에서 정본 경로로 패널을
만들다가 `종목 후보 입력 열이 없습니다: ['kind_stkcert_tp_nm']` 로 멈춰서 알았습니다.

"파생 칸을 늘리면 따라와야 하는 곳" 을 셋으로 알고 있었습니다 — `COLUMN_NOTES` ·
`EXPORT_DAILY_COLUMNS` · `_attach_export_derived`. **넷째가 모델 파트 로더**였고, 그 셋은 전부
제 파일이라 남의 파일은 목록에 없었습니다. 한 줄 고치고(제가 낸 회귀라 제가 고쳤고 PR 본문에
적었습니다) `DAILY_REQUIRED ⊆ DAILY_COLUMNS` 를 계약 시험으로 못박았습니다.

## 배운 것

- **크기를 정하는 매개변수가 생기면 의심한다.** "얼마나" 를 정해야 하는 자리는 대개 "무엇과
  같게" 로 바꿀 수 있고, 그쪽이 다음 예외에서도 맞다.
- **전체 로그를 처음부터 읽는다.** 두 번 놓친 것은 원인이 어려워서가 아니라 `tail` 때문이었다.
- **따라와야 하는 곳의 목록에 남의 파일도 넣는다.** 내 파일만 세면 시험이 초록인 채로 남의
  경로가 깨진다. 목록 대신 계약 시험을 둔다.
