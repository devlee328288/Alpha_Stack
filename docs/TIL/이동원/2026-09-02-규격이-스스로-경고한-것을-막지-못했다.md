# 규격이 스스로 경고한 것을, 그 규격의 기본키가 막지 못했다

> 2026-09-02 · 이동원 · DART 재무 350종 × FY2021~2025 수집 (마이그레이션 v6)

## 오늘 한 것

DART 재무제표를 350종 × 5개년 받아 `dart_financial` 에 채웠다. **351,565행**이고
3,821콜을 썼다(한도 20,000의 19.1%).

배운 것은 수집 자체가 아니라 **두 번의 잘못된 판단**이었다. 둘 다 예외를 던지지
않았고, 둘 다 시키신 대로 검증하지 않았으면 그대로 넘어갔을 것이다.

---

## 1. 규격이 경고한 바로 그 자리에서 6.4%가 사라졌다

반입 규격 `financial.json` 은 이렇게 적어 두었다.

> ⚠️ 계정을 찾을 때 `account_id` 만 보면 안 되고 이 칸(`sj_div`)을 함께 못박아야 한다 —
> **SCE 에는 같은 `account_id` 가 여러 번 나온다** (삼성전자 2024 연결에서
> `ifrs-full_Equity` 가 7번). 이걸 놓치면 자본총계 402조 대신 자본금 10조가 잡힌다.

경고는 정확했다. 그런데 **그 규격의 `primaryKey` 가 그 경고를 반영하지 않았다.**

```
primaryKey: corp_code · bsns_year · reprt_code · fs_div · sj_div · account_nm · ord
```

이대로 v6 표를 만들고 삼성전자 2023 연결 176줄을 넣었더니 **135줄만 남았다.**
예외도 경고도 없었다 — `INSERT OR REPLACE` 가 조용히 덮어썼다.

자본변동표(SCE)는 "자본금·주식발행초과금·이익잉여금·비지배지분…" **열마다 한 줄씩**
주는데, 그 열을 가리키는 칸이 `account_detail` 뿐이다. 계정명도 `ord` 도
`account_id` 도 전부 같다.

```
'기초자본' ord=4 가 8줄이고 값이 전부 다르다
  연결재무제표 [member]         354,749,604 백만
  지배기업 소유주 지분           345,186,142 백만
  비지배지분                      9,563,462 백만
  이익잉여금                    337,946,407 백만
  자본금                            897,514 백만
```

무엇을 더해야 갈라지는지도 재 봤다.

| 기본키 | 176줄 → | 손실 |
|---|---|---|
| 규격 그대로 | 135 | 41줄 |
| + `account_id` | 135 | 41줄 |
| + `thstrm_nm` | 135 | 41줄 |
| **+ `account_detail`** | **176** | **0** |

전체로는 **351,565행 중 22,436건(6.4%)** 이 사라질 뻔했다.

### 잡은 것은 행 수 대조였다

`sync` 가 "347행 저장" 이라고 보고했는데 DB 를 세니 **264행**이었다.
이 대조를 안 했으면 몰랐다. 재무는 900만 행 시세와 달리 눈으로 훑을 수도 없다.

> **"저장했다고 보고한 수"와 "실제로 있는 수"는 다른 값이다.**
> 같은 함수가 둘 다 세면 그건 검증이 아니라 항등식이다.

### 그리고 기본키의 NULL

`account_detail` 을 기본키에 넣으면서 `NOT NULL DEFAULT ''` 로 못박았다.
SQLite 는 rowid 표의 PRIMARY KEY 안에서 **NULL 을 서로 다른 값으로 본다.**
빈 값을 `None` 으로 두면 같은 계정이 실행할 때마다 한 줄씩 쌓이는데 UNIQUE 위반도
안 난다. 저장하는 쪽도 빈 문자열을 넣도록 맞췄다.

## 2. 조건 두 줄의 순서가 104건을 오분류했다

수집이 끝나고 보니 **실패 104건**이 있었다. 사유가 전부 같았다 —
*"접수일(rcept_dt)이 비어 있다"*. 내가 이렇게 썼기 때문이다.

```python
if not rcept_dt:          # ← 이걸 먼저 봤다
    error
elif out["empty"]:
    empty
```

실제 응답을 열어 보니 이랬다.

```
달바글로벌 2021  empty=True  count=0  rcept_no=''   ← 상장 전
삼성화재  2021  empty=True  count=0  rcept_no=''   ← 오래된 회사인데도 DART 가 안 준다
```

**보고서가 아예 없어서 접수일도 없는 것**이었다. `error` 가 아니라 `empty` 다.
연도별 분포도 그렇게 말하고 있었다 — 2021년 49건, 2022년 42건, 2023년 10건,
2024년 3건으로 **과거로 갈수록 많다.**

분류가 틀리면 대가가 있다. `should_collect` 는 `error` 를 3회까지 다시 시도하고
`empty` 는 확정으로 본다. 그대로 뒀으면 **영원히 없을 자료를 실행할 때마다 208콜씩**
다시 불렀을 것이다.

순서를 바꾸고 104건을 다시 받으니 `error 0 · empty 104` 가 됐다.

> **"없다" 와 "못 받았다" 는 다르다.** 이 구별은 `collect_log` 를 만들 때부터
> 적어 둔 것인데, 정작 쓰는 자리에서 조건 순서 하나로 무너졌다.

## 3. 시험이 진짜로 무언가를 잡는지 확인했다

테스트 12개를 쓰고 나서, **일부러 기본키에서 `account_detail` 을 뺐다.**

```
2 failed, 10 passed     ← 깨뜨렸을 때
12 passed               ← 되돌렸을 때
```

이걸 안 해 봤으면 "통과했으니 됐다" 로 끝났을 것이다. 통과는 시험이 옳다는 증거가
아니다. **틀렸을 때 빨간불이 켜지는 것**이 증거다.

같은 이유로 검증 SQL 도 항등식이 아닌지 확인했다.

```
현재 기본키로 중복        0        ← 통과
account_detail 을 빼면    22,436   ← 이만큼이 사라질 뻔했다
```

두 값이 다르므로 이 검증은 무언가를 실제로 재고 있다.

## 4. 예산을 세는 자리

`dart_data.py` 에는 호출 예산을 세는 코드가 아예 없었다. `krx_data.py` 는 세고
있었고 `common/budget.py` 의 `LIMITS` 에는 `"dart": 20_000` 이 이미 있었다 —
**인프라는 준비돼 있는데 부르는 쪽이 안 쓰고 있었다.**

세는 자리는 `_call` 안이어야 한다. 한 단계 위(`fetch_financials`)에서 세면 재무
본문과 접수일 조회가 한 번으로 뭉뚱그려진다. 실제로는 회사·연도마다 2콜이고,
350종 × 5개년이면 그 차이가 **1,750콜**이다.

넣고 나서 실측하니 삼성전자 2023 하나에 `used` 가 정확히 2 올랐다. 전체 수집은
3,821콜로 끝났고, 이는 사전 추정 3,500과 회사별 연결/별도 재시도분을 더한 값과 맞는다.
