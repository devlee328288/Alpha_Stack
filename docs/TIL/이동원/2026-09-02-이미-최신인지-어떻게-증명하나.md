# 이미 최신인지 어떻게 증명하나 — 세 번 뒤집힌 결론과, 비대칭 대조

> 2026-09-02 · 이동원 · HF 배포본 최신성 확인

## 오늘 한 것

팀원 질문 **"HF 의 KRX 자료는 언제 최신으로 업데이트되나요?"** 에 답했다.
답 자체는 한 줄이다 — **개발구간 상한이 `20210831` 이라 9/1 시세를 받아도 파일이 안 바뀐다.**

문제는 그 한 줄을 **믿을 수 있게 만드는 일**이었다. 8/31 배포 뒤로 `features/` 버그 수정
3건과 액면분할 조정 함수가 들어왔기 때문이다. 짐작으로 "안 바뀌었을 것" 이라고 답하면,
틀렸을 때 팀원이 낡은 자료로 모델을 학습한다.

그래서 전량 대조했고, **결론이 세 번 뒤집혔다.** 배운 것은 전부 그 뒤집힘에 있다.

---

## 1. 결론이 세 번 뒤집혔다

| | 무엇을 보고 | 결론 |
|---|---|---|
| ① | 코드 이력 (버그 수정 3건 · 액면분할) | *"재배포가 필요하겠다"* |
| ② | HF 파일 ↔ 지금 코드 재계산 (95% 가 다름) | *"역시 필요하다"* |
| ③ | **변수를 코드 하나로 좁힌 대조** | **"비트 단위까지 같다. 필요 없다"** |

②에서 멈췄다면 **틀린 답을 확신을 갖고** 내놓았을 것이다. 숫자가 컸기 때문이다 —
`hv_20` 이 53,964행(95.16%), `bb_bandwidth` 가 39,686행(69.99%) 달랐다.

---

## 2. 비대칭 대조 — 재는 방법이 틀리면 표본이 클수록 더 그럴듯해진다

②의 대조는 이런 모양이었다.

| | 거친 길 |
|---|---|
| HF 의 값 | 계산 → **CSV 쓰기** → **CSV 읽기** |
| 내 재계산 | **CSV 읽기** → 계산 |

한쪽만 CSV 를 왕복시켜 놓고, 그 차이를 **코드 탓으로 읽었다.** 게다가 입력 자체도
CSV 왕복본이라 `hv_20`(표준편차)·`bb_bandwidth`(표준편차/평균)처럼 **값을 빼는 계산**은
그 흔들림을 몇십 배로 키웠다. 그래서 하필 그 두 칸이 가장 크게 어긋난 것이다.

숫자를 보면 알 수 있었어야 했다.

```
HF     = 0.0567699457082742      ← 유효숫자 15자리
재계산 = 0.05676994570827423     ← 16자리
```

**자리 하나가 잘린 것**이지 값이 달라진 게 아니었다. 최대 상대차가 8.16e-13 이었는데,
액면분할이 반영됐다면 상대차가 0.98(1/50 분할) 규모여야 한다. **열두 자릿수 차이**다.

> **표본이 크면 검증이 강해 보이지만, 재는 방법이 틀리면 표본이 클수록 틀린 결론이
> 더 단단해 보일 뿐이다.** 9월 1일 TIL 에 *"표본 크기는 순환논법을 못 고친다"* 고 적었는데,
> 하루 만에 같은 함정의 다른 얼굴을 만났다.

### 고친 방법 — 변수를 하나만 남긴다

**같은 입력에 8/31 코드와 지금 코드를 각각 걸었다.** 양쪽 다 같은 CSV 왕복본을 쓰니
표기 오차가 상쇄되고 변수가 코드 하나로 좁혀진다. 결과는 **비트 단위 동일**이었다.

`git archive <커밋> | tarfile.extractall()` 로 옛 트리를 임시 폴더에 풀고, `importlib` 로
그쪽 `export_team_dataset.py` 를 불러 같은 함수를 돌렸다. 트리 경로만 바꾸면
**시점이 다른 코드를 나란히 세울 수 있다.**

## 3. SHA-256 은 한쪽으로만 강한 증거다

원래 계획은 "다시 만들어 SHA 대조" 였다. 그런데 반출본의 큰 벌은 이렇게 뽑는다.

```sql
SELECT * FROM daily_price WHERE bas_dd <= ?     -- ORDER BY 가 없다
```

**행 순서가 보장되지 않는다.** 자료가 한 글자도 안 바뀌어도 순서만 달라지면 SHA 는 달라진다.

| SHA 비교 | 무엇을 알 수 있나 |
|---|---|
| 같다 | 확실히 같다 |
| **다르다** | **아무것도 모른다** — 자료·순서·표기 중 무엇 때문인지 못 가른다 |

우리가 알고 싶은 건 "달라졌는가" 인데, 하필 **다를 때 아무 말도 못 하는** 도구였다.
그래서 정렬한 뒤 **값을 칸별로** 보는 쪽으로 바꿨다.

SHA 를 아주 버리지는 않았다. **내려받은 파일이 MANIFEST 가 기록한 그 파일인지** 확인하는
데는 그대로 썼다. 이건 "같다" 를 확인하는 용도라 SHA 가 정확히 강한 쪽이다.

---

## 4. CSV 는 float 를 온전히 담지 못한다

대조하다 부수적으로 확인한 것이다. 같은 실행에서 나온 HF 자기 파일끼리도 이미 어긋나 있었다.

| 어디 | 무엇 | 크기 |
|---|---|---|
| `index_all_dev.csv` 의 `market_cap` | 388행 | 정확히 **1 ULP**(0.25) · 상대차 1.4e-16 |
| `stocks_sample30_raw_dev.csv` 의 `sector` | 32,226행 | **빈 문자열 → `NaN`** |

`market_cap` 은 1.8경(10¹⁵) 규모라 float64 유효숫자를 넘고, `sector` 는 KOSPI 종목에
소속부가 없어 DB 에 빈 문자열로 들어 있는데 CSV 를 거치면 결측이 된다.

**parquet 은 둘 다 온전했다.** 팀원에게 parquet 을 쓰시라고 안내했다.

> 판정 기준을 코드에 못박았다 — **1 ULP 안쪽이면 표기의 한계, 결측이 엇갈리면 크기와
> 무관하게 자료의 변화.** 값이 생기거나 사라지는 것은 ULP 로 잴 수 없기 때문이다.
> `NaN` 과 `0.0` 이 몇 ULP 떨어져 있다고는 말할 수 없다.

## 5. 확인하는 작업이 대상을 바꾸면 안 된다

`export_team_dataset.py` 를 돌리자 3.8초 만에 멈췄다.

```
index_series() → krx_index.series() → init_db() → migrate_path()
MigrationError: DB 가 코드보다 최신이다 (DB v7 > 코드 v6)
```

**확인만 하려던 작업이 스키마 마이그레이션을 실행하려 했다.** 가드가 막아줘서 다행이었지,
막히지 않았다면 공유 DB 를 건드렸을 것이다.

그래서 검증기는 `mode=ro` URI 로만 연다. 그리고 그 약속을 테스트로 못박았다 —
읽기 전용 연결에 `INSERT` 를 시도해 `OperationalError: readonly` 가 나는지 본다.
**약속을 문서에만 적으면 언젠가 지켜지지 않는다.**

## 6. 못 잰 것

- **HF 배포 시각(17:29:56 KST)이 반출 스크립트 커밋(`5a52655`, 17:34 KST)보다 5분 빠르다.**
  배포에 실제로 쓴 코드가 그 커밋과 글자까지 같은지는 확인할 수 없다. 산출물이 전부
  일치하므로 실질적 차이는 없지만, **못 잰 것은 못 잰 대로 남긴다.**
- `supply/` 를 거치는 재현은 마이그레이션 가드에 막혀 못 했다. 대신 산출물을 DB 와 직접
  대조하는 우회로로 메웠다.

이 두 번째 항목이 개선거리를 하나 남겼다. **`MANIFEST.json` 에 생성 커밋(git sha)이 없다.**
반출 스크립트는 *"같은 커밋에서 다시 돌리면 같은 해시가 나와야 한다"* 고 적어두고 있는데,
정작 어느 커밋이었는지 기록하지 않아 그 약속을 검증할 수 없다. 다음 재배포 때 넣는다.
