# 검사기가 자기 자료를 거부했다 — 종목코드는 숫자가 아니었다

> 2026-09-01 · 이동원 · [#35](https://github.com/devlee328288/Alpha_Stack/pull/35)

## 오늘 한 것

어제 세운 반입 규격을 **실제로 집행하는 엔진**을 만들었다. 이름만 있던 정제기 20종을
구현하고, 시점 파생(`eff_dd`·`known_from`)을 붙이고, `krx_cache.db` 에 표 셋을 얹고
(`user_version` 4→5), 팀원이 읽을 보고서를 내게 했다.

그런데 오늘 배운 것은 그 기계의 구조가 아니라 **그 기계를 어떻게 믿을 것인가**였다.

---

## 1. 팀원 파일로만 시험하면 전부 격리해도 통과한다

정제기를 다 만들고 지저분한 CSV 를 넣어 봤다. 심어 둔 오류 세 개가 다 잡혔고,
거래정지 종목(`-`)은 통과했다. 잘 도는 것 같았다.

그런데 이 시험에는 구멍이 있다. **검사기가 전부 격리해도 똑같이 "잘 잡는다" 로 보인다.**
막는 쪽만 재고 있으면 과하게 막는 것을 영영 모른다.

그래서 반대로 재기로 했다. `daily_price` 에서 12만 행을 무작위로 뽑아 **팀원이 줄 법한
모양으로 내보낸 뒤 다시 들였다.** 우리가 이미 가진 자료를 우리 검사기가 거부한다면,
팀원 자료도 같은 이유로 거부한다는 뜻이다.

```
전체 120,000 · 합격 119,579 (99.649%) · 격리 421 (0.351%)
격리 사유:
  code.pattern    421행
```

421행이 걸렸다.

---

## 2. 종목코드는 여섯 자리 **숫자**가 아니다

값을 열어 봤다.

```
00781K  코리아써키트2우B
18064K  한진칼우
08537M  루트로닉3우C
00341A  쌍용양회4우B
0004Y0  디비금융제14호스팩
0007C0  아크릴
```

전부 실재하는 정상 종목이다. **KRX 가 여섯 자리를 다 써서 영문을 섞기 시작한 것**이다.
신형우선주(2우B·3우C)는 끝자리가, 최근 상장·스팩은 다섯째 자리가 영문이다.

DB 전체로 재 보니 **56,190행(0.61%) · 84종**이 `^[0-9]{6}$` 에 걸리고 있었다.

| 자리 | 영문이 오는가 |
|---|---:|
| 1~4번째 | **0종** |
| 5번째 | 57종 |
| 6번째 | 28종 |

내가 `^[0-9]{6}$` 라고 쓸 때 근거는 *"종목코드는 여섯 자리 숫자"* 라는 상식이었다. 그
상식이 자료와 다르다는 것을 **한 번도 재 보지 않았다.** 어제 규격을 만들면서 920만 행에
규칙을 돌려 봤는데도 못 찾았다 — 그때 잰 것은 `rowRules` 뿐이고 칸 제약(`pattern`)은
집행기가 없어서 못 쟀기 때문이다. **규격은 있었지만 그 규격을 실제로 적용해 본 적이 없었다.**

---

## 3. 얼마나 조일지는 관행과 실측 사이에서 정했다

고치는 방법이 여럿이었다.

| 후보 | 문제 |
|---|---|
| `^[0-9]{6}$` 유지 | 정상 종목 84종이 격리된다 |
| `^[0-9A-Z]{6}$` | `A05930`(대신증권 HTS 표기) 같은 다른 체계도 통과한다 |
| 패턴 제거 | 오타를 반입 단계에서 못 잡는다 |

`pykrx`·`FinanceDataReader` 를 찾아보니 **둘 다 종목코드에 정규식을 아예 걸지 않는다.**
KRX 가 주는 문자열을 그대로 쓴다. 즉 널리 쓰이는 관행은 *"검증하지 않는 것"* 이다.

그런데 반입은 다르다. 우리가 받는 것은 KRX 응답이 아니라 **사람이 손으로 만진 파일**이라
오타가 실제로 들어온다. 그래서 관행만큼 느슨하되 **실측이 보장하는 만큼만** 조였다.

```
^[0-9]{6}$   →   ^[0-9]{4}[0-9A-Z]{2}$
```

앞 네 자리를 숫자로 못 박은 것은 3,677종 **전부** 그랬기 때문이다. 상식이 아니라 실측이다.

되잰 결과 12만 행 격리 **0건**, 영문 코드만 모은 19,297행도 전량 합격.

> 규칙을 정할 때 근거를 두 겹으로 두는 법을 배웠다. **관행**은 얼마나 느슨할지의 상한을 주고,
> **실측**은 얼마나 조일지의 하한을 준다. 둘 중 하나만 있으면 근거가 아니라 취향이다.

---

## 4. 시점이 틀린 파일은 아무 데도 걸리지 않는다

값이 틀린 파일은 규칙이 잡는다. 그런데 **시점이 틀린 파일은 형식도 맞고 규칙도 통과하고
성능만 좋아진다.** 잡을 방법은 우리가 같은 계산을 해서 대조하는 것뿐이다.

뉴스의 `eff_dd`(그 기사를 처음 쓸 수 있는 거래일)를 채워 온 파일을 만들어 봤다.

```
2021-01-04T16:00:00+09:00  장 마감 후 기사   eff_dd=20210104
```

장 마감(15:30) 뒤 기사에 발행일을 그대로 적었다. 그러면 그날 시가에 쓰게 되는데, 그건
정확히 미래참조다. 두 겹으로 잡혔다 — 내 파생 대조와 규격 자체 규칙.

여기서 정한 원칙이 있다. **대조의 방향이 한쪽뿐이다.**

- 채워 온 값이 우리 계산보다 **이르면** → 격리
- **늦으면** → 통과

늦게 잡은 것은 자료를 조금 버릴 뿐이지만 이르게 잡은 것은 성능을 부풀린다. 틀리더라도
**언제나 늦는 쪽으로만** 틀리게 둔다.

---

## 5. 달력을 계산하려 하지 않았다

`eff_dd` 배정에는 거래일 달력이 필요하다. 기존 `trading_days()` 는 주말만 건너뛴다.

개발구간에서 재 봤다. 평일 3,042일 중 실제 거래일은 **2,880일** — **162일(5.3%)이 어긋난다.**
그 162일은 명절·공휴일이고, 하필 실적 발표와 뉴스가 몰리는 연휴 전후다.

```python
next_session("20210101")   # 2021-01-01 은 금요일이지만 신정이라 휴장
# → "20210104"
```

공휴일 규칙을 코드로 짜지 않았다. **`daily_price.bas_dd` 에 있는 날이 거래일이다.** 추정이
아니라 기록이라 틀릴 수가 없다. 4,097일.

그리고 달력 밖을 물으면 `False` 를 주지 않고 **예외를 던지게** 했다. 범위 밖에 False 를
주면 부르는 쪽이 *"휴장이었구나"* 로 읽는데, 휴장인 것과 우리가 아직 안 받은 것은 전혀
다른 사실이다.

## 6. 기록을 얼마나 남길지도 정할 문제였다

*"무엇을 무엇으로 바꿨는지 전부 기록한다"* 는 규칙을 그대로 구현하려니 곧 막혔다. 셀 단위로
다 남기면 팀원이 몇십만 행을 줬을 때 **기록이 원본보다 커진다.** 반대로 건수만 남기면
*"318건 변경"* 이 `zfill6` 때문인지 엉뚱한 절단 때문인지 알 수 없다.

Great Expectations 를 찾아보니 기본 결과 형식(`SUMMARY`)이 정확히 이 문제를 갈라 놓았다.
집계(`unexpected_count` 등)는 **전량**, 실제 값 목록(`partial_unexpected_list`)은 **20건**.
같은 선을 썼다.

적재 표도 남의 답을 빌렸다. 규격 5장의 칸이 겹치지 않아 한 표에 펴면 71칸에 대부분 NULL 이
된다. Airbyte Destinations V2 의 raw table 이 **메타는 칸으로, 행은 JSON 으로** 담고
`_airbyte_meta.changes` 에 *"어느 칸을 왜 고쳤나"* 를 배열로 둔다. 그대로 따랐다.

> 어제는 규격을 처음부터 설계했는데, 오늘은 **이미 답이 있는 문제**를 두 번 만났다.
> 남이 푼 문제인지 먼저 보는 습관이 필요하다.

## 7. 변경으로 세지 말아야 할 것

정제 기록을 붙이고 보니 숫자 칸이 전부 "변경됨"으로 나왔다. `to_int` 가 `"1234"` 를
`1234` 로 만드는 것을 변경으로 센 것이다.

그러면 표본 20칸이 `1234 → 1234` 같은 것으로 다 차서 **정작 봐야 할 `"1.5" → <NA>` 가
밀려난다.** 그릇이 바뀐 것과 값이 바뀐 것을 갈랐다.

그런데 이걸 "숫자로 읽어 비교"로 구현하면 `zfill6` 의 `"5930"` → `"005930"` 이 안 잡힌다
(둘 다 5930 이다). 그래서 **타입 변환기만** 값으로 비교하고 나머지는 표기로 비교한다.

작은 것인데 두 번 틀렸다. 한 번은 `Int64` Series 에 `.map()` 을 걸었더니 내부 float 표현이
넘어와 `1234` 가 `"1234.0"` 으로 읽힌 것(`astype("object")` 를 먼저 걸어 고쳤다).
