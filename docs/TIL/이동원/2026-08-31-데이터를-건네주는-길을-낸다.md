# 데이터를 건네주는 길을 낸다 — 그리고 봉인을 두 번 잠근다

**날짜** 2026-08-31 · **작성** 이동원 · **PR** #28

---

## 오늘 한 일

팀원 셋이 "테스트할 데이터를 달라" 고 했는데 우리 저장소에는 **건네줄 방법 자체가
없었다.** `data/` 에 git 이 추적하는 것은 `universe_core.json` 과 `snapshot_meta.json`
둘뿐이었고, 920만 행짜리 DB 는 커밋할 수도 없다.

그래서 반출 경로를 냈다. 개발구간 데이터를 두 벌로 만들어 HuggingFace private
데이터셋에 올리고, 팀원이 받아 쓰고 자기 것을 올리는 방법까지 문서로 적었다.

---

## 1. CSV 로 주려던 것을 parquet 으로 바꾼 이유 — 재 보고 알았다

처음엔 "CSV 로 만들어 주자" 였다. 재 보니 답이 달랐다.

| 형식 | 크기 | 쓰는 시간 |
|---|---:|---:|
| CSV 무압축 | 656.7 MB | 27초 |
| CSV + gzip | 245.6 MB | 116초 |
| parquet snappy | 176.8 MB | 3.8초 |
| **parquet zstd** | **142.1 MB** | **3.9초** |

**4.6배 작은데 쓰는 것도 7배 빠르다.** gzip 은 크기도 parquet 에 지고 시간은 30배
더 든다. "압축하면 느려지겠지" 라는 직관이 여기선 반대였다 — 열 단위로 저장하는
형식이 같은 종류의 값을 붙여 두기 때문에 압축이 훨씬 잘 먹는다.

다만 팀원이 받자마자 열어 보는 작은 벌은 CSV 로 뒀다. 엑셀로 열리는 것이 중요하다.

---

## 2. 기존 함수를 그대로 못 쓴 이유 — 값은 맞는데 **자리**를 모른다

라벨을 만들려고 `evaluation.horizon.returns_5d_open_gapless` 를 쓰려다 멈췄다.

```python
for i in range(len(rows) - horizon - 1):
    ...
    if ei is None or xi is None or xi - ei != horizon:
        continue          # ← 건너뛴다
    out.append(...)
```

**조건에 안 맞는 행을 `continue` 로 건너뛰고 값만 이어 붙인다.** 분포를 세거나 평균을
낼 때는 이걸로 충분하다. 그런데 표에 라벨 **칸**을 붙이려면 "몇 번째 행의 값인가" 가
필요하다. 건너뛴 자리를 모르면 라벨이 한 칸씩 밀려 붙고 — **에러는 안 난다.**

그래서 같은 규칙으로 계산하되 건너뛰는 대신 `nan` 을 남기는 함수를 따로 썼다.
길이가 입력과 같고 순서가 살아 있다.

### 그리고 내가 새로 짠 것을 믿지 않았다

`verify_labels()` 가 매번 대조한다.

- 내 결과에서 `nan` 을 뺀 나열이 기존 함수 출력과 **완전히 같은가**
- 3분류 분포가 `classify_3` 와 **완전히 같은가**

어긋나면 그 자리에서 멈춘다. 조용히 다른 답을 담아 내보내면 팀원 넷이 그걸 기준으로
몇 주를 쓴다.

**결과가 좋았다.** 지수 라벨 분포가

```
상승 978 · 중립 1111 · 하락 785  →  34.03% / 38.66% / 27.31%
```

로 나왔는데, 이건 지난주 조사에서 **독립적으로 측정해 기록해 둔 값과 소수점까지
같다.** 새로 짠 계산이 맞다는 것을 두 번째 경로로 확인한 셈이다.

## 3. 봉인은 한 곳에서 잠그지 않는다

홀드아웃(`20210901` 이후)이 팀원 손에 한 번이라도 들어가면 "미리 정해 두고 딱 한 번
열어본다" 는 검증 설계가 무너진다. **되돌릴 방법이 없는 종류의 사고다.**

자르는 곳이 여러 군데다 — 지수 조회, 종목 조회, 학습 표, 전량 SQL. 각각이 알아서
잘랐을 거라고 믿으면 언젠가 한 곳이 빠지고, 빠진 그 한 번이 봉인을 연다.

그래서 마지막에 **내보낸 파일을 전부 다시 열어** 가장 늦은 날짜를 확인한다.

```
[검사] 홀드아웃 누수
  ✅ 8개 파일 전수 확인 — 봉인 구간 없음
```

비용을 더 내고 전수로 검사한다. 되돌릴 수 없는 것에는 그럴 값어치가 있다.

**같은 생각을 업로드에도 적용했다.** `create_repo(private=True)` 를 부른 뒤 **서버에
다시 물어** private 인지 확인하고, 아니면 한 파일도 올리지 않고 멈춘다. 이미 있는
레포에 `exist_ok=True` 로 붙으면 그 레포가 public 이어도 그냥 성공하기 때문이다.

## 4. 정상만 담은 표본은 팀원을 속인다

종목 30개를 뽑을 때 시가총액 3층에서 고르게 8개씩 24개를 집고, **일부러**

- 중도 소멸 3개 (상장폐지·합병으로 자료가 끊긴 종목)
- 거래정지 3개 (시·고·저가가 0 인 행을 가진 종목)

를 섞었다. 정상 종목만 보고 짠 코드는 전량 데이터에서 처음 깨지는데, 그때는 이미
그 코드 위에 다른 것들이 쌓여 있다. **예외를 나중에 만나는 것보다 처음에 만나는 편이
싸다.**

대신 이 표본의 라벨 분포(32.56/33.30/34.14)는 전 종목 분포(30.12/37.90/31.98)와
다르다. 예외를 섞었으니 당연하다. 그래서 데이터셋 카드와 가이드에 **"전체 통계로
인용하지 마세요"** 를 굵게 적었다. 숫자만 보고 인용하면 틀린다.

## 5. 토큰 하나에도 관리 비용이 있다

팀 조직을 만들 때 토큰을 어떻게 할지 갈렸다. 공식 문서에 답이 있었다.

> `read`/`write` 토큰은 *"public and private repositories that **you, or an
> organization you're a member of**, own"* 을 커버한다

즉 **classic `write` 토큰 하나면 앞으로 만들 모든 조직·레포에 자동으로 적용된다.**
fine-grained 는 특정 대상에 묶여서 조직을 새로 만들 때마다 손봐야 한다.

팀장은 fine-grained 를 골랐다 — 유출 시 피해 범위가 좁다는 쪽을 택한 것이고, 그
맞교환은 타당하다. 다만 **"다음 조직을 만들면 이 토큰에 그 조직을 추가해야 한다"** 는
사실을 알고 고르는 것과 모르고 겪는 것은 다르다.

## 오늘 배운 것

1. **직관은 재 보기 전까지 가설이다.** "압축하면 느려진다" 가 여기선 반대였다.
2. **값이 맞는 것과 자리가 맞는 것은 다르다.** 리스트를 돌려주는 함수를 표에 붙일
   때는 건너뛴 자리가 어디였는지를 반드시 확인한다.
3. **되돌릴 수 없는 것은 두 번 잠근다.** 각 단계가 잘했을 거라고 믿지 말고 마지막에
   전수로 다시 본다.
4. **표본에 예외를 섞되 그 사실을 크게 적는다.** 섞은 것을 안 적으면 표본 통계가
   전체 통계로 인용된다.
