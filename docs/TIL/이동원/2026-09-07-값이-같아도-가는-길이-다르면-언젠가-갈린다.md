# 값이 같아도 가는 길이 다르면 언젠가 갈린다 — 인라인 중복 넷을 원자 함수로

> 2026-09-07 · 이동원 · 이슈 [#155](https://github.com/devlee328288/Alpha_Stack/issues/155)
> (신장환 님 지적) · 관련 [PR #147](https://github.com/devlee328288/Alpha_Stack/pull/147)

## 어디서 시작했나

신장환 님이 #155 에 댓글을 다셨다.

> PR #147로 만든 `atr_ratio`·`hv_regime`·`obv_slope_20`·`macd_hist_atr`가 이미 두 파일에
> 인라인으로 중복 계산되고 있습니다(값은 안 틀렸습니다, 최대 차이 0.0). … 지금은
> 문제없지만, 나중에 원자 함수 쪽만 고쳐지고 이 인라인 코드는 안 따라가면 두 값이
> 조용히 어긋날 수 있습니다.

두 파일 다 **내가 쓴 것**이다. `features/stock_model_dataset.py` 는 개별종목 트랙,
`features/model_dataset.py` 는 KOSPI200 트랙. 원자 함수가 생기기 전에 손으로 짜 넣은
자리가 그대로 남아 있었다.

## 잰 것 — "값은 안 틀렸다" 를 전수로 확인했다

말만 듣고 고치면 무엇을 고쳤는지 모른다. KOSPI 개발구간 **3,315,889행 · 1,224종목**에서
두 방식을 나란히 계산해 행마다 비교했다.

| 피처 | 최대 절대차 | 인라인만 값 | 원자만 값 | 비교 행 |
|---|---:|---:|---:|---:|
| `atr_ratio` | **0.000e+00** | 0 | 0 | 3,293,310 |
| `obv_slope_20` | **0.000e+00** | 0 | 0 | 3,261,663 |
| `macd_hist_atr` | **0.000e+00** | 0 | 0 | 3,270,182 |
| `hv_regime` | **9.481e-11** | **73** | 0 | 2,984,824 |

세 개는 완전히 같았다. 놀라운 것은 **어긋날 자리가 실제로 있었는데도** 같았다는 것이다 —
`volume_sma == 0` 이 29,645행, `hv baseline == 0` 이 8,171행 있다. 원자 함수는
`np.where(denom > 0, …)` 로 NaN 을 내고, 내 인라인은 `inf` 를 낸 뒤 마지막
`.replace([inf, -inf], nan)` 에서 지워진다. **결과는 같은데 가는 길이 다르다.**

그게 이번의 핵심이다. 언젠가 그 `replace` 를 지우거나 위치를 옮기면, 값이 같던 두 길이
조용히 갈린다. 신장환 님이 말한 위험은 "원자 함수만 고쳐질 때"였는데, 실은 **인라인 쪽
주변을 고칠 때도** 갈린다.

## `hv_regime` 만 달랐다 — 원인은 누적합 차분이다

73행에서 원자 함수가 NaN 을 내고 인라인은 값을 냈다. 수치도 9.5e-11 차이가 났다.

`volatility._rolling_mean` 은 `nancumsum` 의 **누적합 차분**으로 이동평균을 낸다. 250일 창을
3,000행에 굴리면 큰 수에서 큰 수를 빼게 되어 정밀도가 깎이고, baseline 이 0 근처일 때
`np.where(baseline > 0, …)` 판정이 pandas `rolling().mean()` 과 갈린다. 변동성이 거의 0 인
저유동성 종목에서만 나온다.

**실제 쓰이는 자리에서는 영향이 없었다.** `hv_regime` 은 KOSPI200 트랙에만 있고, KOSPI200
3,618행에서 재니 최대 절대차 **2.42e-14** · 결측 엇갈림 **0**. 73행은 개별종목에서만 나오고
개별종목 트랙은 아직 `hv_regime` 을 안 쓴다.

**그래서 지금 고치지 않았다.** 대신 이슈에 적어 두었다 — 나중에 `hv_regime` 을 개별종목으로
가져가면 그때 73행이 갈리고, 그때는 `_rolling_mean` 을 손봐야 한다.

## 고친 것

인라인 여섯 자리를 원자 함수 호출로 바꿨다.

```python
# features/stock_model_dataset.py — 전
ordered["atr_ratio"] = atr_14 / close
ordered["obv_slope_20"] = (obv_values - pd.Series(obv_values).shift(20).to_numpy()) / (
    volume_average * 20.0)

# 후
ordered["atr_ratio"] = atr_ratio(high, low, close, 14)
ordered["obv_slope_20"] = obv_slope_20(close, volume, 20)
```

`features/model_dataset.py` 도 넷을 같은 방식으로 바꿨다.

값이 안 바뀌었는지 **end-to-end 로 다시 쟀다** — 고친 코드로 실제 개별종목 패널을 만들어
오전에 인라인 공식으로 만든 값과 견주니 **172,924행 전부 최대 절대차 0.000e+00 · 결측
엇갈림 0** 이었다.

그리고 회귀 시험 둘을 붙였다. 데이터셋이 내는 값이 원자 함수 출력과 같은지 보는 시험이라,
누군가 다시 손으로 짜 넣으면 거기서 걸린다. `if column not in frame.columns: continue` 같은
방어를 넣었다가 지웠다 — **칸이 사라졌으면 조용히 건너뛰지 않고 실패해야** 시험이 실제로
재는 것이 된다.

## 배운 것

- **"값이 같다" 는 중복을 남겨도 된다는 뜻이 아니다.** 같은 값이어도 **가는 길이 다르면**
  한쪽 주변을 고칠 때 갈린다. `inf → replace` 와 `np.where(denom > 0)` 는 오늘은 같은 답을
  내지만 같은 규약이 아니다.
- **팀원의 지적을 실측으로 확인하면 그가 못 본 것까지 나온다.** "최대 차이 0.0" 이라고
  하셨는데 `hv_regime` 은 73행이 달랐다. 다만 그 73행이 **실제 쓰이는 자리에는 없어서**
  결론은 같았다 — 확인이 결론을 뒤집지 않아도 확인은 값을 한다.
- **영향 범위는 그 코드가 실제로 도는 자리에서 센다.** 개별종목 298만 행에서 73행이라도,
  KOSPI200 3,618행에서 0이면 지금 고칠 일이 아니다. 오늘 아침 #155 에서 배운 것과 같은
  교훈이 하루에 두 번 나왔다.
