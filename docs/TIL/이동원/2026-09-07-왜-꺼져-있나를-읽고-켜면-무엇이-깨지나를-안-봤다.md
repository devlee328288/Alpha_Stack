# 왜 꺼져 있나를 읽고, 켜면 무엇이 깨지나를 안 봤다

2026-09-07 · 업종 스냅샷 KOSDAQ 반입 (PR #145 · 이슈 #144)

## 무슨 일

팀장님이 KOSDAQ 업종분류 현황 18장을 받아 주셔서 반입했다. 잘 들어왔다 — 36장 40,874행,
격리 0, 종가·시가총액·시장 전량 대조 일치. 그런데 검증기 §4가 "KOSDAQ 업종지수가
`index_price` 에 0종" 이라고 했다. 조인할 지수가 없으니 받아야겠다고 생각했다.

수집기 주석을 읽었다.

```python
# ⚠️ 왜 KOSDAQ 을 기본에서 뺐나 — 하루 한도 때문이다. KRX 는 인증키당 1일 10,000회를
#    허용한다(이용약관 제8조 ④). 16년 백필은 시장당 4,343콜이라 …
DEFAULT_MARKETS: Tuple[str, ...] = ("KOSPI",)
```

한도를 확인했다. 오늘 KRX 콜은 9회, 한도는 10,000. 4,343콜이면 여유가 있다.
**근거를 확인했다고 생각하고 켰다.**

45분 뒤, 검증기 §4가 이번엔 **KOSPI 업종이 통째로 "지수 없음"** 이라고 했다.

## 무엇이 깨졌나

같은 파일 **위쪽 표**에 이렇게 적혀 있었다.

```
| 키 | (날짜, 종목코드) | (날짜, 지수명) |
```

`index_price` 의 기본키에 **시장이 없다.** 그런데 KOSPI 와 KOSDAQ 은 `건설`·`금속`·
`금융`·`화학`·`전기전자` 같은 **같은 이름의 업종지수를 각각** 가진다. 그래서
`INSERT OR REPLACE` 가 같은 이름의 KOSPI 행을 조용히 덮어썼다.

**KOSPI 업종지수 17종 × 40,324행**이 KOSDAQ 값으로 바뀌었다. 2,372거래일치다.

## 배운 것 셋

### 1. 끄는 이유가 적혀 있다고 그것이 유일한 이유는 아니다

주석은 "하루 한도 때문" 이라고 했고, 그건 **사실이었다.** 거짓말이 아니었다. 다만
그것만이 아니었을 뿐이다. 주석을 쓴 사람은 그때 기본키 문제를 몰랐거나, 알았어도
적을 이유가 없었다.

**"왜 꺼져 있나" 는 "켜도 되나" 에 답하지 않는다.** 답하는 것은 스키마다.
켜기 전에 봤어야 할 것은 주석이 아니라 `PRIMARY KEY` 한 줄이었다.

### 2. 행 수는 덮어쓰기를 못 잡는다 — 이번엔 **늘어서** 못 알아챘다

재무 기본키에서 `account_detail` 을 빼면 자본변동표 6.4%가 사라지는 것을 이미 겪었다.
그때는 **행이 줄어서** 알았다. 그래서 "행 수를 세면 된다" 고 배웠다고 생각했다.

이번엔 반대였다.

```
196,272  →  244,108      (+47,836)
```

**늘었다.** KOSDAQ 이 89,753행 들어오고 KOSPI 가 40,324행 덮여서, 합계는 커졌다.
개수만 보면 "잘 받아졌네" 다. 실제로 수집기는 정상 종료했고 오류도 0이었다.

드러난 것은 **축별로 세고 나서**였다.

```
KOSPI  51종 196,272행  →  49종 155,868행
하루 종수 48  →  31
```

행 수는 스칼라라서, 두 방향으로 동시에 움직이면 서로를 가린다. **키를 이루는 축마다
세야** 한 쪽이 줄어든 것이 보인다.

### 3. 막는 자리는 "쓰기 전" 이다

우리 반출 경로에는 게이트가 있다. 검사기 네 개가 돌고, 붉으면 안 나간다. 그런데
이번 사고는 **게이트가 잡을 수 없었다** — 이미 덮어쓴 뒤에 도는 검사는 잃은 값을
되살리지 못한다. `verify_sector.py` 는 실제로 붉어졌지만, 그때는 40,324행이 이미 없었다.

그래서 이번에는 검사가 아니라 **문**을 세웠다. `sync()` 진입부에서 KOSPI 아닌 시장을
요청받으면 **받기 전에** 예외를 던진다. 경고가 아니라 차단인 이유는, 이 사고가 겉으로
성공처럼 보이기 때문이다.

문구에는 **푸는 방법까지** 적었다.

```
할 일: 기본키에 index_class 를 넣는 마이그레이션(v13)을 먼저 하고,
       그다음 이 파일의 SAFE_MARKETS 에 시장을 더한다.
```

환경 가드를 막다른 길로 두지 않는다는 규약대로다. 막기만 하고 길을 안 알려 주면,
다음 사람은 가드를 지우고 같은 사고를 낸다.

## 덤 — 복구하면서 하나 더

`collect_log` 를 지우고 재수집했더니 **전부 건너뛰었다.** 1,733일을 "받았다" 고
찍었는데 DB 는 한 줄도 안 변했다.

건너뛰기 판정은 `collect_log` 가 아니라 **`index_fetch_log`**(옛 대장)를 본다
(`krx_index.fetched_dates`). 대장이 둘이고, 지운 쪽은 판정에 안 쓰이는 쪽이었다.

**"지웠으니 다시 받겠지" 도 확인해야 하는 가정이다.** 재수집이 정말 새 값을 넣었는지는
행 수가 아니라 **목표값과의 대조**로 봐야 했다. 두 번째 시도에서 둘 다 지우고서야
196,272행으로 정확히 돌아왔다.

## 남은 것

- `index_price` 기본키에 `index_class` 를 넣는 마이그레이션 **v13** → 이슈 #144
- 그 전까지 KOSDAQ 업종지수는 받지 않는다. **쓰는 곳이 아직 없어 급하지 않다** —
  2안(업종 상위 10)은 KOSPI 만 쓰고, KOSPI200 트랙은 업종을 안 쓴다.

## 참고

- 시장 데이터 스키마의 표준은 시계열 키에 시각·종목과 함께 **거래소(venue)** 를 넣는다
  ([QuestDB](https://questdb.com/glossary/market-data-time-series-schema/))
- 표를 시장별로 쪼개는 방식도 있지만 근거는 *"데이터 볼륨이 클 때"* 다. `index_price` 는
  24만행이라 해당하지 않는다. 필요하면 시장별 **뷰**를 얹는 쪽이 조인을 단순하게 둔다
