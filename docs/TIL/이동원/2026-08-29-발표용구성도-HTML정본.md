## 1. 무엇을 했나

킥오프(9/1) 발표용 구성도 2장을 만들었다 — **시스템 아키텍처**(최종 목표 구성
전체)와 **AI 에이전트 구성**(제안 · 킥오프 안건). 둘 다 HTML 을 정본으로 두고
`scripts/render_html.mjs` 로 PNG 를 굽는다. 아키텍처 문서를 v1.2 로 올렸다.

## 2. 왜 했나

두 가지가 겹쳤다.

**① 기존 `.mmd` 3장으로는 못 그리는 것이 있었다.** 카드 안에 부제·배지·수치를 넣는
자유 배치다. mermaid 는 "무엇이 무엇으로 흐르나" 에는 맞지만 **설명을 그림 안에
담지 못한다.** 발표에서는 그림 하나로 설명이 끝나야 한다.

**② 코드가 그림보다 앞서 나가 있었다.** v1.1 을 쓴 날 PR 두 건이 더 들어왔고, 특히
[PR #10](2026-08-29-시세공급-문을-둘로.md)은 `supply/` 를 **문 하나에서 문 둘로**
바꿨다. v1.1 그림만 보면 정문이 정리매매 판정까지 하는 것처럼 읽히는데 **정반대다.**

## 3. 어떻게 했나 — 고른 것과 버린 것

### HTML 을 정본으로 둔다 (PNG 만 커밋하지 않는다)

PNG 만 커밋하면 이력에 바이너리 덩어리만 쌓이고 **무엇이 달라졌는지 아무도 못
읽는다.** `.mmd` 를 정본으로 두는 이유와 같다. HTML 이면 `git diff` 에 문구 하나까지
그대로 보인다.

```
node scripts/render_html.mjs docs/아키텍처/version1.2/시스템아키텍처.html
```

### puppeteer 를 직접 의존하지 않는다

그림 하나 굽자고 Chrome 을 또 내려받게 만들 이유가 없다. 이미 깔려 있는
`@mermaid-js/mermaid-cli` 것을 빌려 쓴다 — 그쪽은 이미 이 저장소의 `.mmd` 를 굽고 있다.

둘 다 없으면 **무엇을 해야 하는지까지 출력하고** 멈춘다. 예외만 던지면 받는 사람이
막다른 길에 선다.

### 실선과 점선을 가른다 — 그림이 사실보다 앞서지 않게

v1.1 그림은 전부 같은 선이라 보는 사람이 `features/` · `models/` 가 이미 있는 줄
안다. **실제로는 `__init__.py` 뿐이다**(각각 35줄 · 34줄).

v1.2 는 **실선 = 서 있는 것, 점선 = 계획**으로 갈랐다. 줄 수는 실측으로 세었다.

| | |
|---|---|
| 서 있는 것 | common 2,668 · ingest 7,546 · supply 591 · evaluation 848 · timeseries 2,063 · scripts 3,107 · tests 4,016 |
| 뼈대만 | api 28 · features 35 · models 34 |
| 비어 있음 | pipelines |
| 없음 | CI · Streamlit 코드 |

전체 구성을 그리는 이유는 *"추후 바뀌더라도 이렇게 계획하고 있다"* 를 보이기
위해서다. **다만 계획을 실선으로 그리면 그건 계획이 아니라 거짓말이 된다.**

### 에이전트 그림은 "제안" 이라고 못 박았다

이 그림의 **어느 칸도 구현돼 있지 않다.** 제목 옆 배지 · 머리말 경고 · 점선 테두리
셋으로 그 사실을 밝혔다.

남의 구성을 베끼지 않으려고 **우리 자료와 우리 제약**으로 채웠다 — 큐레이터가
`as_of` 를 정하고 supply 정문으로만 자료를 꺼내는 것, 검증자가 출처 행을 못 대는
문장을 버리는 것, 호출 예산을 `call_budget` 표로 세는 것.

정직하게 함께 적은 것 셋:

- 이건 1차 목표가 아니다 — 1차가 먼저 서지 않으면 근거로 댈 숫자 자체가 없다
- 가장 큰 위험은 **"그럴듯한 거짓말"** 이다 — 그래서 검증자를 통과 조건으로 둔다
- 뉴스 본문 저장은 네이버 약관 7.3 ③ 이 걸린다. **법적 판단이라 단독 결론 금지**

## 4. 어떻게 확인했나

구운 PNG 를 눈으로 봤고, 두 군데가 실제로 깨져 있었다.

**⚠️ 한글은 `word-break` 기본값이면 단어 한가운데서 끊긴다.** 처음 구운 그림에
"않는 / 다" · "열 / 거" · "시 연 안정성" 이 나왔다. `word-break: keep-all` 로 고쳤다.

**⚠️ `.agent b { display: block }` 이 `<i>` 안에 강조로 넣은 `<b>` 까지 블록으로
만들어** 문장이 세 토막으로 갈라졌다("질문을 받고 / `as_of` 를 정한다 / . 자료는…").
자식 선택자로 좁혀 고쳤다.

### 정정된 것

v1.1 그림이 `supply/` 를 **228줄**로 적었다. PR #10 이후 **591줄**이고 테스트도
16개에서 **48개**로 늘었다.

## 5. 막힌 것 · 남은 것

- 역할별 파이프라인 · 일정 간트(`.mmd` 2장)는 v1.1 그대로다. **킥오프에서 역할이
  확정되면 그때 고친다** — 지금 고치면 확정 전 추측을 그림으로 굳히는 일이다.
- CI 가 없다(`.github/workflows` 없음). 그림의 자동화 띠에 "배치는 계획" 이라고 적었다.
- PNG 가 장당 약 0.5MB 다. 고칠 때마다 이력에 쌓인다. `.mmd` · `.png` 관례를 그대로
  따랐지만, 그림을 자주 고치게 되면 그때 다시 볼 일이다.

## 6. 배운 것

**그림은 문서보다 빨리 낡는다.** 코드는 PR 마다 바뀌는데 그림은 누가 열어보기
전까지 아무도 틀린 줄 모른다. 그래서 그림도 **정본을 텍스트로 두고 diff 가 읽히게**
해야 한다. PNG 만 있으면 "언제부터 틀렸는지" 를 영영 못 찾는다.

**같은 선으로 그리면 없는 것도 있는 것이 된다.** 발표 자료에서 가장 하기 쉬운
거짓말이 이것이다. 실선/점선을 가르는 데 든 비용은 줄 수를 세는 5분이었다.

**한글 웹 렌더링은 반드시 눈으로 확인한다.** `word-break: keep-all` 은 알고 있으면
한 줄이지만, 모르면 구운 그림에서만 드러난다. 코드 리뷰로는 절대 안 잡힌다.
