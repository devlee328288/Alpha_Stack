# 주석이 얇다는 착시와 병렬의 잔재 — 재는 방법이 계획을 바꾼 날

## 오늘 한 것

병렬로 돌리던 작업 세션들을 하나로 합치면서, 병렬이 남긴 잔재를 걷어냈다.

- 머지가 끝난 워크트리 1곳과 로컬 브랜치 13개를 정리했다
- **ruff 위반 30건을 0건으로** — 병렬 세션 두 개가 서로 "상대 세션 노트북"이라며
  미뤄 둔 21건 + 9건이었다. 세션이 하나가 되니 전부 내 몫이 됐다
- 코드 주석을 보강하려다가, **측정을 다시 해 보니 보강할 필요가 없다는 결론**을 얻었다

## 1. 주석이 얇다는 착시 — `#` 만 세면 독스트링을 놓친다

"주석이 약하니 보강하자"는 계획으로 시작했다. 근거는 이 측정이었다.

```bash
grep -cE '^\s*#' ingest/inbox/rules.py   # → 11줄 / 369줄 = 3%
```

3% 면 심각하다. 그런데 파일을 **직접 열어 보니** 모듈 머리에 파서를 왜 쓰는지,
`eval` 을 왜 안 쓰는지, 연산자 우선순위 버그로 892만 행이 위반으로 나왔던 사연까지
전부 적혀 있었다. 얇기는커녕 수업 자료 수준이었다.

원인은 재는 방법이다. **파이썬의 설명은 `#` 주석과 독스트링 두 곳에 사는데,
`grep '^#'` 은 앞의 것만 센다.** 이 저장소는 설명 대부분을 독스트링에 두는
스타일이라, 잘 문서화된 파일일수록 `#` 카운트는 오히려 낮게 나온다.

`tokenize` 로 주석 + 독스트링을 함께 세는 측정으로 바꾸니 그림이 뒤집혔다.

| 측정 | `ingest/inbox/rules.py` | 결론 |
|---|---|---|
| `#` 줄만 | 3.0% | "심각하게 얇다" |
| 주석 + 독스트링 | **24.3%** | 상위권 |

전 저장소를 다시 재니 내 파트·팀원 파트·common 모두 30~90% 였고, 가장 얇게 나온
파일 7개를 직접 열어도 전부 '왜'가 적혀 있었다. **코드 보강 계획을 접고**, 쉽고
자세한 해설은 새로 만드는 `docs/핵심코드/` 문서에 담기로 했다.

> 어제 "내 메모의 값도 실측으로 재확인한다"를 배웠는데, 오늘은 **실측 자체도
> 재는 방법이 틀리면 착시를 만든다**를 배웠다. 측정이 틀리면 계획이 통째로 틀린다.
> 숫자가 이상하게 크거나 작으면 계산을 의심하기 전에 **측정 도구가 무엇을 못 보는지**부터
> 의심할 것.

## 2. 병렬의 잔재 — 서로 미룬 것은 아무도 안 한다

ruff 30건의 분포가 정직하게 말해 준다.

- 세션 A 의 인수인계: "21건은 상대 세션 노트북이다"
- 세션 B 의 인수인계: "9건은 병행 세션 노트북이다. 내 파일은 0건"

둘 다 맞는 말인데, 합치면 **30건 전부 주인이 없다.** 문서 버전도 같은 꼴이 났다 —
각 세션이 자기가 만진 부분만 버전업해서 데이터파트에 1~3파일짜리 부분 버전
(v2.2·v2.3·v2.4)이 쌓였고, 인덱스는 그 사이 낡았다.

병렬의 비용은 충돌만이 아니다. **"내 것 아님"이 성립하는 구조 자체가 비용이다.**
단일 세션으로 바꾸면 모든 위반이 즉시 내 몫이 된다. 오늘부로 워크트리 없이
`feat/*` 브랜치 하나씩만 쓴다.

## 3. 노트북의 절대 경로는 재현성 버그다

ruff E501(긴 줄) 을 고치다 보니 긴 줄의 절반이 이런 모양이었다.

```
%run ../../scripts/_probe_fdr_adjust.py --db c:/Users/kik32/workspace/.../krx_cache.db
```

`c:/Users/kik32/...` 는 **내 PC 에만 있는 경로다.** 팀원이 이 노트북을 받아
실행하면 그 자리에서 죽는다. 줄이 길다는 지적을 따라가니 이식성 버그가 나왔다 —
린트 규칙은 가끔 이렇게 다른 문제를 딸려 올린다.

상대 경로로 바꾸면서 한 가지를 실측했다. **IPython 의 `%run` 은 `$변수` 를
확장하는가?** 문서 기억에 의존하지 않고 돌려 봤다.

```python
DB = "../../data/krx_cache.db"
%run script.py --db $DB        # → sys.argv == ['--db', '../../data/krx_cache.db'] ✅
```

확장된다. 그래서 176자짜리 `%run` 줄을 변수 선언 + 짧은 명령으로 갈랐다.
실행 결과(출력 셀)는 건드리지 않았다 — 고친 것은 표기와 경로뿐이고, 의미가
같음은 치환 전후를 눈으로 대조해 확인했다.

## 오늘의 한 줄

**측정 도구가 무엇을 못 보는지 모르면, 실측도 착시가 된다.**

`#` 카운트는 독스트링을 못 보고, 행 수 검증은 덮어쓰기를 못 보고, SHA 는 순서와
내용을 못 가른다. 도구마다 맹점이 있고, 결론을 내리기 전에 그 맹점이 지금 결론을
만들고 있지 않은지 물어야 한다.
