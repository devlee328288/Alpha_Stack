01 — 문제

맞히는 것보다 어려운 건, 맞혔다고 말해도 되는지 아는 것

개별 기술적 지표(RSI·MACD 등)를 따로 쓰기보다 여러 지표를 머신러닝으로 종합하면 예측력이 실제로 오르는가 — 이것이 출발점입니다. 그런데 이 질문에 답하려다 보면 더 어려운 문제를 먼저 만납니다.

주가 예측은 “몇 퍼센트를 맞혔는가”보다 “어떻게 검증했는가”가 결론을 좌우합니다. 시계열에 무작위 K-겹 교차검증을 쓰면 미래 정보가 학습에 새어 들어가 정확도가 부풀려지고, 기준선 없이 정확도 52%를 보면 그게 성과인지 알 수 없습니다. 올해 데이터로 배워서 작년을 맞히는 모델은 백테스트에서만 훌륭합니다.

지표를 합치면 나아지는가

RSI·MACD·이동평균을 하나씩 쓸 때와 모델로 종합할 때를 같은 조건에서 비교합니다.

기준선을 이기는가

항상 매수·무작위·전일 방향 지속 3종을 항상 함께 냅니다. 기준선 없는 정확도는 숫자일 뿐입니다.

비용을 내고도 남는가

수수료와 세금을 넣습니다. 거래비용을 빼고 나면 사라지는 전략이 대부분입니다.

02 — 착수 자산

데이터 수집·저장·화면은 이미 돌아갑니다

제가 개인 프로젝트로 개발해 온 data-service 를 팀 저장소로 가져갑니다. 국내 투자 정보를 모아 두는 FastAPI 서비스이고, 지금도 계속 개발 중입니다. 목업이 아니라 화면에 뜨는 시세·거래대금·시가총액이 전부 KRX 가 준 실제 값입니다.

03 — 이관

필요한 것만 가져가서, 팀 저장소에서 다시 짭니다

개인 저장소를 그대로 쓰지 않습니다. 새 팀 저장소를 만들고 필요한 부분만 옮겨 리팩터링합니다. 제 커밋 이력과 팀의 커밋 이력을 섞지 않기 위해서이고, 여러분의 기여가 팀 저장소에 각자 이름으로 남게 하기 위해서입니다.

가져갑니다

약 15,900줄

  • 수집 클라이언트 9종 — 학습 데이터 확보

  • FastAPI 서비스 골격 + 화면 10개 — 대시보드 뼈대
  • 검증 체계(invoke check) · 결정 기록 13건
버립니다

약 11,200줄

  • 기업 리서치 리포트 자동 생성 기능 (24파일)
  • 1차 주제(지표 기반 예측)와 무관합니다

결과적으로 팀이 다루는 코드는 약 27,000줄에서 약 15,900줄로 줄어듭니다. 읽어야 할 양을 먼저 줄이는 것이 리팩터링의 첫 단계입니다.

04 — 범위

필수는 2주 안에 끝내고, 선택은 함께 고릅니다

필수 범위 — 반드시 닫습니다

항목완료 기준
①기술적 지표 기반 등락 방향 예측 모델예측 결과가 재현된다

⑤성과 검증 엔진 분리 (MDD·Sharpe·승률·거래비용)2·3차가 그대로 가져다 쓴다

항목언제 넣나

⑧유니버스 확장 — 약 350종목 횡단면 랭킹 예측학습 시간이 감당될 때

⑩종목별 하이퍼파라미터 자동 탐색과적합 관리가 가능할 때
⑪저장계층 Postgres 전환 마무리 (9단계 중 6단계 완료)인프라에 관심 있는 분이 있을 때
⑫ 여러분이 제안하는 기능 — 주제 안에 있고 설명할 수 있으면 채택 킥오프에서 협의

먼저 풀어야 할 것 — 숨기지 않고 적습니다

저장소를 실측해 보니 착수 전에 결정해야 할 것이 셋 남아 있습니다. 전부 첫 주에 처리 가능하고, 각각이 담당 하나의 첫 과제가 됩니다.

데이터

학습 기간이 얇습니다

지금 쌓인 시세는 297거래일(2025.06~2026.08)입니다. 학습·검증·홀드아웃으로 나누기에 넉넉하지 않아 과거 구간 백필이 먼저입니다. 수집 스크립트는 이미 있어서 돌리는 일에 가깝습니다.

인프라

학습을 어디서 돌릴지

배포처(Vercel)는 함수 용량 한도가 있어 PyTorch 급 라이브러리를 실을 수 없습니다. 학습은 로컬에서 돌리고 결과물만 서빙하는 구조로 가릅니다. 어떤 형식으로 저장할지가 첫 주 결정입니다.

설계

피처·레이블을 담을 자리

지금 DB 표는 시세용이라 피처 테이블과 레이블 테이블이 없습니다. 지표는 화면에 쓰고 버리는 일회성으로 계산됩니다. 학습용 데이터셋 스키마를 새로 설계해야 합니다.

05 — 합류

기능을 얹는 건 환영입니다. 조건은 하나입니다

이 프로젝트는 지금도 진행 중이고, 여러분이 자기 기능을 추가해도 아무 문제가 없습니다. 오히려 그러라고 선택 범위 ⑫를 열어 두었습니다. 하고 싶은 게 있으면 킥오프에서 말씀하시면 됩니다.

대신 한 가지가 필요합니다 — 지금까지의 코드를 이해하는 것. 기존 구조를 모른 채 옆에 새 폴더를 파면 같은 일을 하는 코드가 두 벌이 되고, 2·3차에서 그 둘을 합치는 비용을 우리가 냅니다. 붙일 자리를 알고 붙이면 그럴 일이 없습니다.

어렵게 들릴 수 있지만 도구는 준비되어 있습니다 — 결정 기록(ADR) 13건이 “왜 그렇게 했는가”를 전부 적어 두었고, README 가 화면·API·폴더 구조를 전수로 설명하며, docker compose up -d 한 줄이면 30초 만에 로컬에서 돕니다. 첫 이틀을 다 같이 읽는 시간으로 잡아 두었습니다.

주담당과 교차 검수

아래는 “무엇을 했는지 말할 수 있게” 나눈 것이지 벽을 세운 것이 아닙니다. 각자 자기 영역을 끌고 가되 바로 옆 담당의 산출물을 한 번 더 확인합니다. 제가 백엔드로 참여할 때도 CRUD 를 맡으면서 배포·연동 쪽을 같이 봐 왔고, 그 방식이 잘 통했습니다.

06 — 로드맵

왜 팀 이름이 ‘적층’인가

6주 동안 프로젝트를 세 번 합니다. 그리고 세 주제가 전부 “개발 및 성과 검증”으로 끝납니다. 매번 새로 만드는 것은 앞쪽이고, 검증하는 방법은 같습니다.

그래서 1차에서 검증 엔진을 재사용 가능하게 분리하면 2·3차는 그 위에 얹는 일이 되고, 노트북 셀에 흩어 놓으면 매번 처음부터 다시 짭니다. 이 판단 하나가 6주 전체의 비용을 결정합니다.

그래서 간단한 프로젝트가 아닙니다. 사전 작업분이 있어 시작은 빠르지만, 1차에서 대충 만든 것은 2·3차 내내 우리를 따라다닙니다. 대신 여러분이 1차에 만든 코드도 6주 내내 살아남습니다.

08 — 모집

이런 분과 함께하고 싶습니다

설명할 수 있는 분

바이브 코딩을 하셔도 좋습니다. 도구를 쓰는 건 자유입니다. 다만 자기가 만든 기능은 설명할 수 있어야 하고, 문서화와 버전 관리는 함께 합니다.

남의 코드를 고칠 수 있는 분

이미 진행된 코드를 팀 프로젝트로 리팩터링합니다. 사전 작업분을 읽고 고칠 수 있고, 주제에 맞는 자기 기능을 얹고 싶은 분을 찾습니다.

6주를 함께 갈 분

2주는 짧지만 3개 프로젝트로 이어집니다. 만든 것을 다음 차수로 가져가 확장하는 방식이라 1차의 설계가 3차까지 갑니다.

매일 조금씩 하실 분

많이 하지 않아도 됩니다. 매일 조금씩, 중간 이탈 없이 끝까지 함께할 수 있는 분이면 좋겠습니다. 취업 준비 중인 대학생(20대 중반) 우대합니다.

미리 말씀드리는 것 — 읽고 결정해 주세요
  • 간단한 프로젝트는 아닙니다. 사전 작업분이 있어 시작은 빠르지만, 그만큼 완성도의 기준도 높습니다.
  • 역할은 고정이 아닙니다. 4개 영역은 주담당일 뿐이고, 원하는 기능을 제안하고 직접 만들 수 있습니다.
  • 다만 추가하는 기능은 “지표 기반 예측과 그 성과 검증”이라는 주제 안에 있어야 하고, 왜 넣었는지 설명할 수 있어야 합니다.
  • 기존 코드를 이해하는 시간이 필요합니다. 첫 이틀을 그 시간으로 잡아 두었고, ADR·README 가 준비되어 있습니다.
  • 개인 프로젝트의 코드를 가져오지만 팀 프로젝트는 별개의 저장소입니다. 기여는 팀 저장소의 커밋 이력으로 각자에게 남습니다.
  • 유료 LLM API 는 쓰지 않습니다(비용 0원 방침). 클라우드 인프라도 쓰지 않고 로컬 + Vercel 무료 범위에서 돌립니다.
