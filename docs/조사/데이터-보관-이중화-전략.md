# 데이터 보관 이중화 전략 — 구글 드라이브 5TB + HuggingFace

> 조사 2026-09-01 · 이동원
> 사용자 구상: *"실데이터 저장소는 로컬용으로 구글 드라이브, 코드와 연계해서 사용할 수 있도록
> HuggingFace, 그리고 구글 드라이브 공유하면 되지 않을까?"*

## 0. 직답 — 구상의 두 곳을 바꿔야 합니다

| 구상 | 판정 | 왜 |
|---|---|---|
| 로컬을 작업 정본으로 | ✅ 그대로 | — |
| **드라이브를 "실데이터 저장소"로** | ❌ **바꿔야 함** | 개인 계정은 **단일 실패점**이고 무결성 검증이 수동입니다 |
| HF 를 코드 연계용으로 | ✅ 그대로 — 오히려 **여기가 정본**이어야 합니다 | 커밋 이력·`hf_hub_download` 한 줄 |
| **드라이브를 팀원에게 공유** | ⚠️ **하지 마세요** | 약관 통제가 약하고, 팀원이 스크립트로 못 받습니다 |

**권고**

```

HF private  팀 공유의 유일한 경로 · 배포 정본
드라이브     아카이브 · 콜드 백업 (공유 끄고 나만)
```

## 1. 왜 드라이브를 정본으로 삼으면 안 되는가

전부 공식 문서 원문으로 확인한 것입니다.

| 제약 | 내용 |
|---|---|
| 🔴 **공유 드라이브를 못 만든다** | 개인(gmail.com) 계정에서는 Shared Drive 생성이 불가합니다. 소유권이 **사용자님 계정 한 곳**에 묶입니다 — 계정에 문제가 생기면 팀 전체가 멈춥니다 |
| 🔴 **공유해도 업로더 용량을 먹는다** | 공유 드라이브였다면 조직이 소유해 업로더 할당량을 안 쓰지만, 개인 폴더 공유는 **끝까지 사용자님 5TB 에서 나갑니다** |
| 🔴 **100MB 초과 파일은 팀원이 스크립트로 못 받는다** | 바이러스 스캔 확인 페이지가 뜨고, 이를 우회하는 `acknowledgeAbuse` 는 **파일 소유자만** 쓸 수 있습니다. 우리 `daily_price_dev.parquet` 은 142MB 입니다 |
| ⚠️ 전송이 느리다 | rclone 이 **초당 약 2파일**. 받으신 재무 830개면 약 7분 |
| ⚠️ 5TB 는 통합 용량 | *"5 TB of cloud storage across Gmail, Drive, and Photos"* — Drive 전용이 아닙니다 |
| ⚠️ 2026년 변경 | rclone **공용 client_id 폐기 예정** → 개인 client_id 발급 필수. Drive API 쿼터 개편 + 초과 과금 시작 예정 |

**바뀐 사실 하나** — 널리 알려진 "내 드라이브 500만 개 항목 제한"은 **2023년에 철회**됐고
현행 공식 수치는 **5억 개**입니다. 파일 개수는 우리에게 병목이 아닙니다.

## 2. 🔴 약관 — 가장 중요한 비대칭

**같은 한국거래소 시세라도 어느 문으로 받았는지에 따라 조건이 정반대입니다.**

| 출처 | 조문 | 재배포 |
|---|---|---|
| KRX Data Marketplace | 제12조② "사전 허락 없이 복사·복제·배포·전송·공중송신 금지" (2026-08-29 시행) | ❌ 전면 금지 |
| **KRX OPEN API** ← 우리 경로 | 제11조② "제3자에게 제공할 수 없다" + 제6조② "비상업적 목적으로만" | ❌ 금지 |
| **공공데이터포털** 금융위원회_주식시세 (출처: 한국거래소) | 이용허락범위 **"제한 없음"**, 무료, 자동승인 | ✅ 가능 |
| **OpenDART** | 재배포·제3자 제공 금지 조문 **없음** (제19조②는 *인증키* 공유 금지) | ✅ 조문상 제약 없음 |
| 공공데이터포털 금융감독원 DART API | 이용허락범위 **"제한 없음"** | ✅ 가능 |

### 우리에게 주는 뜻

- 우리 `daily_price` 920만 행은 **KRX OPEN API 로 받은 것**이므로 **재배포 금지 대상**입니다.
  → HF 는 **반드시 private**, 조직 멤버 밖으로 나가면 안 됩니다.
  → 드라이브 링크 공유는 통제가 약해 **더 위험**합니다.
- 받으신 **재무 830개는 OpenDART 출처**라 조문상 제약이 없습니다. 상대적으로 자유롭습니다.
- ⚠️ **앞으로 시세가 필요하면 공공데이터포털 경로를 검토할 가치가 있습니다** — 같은 자료인데
  재배포가 열립니다. (다만 이전 조사에서 지수시세정보는 **2020-01-01 부터**라 우리 2010년 기록을
  대체하지 못한다는 제약이 확인됐습니다.)

> 📌 **조항 번호가 팀 기록끼리 어긋났던 것**을 정리했습니다. 저장소 코드 주석은 "제11조②",
> 이전 세션 브리프는 "제12·13조"라 했는데 **둘 다 맞습니다** — 서로 **다른 약관**입니다.
> OPEN API 약관이 제11조②, 홈페이지 이용약관이 제12조②입니다.

## 3. HuggingFace — 용량은 문제가 아니고 패턴이 문제입니다

| 질문 | 답 |
|---|---|
| 무료 private 한도 | **100GB** (계정 전체 합산, 레포당 아님) |
| 우리 1.8GB 는? | **든다 — 100GB 의 1.8%** |
| Xet 이 중복 제거를 하나 | **한다** (~64KB 청킹, 전역 dedup) |
| 🔴 **dedup 이 quota 를 줄여주나** | **아니다.** 논리 크기로 과금됩니다 (Enterprise 제외) |
| 🔴 **날짜마다 통째로 다시 올리면** | **용량이 곱해집니다.** 새 파일만 추가하면 안 곱해집니다 |
| git 히스토리 | **누적됩니다.** 파일을 지워도 용량이 안 줍니다 |
| 과거 리비전 삭제 | `super_squash_history` — 되돌릴 수 없고 반영까지 36시간 |
| 백업처로 믿을 수 있나 | ❌ ToS 가 **무통보 정지·중단 권리**를 명시, 무보증(AS IS) |

**그래서 우리가 고른 "레포 분리 + git 태그" 방식이 맞습니다** — 파일 경로를 고정하고 태그만 다는
방식은 내용이 바뀐 파일만 새로 저장되므로 곱해지지 않습니다.

> ⚠️ 반대로 **날짜 폴더 방식**(`date=20260901/daily_price.parquet`)을 골랐다면
> 1.5GB × 날짜 수만큼 quota 를 먹었을 것입니다.

## 4. 용량 감축 — 전부 직접 측정했습니다

원본은 건드리지 않고 **사본에서** 쟀습니다 (2026-09-01).

### 4.1 SQLite VACUUM

```
전  1,585.6 MB
후  1,350.4 MB      −235.1 MB (−14.8%) · 23.3초
```

⚠️ `freelist_count` 가 **0** 인데도 줄었습니다 — 빈 페이지가 아니라 **단편화**가 원인입니다.

### 4.2 parquet 코덱 — daily_price 920만 행 전체

| 코덱 | 크기 | 쓰기 | 읽기 | db 대비 |
|---|---|---|---|---|
| snappy | 275.0 MB | 5.1초 | 0.4초 | 5.8배 |
| gzip | 222.5 MB | **152.1초** | 0.4초 | 7.1배 |
| **zstd** | **220.7 MB** | **5.2초** | 0.4초 | **7.2배** |
| brotli | 210.1 MB | 45.3초 | 0.5초 | 7.5배 |

> 🟢 **zstd 를 씁니다.** gzip 과 크기가 사실상 같은데 **29배 빠릅니다.**
> brotli 가 4.8% 더 작지만 쓰기가 **8.7배** 느려 증분 적재에 맞지 않습니다.

### 4.3 정렬 순서 (zstd 고정)

| 정렬 | 크기 | 차이 |
|---|---|---|
| 원래 순서 | 220.7 MB | 기준 |
| **(code, bas_dd)** | **193.2 MB** | **−12.4%** |
| (bas_dd, code) | 220.4 MB | −0.1% |

같은 종목을 붙여 놓으면 종목코드·종목명이 반복돼 사전 압축이 살아납니다.

### 4.4 row group 크기

| row group | 크기 | 읽기 |
|---|---|---|
| 64,000행 | 227.5 MB | 0.3초 |
| 256,000행 | 213.4 MB | 0.3초 |
| **1,000,000행** | **194.7 MB** | 0.3초 |

읽기 속도는 같고 크기만 줍니다.

### 4.5 🔴 날짜별 분할은 손해입니다

```
2026-08 이후 20거래일 · 55,278행
  날짜별 20개 파일 합계   2.99 MB
  한 파일로              1.63 MB      → 쪼개면 +82.7%
```

작은 파일은 압축 사전을 못 살립니다. 하루치 평균 0.15MB.
**증분은 "그날치 작은 파일"로 두되, 주기적으로 전체본에 합쳐야 합니다.**

### 4.6 최적 조합

```
zstd + (code, bas_dd) 정렬 + row group 1,000,000행
  → 194.7 MB   (원본 1,585.6 MB 대비 8.1배)
```

## 5. 용량 추정 — 5TB 는 남아돕니다

| 자료 | 지금 | 프로젝트 끝까지 (추정) |
|---|---|---|
| 시세·지수 (db) | 1.55 GB | ~1.7 GB (연 15MB 증가) |
| 반출본 (parquet/csv) | 206 MB | ~400 MB |
| **재무 (손으로 받은 TSV)** | **7.5 GB** | 7.5 GB → **parquet 변환 시 대폭 감소 예상** |
| 재무 (API 수집분) | 0 | ~100 MB |
| 거시 (ECOS 9종 등) | 0 | ~10 MB |
| 뉴스 (제목·요약) | 0 | ~수백 MB |
| **합계** | **9.5 GB** | **~10 GB** |

**5TB 의 0.2%.** 용량은 병목이 아닙니다.

⚠️ 다만 **재무 TSV 7.5GB 를 parquet 로 바꾸면 얼마나 주는지는 아직 안 쟀습니다.**
시세에서 7.2배가 나왔으니 비슷하다면 1GB 안팎이 되겠지만, **추정입니다.**

**진짜 병목 셋** — 전부 용량이 아닙니다.

1. **HF 무료 private 100GB** (계정 합산)
2. **약관** — KRX 자료는 조직 밖으로 못 나감
3. **드라이브 개인 계정의 단일 실패점**

## 6. 🔴 위험 목록

| 위험 | 왜 | 막는 법 |
|---|---|---|
| 🔴 **WAL 상태의 SQLite 를 동기화가 찢어간다** | 우리 DB 는 `journal_mode=WAL` 이고 수집 중 `-wal` 이 9.6MB 까지 자랍니다. 동기화 클라이언트가 본체와 `-wal` 을 다른 시점에 복사하면 **깨진 DB** 가 백업됩니다 | 드라이브에 **db 를 직접 두지 않습니다.** 백업할 땐 `VACUUM INTO` 로 정지 시점 사본을 만들어 그것만 올립니다 |
| 🔴 **동기화는 백업이 아니다** | 로컬에서 지우면 드라이브에서도 지워집니다 | rclone 은 **`copy` 만** 씁니다. `sync` 는 대상을 지웁니다 |
| 🔴 **HF public 전환** | 그 순간 KRX 약관 위반입니다 | `upload_to_hf.py` 가 이미 서버에 private 를 재확인하고 아니면 한 파일도 안 올립니다 |
| 🔴 **드라이브 링크 오설정** | "링크가 있는 모든 사용자"로 잘못 두면 공개 배포가 됩니다 | 팀 공유를 **아예 하지 않습니다** (HF 로 일원화) |
| ⚠️ HF git 히스토리 누적 | 206MB × 20회 ≈ 4GB | 전체본은 덮어쓰고, 증분만 새 파일로 |
| ⚠️ 드라이브 무결성 | 손상 여부를 자동으로 모릅니다 | `rclone check --checksum` 으로 `md5Checksum` 대조 (다운로드 없이 됩니다) |

## 7. 🔴 못 잰 것

- **재무 TSV 7.5GB 를 parquet 로 바꿨을 때의 실제 크기** — 시세로 유추만 했습니다
- **드라이브 실제 잔여 용량** — 사용자님 계정을 조회하지 않았습니다
- **뉴스 수집량** — 아직 수집기가 없어 규모를 모릅니다. 증가 시나리오의 최대 변수입니다
- **`dbstat` 로 표별 용량** — 이 SQLite 빌드에 `dbstat` 가 없어 못 쟀습니다
  (`no such table: dbstat`). 로그성 표가 얼마를 먹는지는 미확인입니다
- **FRED 접속 불가 원인** — 이 PC 에서 타임아웃이 나는 이유를 못 밝혔습니다
- Zenodo·OSF 같은 학술 보관처는 KRX 재배포 금지 때문에 애초에 후보에서 빠져 검토하지 않았습니다
