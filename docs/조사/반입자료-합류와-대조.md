## 1. 조사가 낸 답과, 그것이 틀린 이유

조사는 8개 계열(Databricks 메달리온 · dbt · Data Vault · Kafka DLQ · MDM · 금융 golden
copy · Feast · Airbyte)을 훑고 이렇게 권고했습니다.

> `supply/` 안에 이름이 다른 **두 번째 문**(`contrib_price_series`)을 열고, 거기에
> `source` 칸을 붙이며, `as_of` 를 `bas_dd` 뿐 아니라 **`inbox_accepted.loaded_at`
> (알게 된 날)에도 함께 걸어라.

세 관점(과잉설계 · 증거 · 우리 코드)으로 반박했더니 **3표 전부 기각**됐습니다.

### 1.1 🔴 인용문 다섯 건이 출처에 없었다

URL 을 직접 열어 확인한 결과입니다.

| 인용 | 실제 |
|---|---|
| LSEG Point-in-Time *"original data is never overwritten"* | 그 페이지에 **없음.** 게다가 그 제품은 **fundamentals** 이고 시세를 다루지 않는다 |
| thegoldensource *"exception queue"* | **없음.** 벤더 제품 마케팅 페이지 |
| ivp.in golden copy 설명 | **없음.** 저자 표기 없는 판촉물 |
| automate-dv *"소스가 늘면 satellite 을 늘린다"* | **논의하지 않음.** 오히려 `EFFECTIVE_FROM` 을 *"not part of the Data Vault 2.0 standard, optional"* 이라고 적는다 |
| Confluent DLQ *"요건은 넷"* | 그런 목록 **없음** |

**검증을 통과한 것은 4건뿐**이었고, 그 넷이 말하는 것은 우리가 이미 하고 있는 것이었습니다.

| 출처 | 원문 | 우리 상태 |
|---|---|---|
| dbt staging | *"joins are almost always a bad idea here"* | `accepted_frame` 이 join 을 안 한다 ✅ |
| dbt-utils `union.sql` | `source_column_name='_dbt_source_relation'` 이 기본값 | 합칠 때 출처 칸을 붙인다 — 아직 안 함 |
| MS Learn 메달리온 | *"recommended best practice but not a requirement"* · *"does not recommend writing to silver tables directly from ingestion"* | `daily_price` 를 안 건드린다 ✅ |
| Databricks quarantine | 버리지 않고 사유를 남긴다 | `inbox_quarantine` + `violations` ✅ |

> **교훈**: 블로그·벤더 마케팅을 "업계 표준"으로 부풀리기 쉽습니다.
> 포트폴리오에서 **확인 안 되는 인용은 자산이 아니라 부채**입니다.

### 1.2 🔴 막겠다는 구멍이 아직 없다

권고는 *"`as_of` 정문이 조용히 뚫린다"* 를 근거로 들었습니다. 실측으로 확인했습니다.

```bash
grep -rn 'inbox' supply/ features/ models/ evaluation/ timeseries/ --include=*.py
# → 0건
```

`inbox_accepted` 를 읽는 코드는 `ingest/inbox/store.py::accepted_frame` 하나뿐이고,
그것을 부르는 프로덕션 코드는 없습니다. **구멍은 두 번째 문을 여는 순간에 생깁니다.**

### 1.3 🔴 `loaded_at` 을 `as_of` 에 거는 것은 우리가 이미 기각한 설계다

`supply/clock.py` 머리말이 소제목까지 달아 적어 두었습니다.

> **"수집 시각은 답이 아니다."** 가장 흔한 실수는 '우리가 받은 시각' 을 그대로 쓰는
> 것이다. 우리는 2010년 자료를 2026년에 백필했다. 그 값을 그대로 쓰면 2010~2025년
> 전 구간이 '2026년에야 알 수 있었던 것' 이 되어 **백테스트에 아무것도 못 쓴다.**

반입 행의 `loaded_at` 은 전부 2026-09-xx 입니다. 우리 개발구간은 `DEV_END=20210831`
입니다. 즉 **올바르게 구현한 bitemporal 필터가 모든 호출에서 0행을 돌려줍니다.**
맞으면서 비어 있는 함수입니다.

인용된 Feast 조차 `filter_by_created_timestamp` 를 **기본값 False** 로 둡니다.
그 도구가 하지 않는 일을 그 도구를 근거로 요구한 셈입니다.

### 1.4 두 번째 문은 목적을 달성하지 못한다

`supply/training.py:144` 는 `price_series` 를 거치지 않고 `krx_store.series` 를 직접
부릅니다. 즉 `contrib_price_series` 를 만들어도 **학습 자료에는 반입분이 안 들어갑니다.**
문만 셋이 되고 조합이 늘 뿐입니다.

## 2. 대조 결과를 어디에 남기나 — "둘 다"는 절반만 맞다

조사는 *"값이 든 증거는 새 표 `inbox_reconcile`(v8), 판정은 파일"* 을 권고했고
이것도 3표 기각됐습니다.

### 2.1 검증된 도구들의 기본값은 전부 "저장 안 함"이다

이쪽 인용은 대부분 **정확했습니다**(원문 확인).

| 도구 | 값이 든 증거의 기본값 |
|---|---|
| dbt `store_failures_as` | `ephemeral — nothing stored in the database (default)` |
| AWS Glue DQ | *"By default, AWS Glue Data Quality does not write results to Data Catalog tables"* |
| Soda | failed-row samples 는 *"an opt-in feature"* |
| Great Expectations | **DB 가 아니라** gitignore 된 디렉터리(`uncommitted/`) |

GX 의 이유가 우리와 같습니다 — *"Validation Results can include sensitive or regulated
data that should not be committed to a source control system."*

### 2.2 🔴 v8 은 우리 엔진에서 만들 수 없다

```python
LATEST_VERSION = len(MIGRATIONS)   # = 5
# migrate() 는 range(current, LATEST_VERSION) 으로 돌며 MIGRATIONS[index] 를 쓴다
```

`ingest/store/sqlite_db.py` 는 `NEXT_MIGRATION_VERSION = 8` 이라고 적어 두었지만,
v6(공시)·v7(거시)은 **DDL 0줄 예약**이라 배열에 없습니다. **지금 항목을 더하면 v6 을
받습니다.** v8 을 잡으려면 빈 항목을 끼워야 하고, 그러면 진짜 공시·거시가 들어와도
그 DB 는 **영원히 건너뜁니다** — 예외도 경고도 없이.

> 주석 자신이 *"예약은 자리를 비워 둔 것이지 배포된 것이 아니다"* 라고 적어 두었습니다.
> 즉 **예약은 밀 수 있습니다.**

### 2.3 🔴 브랜치를 오가면 DB 가 깨진다

`user_version` 이 코드보다 높으면 `MigrationError: DB 가 코드보다 최신이다` 가 납니다.
**다운 마이그레이션이 없습니다.** feat 브랜치에서 마이그레이션을 돌리고 main 으로
체크아웃하면 반입 계층 공개 함수 5개가 전부 터지고, 그 DB 는 16년 백필이라 다시
만들 수 없습니다.

### 2.4 값은 이미 DB 에 두 벌 있다

그들 값은 `inbox_accepted.payload`, 우리 값은 `daily_price` — **둘 다 같은
gitignore 된 `krx_cache.db`** 안입니다. 대조 결과는 그 둘의 **함수**라 언제든
재계산됩니다. 세 번째 표는 파생값을 비정규화해 복제하는 것입니다.

### 2.5 그래서 사용자의 "둘 다" 직관은

**역할 분담으로서는 맞습니다** — 판정은 커밋되는 파일, 값은 커밋 안 되는 자리.
**그러나 DB 표를 새로 만드는 '둘 다'는 아닙니다.** 값이 갈 자리는 이미 있습니다.

```text
reports/inbox/<날짜>/대조.md      건수·비율만          (git 커밋)
data/inbox/reconcile/<batch>.json  값이 든 행별 증거    (gitignore)
```

`data/inbox/*` 규칙이 이미 덮으므로 **`.gitignore` 도 안 고칩니다.**
`batch_id` 마다 새 파일이라 재실행해도 안 덮입니다 — 새 표를 원했던 유일한
이유(append)가 파일에서 공짜로 해결됩니다.

## 3. 조사 과정에서 덤으로 찾은 결함

권고와 무관하게, 코드를 읽다가 나온 것들입니다.

| 무엇 | 어디 | 왜 문제인가 |
|---|---|---|
| `accepted_frame` 이 빈 결과에 **칸 없는 표** 반환 | `ingest/inbox/store.py:239` | `supply` 계약 위반. 반입 0행인 지금 **100% 이 분기**다 |
| 보고서 파일명에 `batch_id` 가 없다 | `ingest/inbox/report.py:277` | 같은 날 같은 이름 파일이 오면 덮이고, `inbox_batch.report_path` 가 거짓 포인터가 된다 |
| `aliases.close` 에 **"수정종가"** | `schemas/ohlcv_stock.json` | 수정주가가 원주가 `daily_price` 와 같은 칸으로 합격한다. **실재하는 유일한 restatement 경로** |
| `merge_asof` 가 `bas_dd` 에 안 걸린다 | — | 실측 `MergeError: Incompatible merge dtype` — 8자리 문자열이라 datetime 변환이 선행돼야 한다 |

`PRICE_COLUMNS` 를 정확 일치로 검사하는 곳은 **5곳**입니다
(`test_supply_price.py:109,115,197` · `test_supply_boundary.py:267,274`).
조사가 *"features 계약 테스트 23개"* 라고 한 것은 과장이었습니다 — 그중 칸을 보는 것은
하나뿐이고 `in` 검사라 칸이 늘어도 안 깨집니다.

## 4. 어휘만 빌려 온다 (비용 0)

도입은 안 하되 용어는 씁니다. 근거 링크가 붙어 문서가 업계 용어로 읽힙니다.

| 우리 것 | 업계 용어 |
|---|---|
| `ingest/inbox/schemas/*.json` | **data contract** |
| `inbox_batch` | **batch-level provenance** |
| `target.compareWith` | **reconciliation target** (merge 가 아니다) |
| `inbox_quarantine` | **DLQ** + sha 기반 재투입 경로 |

**도입하지 않는 것**: 메달리온 3층 전면 구축 · OpenLineage/Marquez 백엔드 ·
ODCS 전면 채택 · Great Expectations · 대조 전용 대시보드 · 금융권 대사 도구식
break 상태기계. 4인 · SQLite 하나 · 반입 0행 규모에 전부 과합니다.
