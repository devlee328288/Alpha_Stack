## 1. 왜 표를 하나 더 만드나 — 결과와 사건은 다른 자료다

우리 시세에는 **조정 결과**만 있었습니다.

| 있던 것 | 무엇을 말하나 |
|---|---|
| `daily_price.adj_close` 외 3칸 (v9) | 이미 펴진 값 |
| `daily_price.adj_source` (v9) | 그 값이 `fdr` 에서 왔나 `chain` 에서 왔나 |

*"무슨 일이 언제 얼마만큼 일어났나"* 는 어디에도 없었습니다. 물을 때마다
`common.corporate_actions.adjustment_factor` 로 923만 행을 훑어 **역산**해야 했고, 그 한
번이 4분입니다.

zipline 이 `splits`·`mergers`·`dividends` 세 표를 따로 두는 이유가 이것입니다. 배당은
v14 에서 이미 표가 됐으므로, 남은 자본 사건을 세웠습니다.

이것은 데이터파트 상태표의 **D-24**([데이터파트 v4.3 §200](../../데이터파트/version4.3/명세서.md))
가 *"없음. zipline 은 세 표를 둔다"* 로 남겨 두었던 자리입니다.

## 2. 설계에서 두 번 바꾼 것

### 2.1 `stock_base_info` 를 독립 출처로 잡았는데 아니었다

처음 설계는 *"시세와 종목기본정보가 다른 API 에서 오니 주식수를 서로 대조하자"* 였습니다.
그런데 겹치는 **9,229,173행 전부 같았습니다**(불일치 0).

```
daily_price.listed_shares  ==  stock_base_info.list_shrs      923만 행 전부
```

대조가 아니라 **복사**였습니다. 이 표가 홀로 주는 것은 **액면가(`parval`)와
상장일(`list_dd`)** 둘뿐입니다 — `isin_cd` 는 우리 구간에서 한 번도 안 바뀝니다(0건).

그래서 `corporate_action` 은 주식수를 `stock_base_info` 에서 읽지 않습니다. 그리고 액면가·
상장일은 **계단 함수**라 전량이 필요 없습니다 — 923만 행 중 실제로 바뀌는 자리는
**4,493행**뿐입니다(첫 행 3,677 + 액면가 792 + 상장일 24).

⚠️ 처음에는 전량을 dict 로 올렸다가 **14분을 넘기고도 안 끝났습니다.** 920만 개짜리 dict
가 메모리를 삼켰습니다. 계단으로 바꾸니 **264초**입니다.

### 2.2 `agrees` 를 배율이 있는 사건 전부에 매겼는데 순환이었다

처음에는 `rights_off`(3,191) · `resume_revalue`(783) 도 chain 과 대조했고, **전부
"맞음"** 이 나왔습니다. 당연합니다 — 이 둘은 배율을 `adjustment_factor` 에서 얻는데 그것을
다시 `factor_series` 와 견줬습니다. **검사가 대상과 같은 값을 씁니다.**

이 함정은 이미 아는 것이었습니다. `series_restart` 에는 피해 놓고(같은
`is_series_restart` 를 공유하므로) 바로 옆자리에서 밟았습니다. `agrees` 는 chain 이 배율
계산에 **쓰지 않는 축**(액면가·상장일)에서만 매기도록 좁혔고, 나머지는 `NULL` 입니다.

그 대신 chain 을 안 쓰고 재는 축을 **칸으로 따로** 세웠습니다 — `source_conflict` 입니다
(§3).
