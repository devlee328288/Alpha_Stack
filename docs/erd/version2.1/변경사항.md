# ERD 변경사항 — v2.0 → v2.1

> 2026-09-02 · 이동원 · 마이그레이션 v9 · 이슈 #51

Minor 개정입니다. 표 구조의 성격이 바뀐 것이 아니라 **v9 가 실제로 적용되어**
"예정" 이라고 적혀 있던 것이 실물이 됐습니다.

---

## 1. `daily_price` 에 칸 5개 (v9)

| 칸 | 형 | 뜻 |
|---|---|---|
| `adj_open` `adj_high` `adj_low` `adj_close` | REAL | 수정 시·고·저·종가 |
| `adj_source` | TEXT | `fdr` / `chain` |

v2.0 에는 *"v9 에서 추가하기로 확정"* 으로만 적혀 있었습니다. **적재를 마쳤습니다** —
9,223,644행 **전부**(100%) 채웠고 `fdr` 81.6% · `chain` 18.4% 입니다.

### v2.0 이 예상하지 못했던 것 세 가지

**① 외부 출처가 우리 구간의 일부만 덮는다.** FinanceDataReader 는 최근 3,000거래일만
줍니다 — 네이버 fchart 가 원천이고 서버가 자릅니다(`count` 를 6000·9000 으로 올려도
3,000 에서 잘리는 것을 실측). pykrx 의 `adjusted=True` 도 같은 경로입니다.
그래서 FDR 이 닿는 가장 이른 날을 앵커로 삼아 그 앞을 조정계수로 이어 붙였고,
그 사실을 `adj_source` 칸으로 행마다 남깁니다.

**그런데 경계가 종목마다 다릅니다.** 3,000일 창이 오늘이 아니라 **그 종목의 마지막
거래일**에 걸리기 때문에, 2015년에 상장폐지된 종목은 2010년까지 `fdr` 이 닿습니다.
20140613 이전 구간에도 fdr 행이 444,829행 들어왔습니다. **날짜로 유추할 수 없어
칸으로 둔 이유**가 이것입니다.

**② REAL 이어야 한다.** v2.0 은 형을 명시하지 않았는데, 후방조정 값은 정수가 아닙니다 —
삼성전자 2010-01-04 은 원종가 809,000 이 아니라 **16,180.00** 이 되고, 분할이 잦았던
종목은 1원 아래로 내려갑니다. INTEGER 로 뒀다면 조용히 잘렸을 것입니다.

**③ 외부 값을 그대로 실으면 고저 관계가 깨진다.** FDR 이 네 칸을 각각 따로 반올림해서,
원문에서 `close == high` 인 날에도 `adj_high(27,999) < adj_close(28,000)` 으로 뒤집힙니다.
표본 3종에서만 68행이었고 전부 fdr 행이었습니다(원가격 위반 0행).
**배율 하나를 네 칸에 똑같이 곱하는 것**으로 고쳤고 전체에서 위반 0행이 됐습니다.

## 2. `trading_calendar` 표 신설 (v9)

**PK `(bas_dd, market)`** · 4,102일 × (ALL·KOSPI·KOSDAQ) = 12,306행.

달력 로직 자체는 `common/trading_calendar.py` 에 이미 있었습니다(v2.0 시점에도).
**표로 옮긴 것은 속도 때문**입니다 — `SELECT DISTINCT bas_dd FROM daily_price` 가
9.2M 행을 훑어 599ms 걸리는데, 4,102행 표를 읽으면 13ms 입니다(**45배**).
두 답이 같음을 실측으로 확인했습니다.

⚠️ **파생 표**라 원본이 늘면 낡습니다. `adj_price.rebuild_calendar()` 를 시세 적재 뒤에
부르고, `common/trading_calendar.py` 는 표가 없거나 비면 **원본을 세는 폴백**으로 갑니다.

## 3. 🔴 스키마 변경이 드러낸 기존 결함 — `INSERT OR REPLACE`

칸을 더하다가 발견했습니다. `krx_store` 의 두 쓰기 경로가 이랬습니다.

```sql
INSERT OR REPLACE INTO daily_price (…원가격 15칸…) VALUES (…)
```

`REPLACE` 는 이름과 달리 갱신이 아니라 **행을 지우고 새로 넣습니다.** 그래서 문장에
없는 칸은 조용히 NULL 이 됩니다 — v9 가 얹은 `adj_*` 다섯 칸이 정확히 그 처지였습니다.

**시세를 하루만 다시 받아도 그 날 3천 종목의 수정주가가 통째로 사라지는데 행 수는
그대로**라 어떤 검증에도 안 걸립니다. (재무에서 PK 에 `account_detail` 을 빠뜨려 6.4%가
조용히 사라진 것과 같은 종류입니다.)

`ON CONFLICT(bas_dd, code) DO UPDATE SET …` 으로 바꿔 원가격 칸만 덮게 했습니다.
회귀를 막는 테스트를 `tests/test_adj_price.py` 에 넣었습니다.

## 4. 마이그레이션 실행부 — 지연 문장을 허용

`ALTER TABLE … ADD COLUMN` 에는 `IF NOT EXISTS` 가 없어 **두 번 돌면 예외**입니다.
그런데 `migrations.py` 의 규약은 *"문장은 여러 번 돌려도 같은 결과"* 입니다.

문자열만으로는 둘을 동시에 만족할 수 없어서, **연결을 받아 SQL 을 만들거나 `None` 을
주는 함수**를 문장 자리에 허용했습니다. 지금까지 쓰이지 않던 `add_column_sql()` 이
비로소 실제로 쓰입니다.

⚠️ `daily_price` 는 마이그레이션이 아니라 `krx_store.SCHEMA` 가 만듭니다. 그런데
`migrate_path()` 는 예산·raw·robots·반입이 각자 지연 호출하므로 **시세를 한 번도 받지
않은 DB 에서는 표가 없는 채로 v9 가 돕니다.** 그래서 표가 없으면 건너뛰고, 대신
**`krx_store.SCHEMA` 에도 같은 칸을 넣어** 두 경로가 같은 모양으로 모이게 했습니다.
한쪽만 고쳤다면 그 DB 는 v9 로 표시된 뒤 칸 없는 표를 만들고, 마이그레이션은 다시 돌지
않으므로 **칸이 영영 안 생겼을 것입니다.**
