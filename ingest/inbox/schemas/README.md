# 반입 규격 — 무엇을 어떤 모양으로 받는가

팀원이 손으로 모은 파일을 우리 파이프라인에 넣기 전에 **무엇이 맞는 모양인지**를 적어 둔 곳입니다.
규격은 커밋하고 파일은 커밋하지 않습니다 — 시세는 KRX 이용약관 제11조 ② 가 제3자 제공을 금지하고,
뉴스 본문은 언론사 저작물이며, 이 저장소는 **PUBLIC** 입니다.

| 규격 | 받는 것 | 대조할 표 |
|---|---|---|
| [`ohlcv_stock.json`](ohlcv_stock.json) | 종목 일별 시세 | `daily_price` (920만행) |
| [`ohlcv_index.json`](ohlcv_index.json) | 지수 일별 시세 | `index_price` (19.6만행) |
| [`news.json`](news.json) | 기사 제목·요약·링크 | 아직 없음 |
| [`financial.json`](financial.json) | DART 재무제표 계정 | 아직 없음 |
| [`macro.json`](macro.json) | ECOS·FRED·KOSIS 거시 지표 | 아직 없음 |
| [`sector.json`](sector.json) | KRX 업종분류 현황 스냅샷 (팀장이 화면에서 받음 · 연 1회) | `daily_price` (종가·시총으로 기준일 대조) |

바탕은 [Frictionless Table Schema](https://specs.frictionlessdata.io/table-schema/) 이고,
우리에게만 필요한 것은 `x-alphastack` 아래에 모았습니다. 표준 자리를 우리 뜻으로 덮어쓰면
나중에 표준 도구를 붙일 때 조용히 어긋납니다.

---

## 1. 규격 한 장의 구성

```jsonc
{
  "name": "…", "title": "…", "description": "…",
  "fields": [ { "name", "type", "title", "description", "constraints" } ],
  "primaryKey": [ … ],        // 행을 유일하게 가리키는 칸들
  "missingValues": [ … ],     // 이 문자열은 값이 아니라 '없음' 으로 읽는다
  "x-alphastack": {
    "version": "1.2",
    "target":          { "compareWith": "표 이름 또는 null" },
    "aliases":         { "칸이름": ["팀원 파일에서 나올 법한 다른 이름들"] },
    "ambiguousNames":  { "이름": { "candidates": [...], "note": "왜 못 정하는가" } },
    "rejectedNames":   { "이름": "왜 파일째 돌려보내는가" },   // news 에만 있음
    "fileMeta":        { "fields": [...], "note": "…" },       // financial 에만 있음
    "cleaners":        { "칸이름": ["정제 함수 이름", …] },
    "rowRules":        [ { "id", "expr", "severity", "note" } ],
    "lookahead":       { … }   // 미래참조를 어떻게 막는가
  }
}
```

## 2. `expr` 문법 — 파이썬 식이되 뜻은 우리가 정한다

`rowRules` 의 `expr` 은 **유효한 파이썬 식**입니다. 그래서 따로 파서를 만들지 않고
`ast.parse(expr, mode="eval")` 로 읽습니다.

> ⚠️ **문자열 치환으로 옮기지 마세요.** `and` → `&`, `or` → `|` 로 바꿔 보면
> 파이썬에서 비트 연산자가 비교보다 **먼저** 묶여 `a | b == 0` 이 `a | (b == 0)` 이 됩니다.
> 실제로 이 방식으로 종목 규격을 검증했더니 920만 행 중 **892만 행이 가짜 위반**으로 나왔습니다.
> 규격이 아니라 옮기는 쪽이 틀린 것이었습니다. `ast` 로 읽으면 우선순위는 파이썬 파서가
> 이미 옳게 알고 있으므로 그것을 빌리면 됩니다.

### 쓸 수 있는 것

| 종류 | 쓰는 법 |
|---|---|
| 칸 이름 | `close`, `bas_dd` — `fields` 에 있는 이름 그대로 |
| 비교 | `==` `!=` `<` `<=` `>` `>=` |
| 논리 | `and` `or` `not` (괄호로 묶어 뜻을 분명히 합니다) |
| 산술 | `+` `-` `*` `/` |
| 결측 | `close is null` · `close is not null` |
| 요일 | `bas_dd is weekday` (월~금이면 참) |
| 특수 이름 | `today` (오늘 YYYYMMDD) · `now` (지금 시각) |

### 함수 — 이 열 개뿐입니다

| 함수 | 하는 일 | 돌려주는 것 |
|---|---|---|
| `abs(x)` | 절댓값 | 수 |
| `len(x)` | 문자열 길이 | 정수 |
| `year(x)` | `YYYYMMDD` 에서 연도 | 정수 |
| `month(x)` | 월 | 정수 |
| `day(x)` | 일 | 정수 |
| `date(x)` | 시각에서 날짜만 | `'YYYYMMDD'` 문자열 |
| `time(x)` | 시각에서 시분초만 | `'HHMMSS'` 문자열 |
| `starts_with(x, s)` | 앞이 `s` 로 시작하는가 | 참/거짓 |
| `contains(x, s)` | `s` 를 품고 있는가 | 참/거짓 |
| `matches(x, re)` | 정규식에 맞는가 | 참/거짓 |

`date()` · `time()` 이 **문자열**을 돌려주는 것이 중요합니다. 날짜형과 문자열이 섞이면
같은 칸을 어떤 규칙은 날짜로, 어떤 규칙은 문자열로 전제하게 되고 어느 쪽으로 정해도
나머지가 깨집니다. 실제로 재무 규격 초안이 `rcept_dt.dt.year` 와 `rcept_dt == rcept_no.str[:8]`
을 함께 두어 두 식이 서로를 부정했습니다.

### 🔴 널 가드는 선택이 아닙니다

**비교하는 칸이 비어 있을 수 있으면 반드시 앞에 `is null` 가드를 답니다.**

```jsonc
// 틀림 — 널이 섞이면 비교가 False 로 떨어져 위반이 된다
{ "expr": "high >= low" }

// 맞음
{ "expr": "high is null or low is null or high >= low" }
```

가드를 빠뜨렸을 때 무슨 일이 생기는지는 실측이 있습니다. 지수 규격 초안이 이 가드 없이
`high >= low` 를 `error` 로 두어, **우리 자신의 자료 24,933행(12.73%)을 스스로 격리**했습니다.
격리는 자료가 나쁘다는 뜻인데 나쁜 것은 규칙이었습니다.

### 규칙을 새로 만들면 반드시 우리 자료에 먼저 돌려 봅니다

`error` 규칙이 우리 자료를 한 행이라도 격리하면 규칙이 틀린 것입니다. 팀원 파일을 받기 전에
여기서 먼저 압니다. 검사 방법은 [`tests/test_inbox_schemas.py`](../../../tests/test_inbox_schemas.py) 를 보세요.

## 3. `severity` — 격리와 표시는 다른 일입니다

| 값 | 뜻 | 그 행은 |
|---|---|---|
| `error` | 이 행은 쓸 수 없다 | `inbox_quarantine` 으로 간다 |
| `warn` | 이상하지만 쓸 수 있다 | `inbox_accepted` 로 가고 보고서에 표시된다 |

고르는 기준은 **"고칠 방법이 있는가"** 가 아니라 **"이 값을 학습에 넣으면 결과가 틀리는가"** 입니다.
`zero_ohlc` 는 283,468행이나 되지만 거래정지라는 사실 자체가 정보라서 `warn` 입니다.
반대로 `eff_dd_same_day_needs_premarket` 은 몇 행 안 되어도 그 몇 행이 미래를 보므로 `error` 입니다.

## 4. `aliases` — 한 이름은 한 필드에만

같은 이름이 두 필드의 별칭이면 검사기가 어디로 보낼지 정할 근거가 없습니다. 재무 규격 초안에서
`"당기"` 가 `thstrm_nm`(문자열 '제 56 기')과 `thstrm_amount`(숫자) 양쪽에 들어 있었고,
어디로 가든 뒤에서 조용히 깨지는 상태였습니다.

정할 수 없는 이름은 **어느 쪽 별칭에도 넣지 않고** `ambiguousNames` 에 적습니다.
검사기는 그 이름을 만나면 추측하지 않고 **사람에게 묻는 항목으로 보고**합니다.

`rejectedNames` 는 한 단계 더 셉니다 — 그 이름의 컬럼이 있으면 **파일째** 돌려보냅니다.
뉴스 본문(`content`·`body`·`내용`)이 여기 있습니다. 격리는 곧 `inbox_quarantine` 에 **저장**이라,
저작권 방어를 격리로 하면 본문이 우리 DB 에 내려앉습니다.

## 5. `cleaners` — 무엇을 무엇으로 바꿨는지 전부 기록합니다

정제는 자동으로 하되 **조용히** 하지 않습니다. 검사기는 칸마다 바꾼 값의 앞뒤를 세어
`reports/inbox/` 에 남깁니다.

| cleaner | 하는 일 |
|---|---|
| `strip` | 앞뒤 공백 제거 |
| `upper` | 대문자로 |
| `collapse_space` | 이어진 공백을 하나로 |
| `strip_comma` | `1,234` → `1234` |
| `strip_percent` | `3.5%` → `3.5` |
| `paren_to_negative` | `(1,234)` → `-1234` — 회계 표기의 괄호는 음수입니다. 떼기만 하면 손실이 이익이 됩니다 |
| `to_int` · `to_float` | 숫자로 |
| `to_yyyymmdd` | 어떤 날짜 표기든 여덟 자리로 |
| `zfill6` · `zfill8` | 엑셀이 지운 앞자리 0 을 되살립니다 |
| `drop_suffix_ks_kq` | `005930.KS` → `005930` |
| `map_market` | 시장 이름을 `KOSPI`/`KOSDAQ`/`KONEX` 로 |
| `map_source` · `map_freq` | 거시 출처·주기 표기를 통일 |
| `strip_html_tags` · `unescape_html` | 뉴스 제목의 `<b>` 와 `&amp;` |
| `drop_tracking_params` | 링크의 추적 파라미터 |
| `rfc1123_to_kst` · `to_kst_iso` | 시각을 KST 로 |

**여분의 컬럼은 버리지 않습니다.** 규격에 없는 칸은 `extras` 로 따로 모아 보고합니다 —
버리면 그 칸이 필요했는지 영영 알 수 없고, 팀원이 애써 모은 것을 말없이 없애는 일이 됩니다.

## 6. `lookahead` — 이 규격들이 존재하는 진짜 이유

미래참조는 예외를 내지 않습니다. 성능만 좋아집니다. 그래서 규격마다 **그 시점에 알 수 있었나**
를 어떻게 판단하는지 적습니다.

| 규격 | 시점 기준 | 언제부터 쓸 수 있나 |
|---|---|---|
| `ohlcv_stock` · `ohlcv_index` | `bas_dd` | 거래일 T 의 자료는 **T+1 0시**부터 |
| `news` | `pub_dt` (발행 시각) | 08:30 이전 기사는 당일, 이후는 **다음 거래일** |
| `financial` | `rcept_dt` (공시 접수일) | **접수일 다음 거래일**부터 |
| `macro` | `known_from` | 발표일, 없으면 (출처·주기)별 지연 추정 |

원칙은 하나입니다 — **항상 진실보다 늦은 쪽으로만 틀린다.** 앞당기는 방향이 곧 누설 방향이라,
확실하지 않으면 늦춥니다.

> ⚠️ **거래일 판정을 계산으로 하지 마세요.** `common.trading_calendar.trading_days()` 는
> 주말만 건너뛰고 공휴일을 모릅니다. 실측하면 개발구간(2010-01-04~2021-08-31) 평일 3,042일 중
> 실제 거래일은 2,880일로 **162일(5.3%)이 어긋납니다.** 진짜 거래일 달력은 `daily_price` 의
> `bas_dd` 실측 집합입니다.

미래참조 차단이 **실제로 강제되는 곳은 `supply/` 정문 하나뿐**입니다. 반입 규격은 그 사실을
적어 두고 어긋난 행을 잡을 뿐, 스스로 `as_of` 를 강제하지 않습니다.

## 7. 규격을 고칠 때

1. `x-alphastack.version` 을 올립니다.
2. 새 규칙은 **우리 자료에 먼저 돌려 봅니다.** `error` 가 한 행이라도 걸리면 규칙이 틀렸습니다.
3. 일부러 어긋난 행을 만들어 **실제로 잡히는지** 확인합니다. 통과만 보고는 검사가 도는지 알 수 없습니다.
4. `note` 에는 무엇을 하는지가 아니라 **왜 그렇게 정했는지**를 씁니다. 무엇을 하는지는 `expr` 에 이미 있습니다.

## 8. 개정 이력

### v1.2 (2026-09-01) — 종목코드가 여섯 자리 숫자가 아니었다

`code`·`stock_code` 의 `pattern` 을 `^[0-9]{6}$` 에서 **`^[0-9]{4}[0-9A-Z]{2}$`** 로 넓혔습니다.

🔴 **왜 고쳤나.** v1.1 로 우리 자료를 왕복시켜 봤더니 `code.pattern` 위반이 나왔습니다.
전체 구간에서 **56,190행(0.61%) · 84종**입니다. 값을 보니 전부 실재하는 정상 종목이었습니다.

| 자리 | 실측 | 예 |
|---|---|---|
| 1~4번째에 영문 | **0종** | — |
| 5번째에 영문 | 57종 | `0004Y0` 디비금융제14호스팩 · `0007C0` 아크릴 |
| 6번째에 영문 | 28종 | `00781K` 코리아써키트2우B · `08537M` 루트로닉3우C · `00341A` 쌍용양회4우B |

KRX 가 여섯 자리를 다 써서 **영문을 섞기 시작한 것**이라 앞으로 늘어납니다. 신형우선주(2우B·
3우C)는 끝자리가, 최근 상장·스팩은 다섯째 자리가 영문입니다. 길이는 3,677종 전부 6이었습니다.

**왜 `^[0-9A-Z]{6}$` 로 다 열지 않았나.** `pykrx`·`FinanceDataReader` 같은 라이브러리는
종목코드에 정규식을 아예 걸지 않습니다 — KRX 가 주는 문자열을 그대로 씁니다. 그 관행을 따르면
패턴을 지우는 게 맞지만, 반입은 **남의 파일을 받는 자리**라 오타는 잡아야 합니다. 그래서
관행만큼 느슨하되 **실측이 보장하는 만큼만** 조였습니다 — 앞 네 자리는 3,677종 전부 숫자입니다.

`cleaners` 에 `upper` 를 더했습니다(`strip → upper → drop_suffix_ks_kq → zfill6`).
팀원이 `00781k` 로 적어 오면 v1.1 에서는 격리됐는데, KRX 원본이 전부 대문자라 올려도 잃는
정보가 없습니다.

**되잰 결과**: 개발구간 무작위 12만 행 → 격리 **0건**. 영문 코드 19,297행 전량 합격.
